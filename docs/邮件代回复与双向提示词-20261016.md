# 邮件代回复与收发提示词

用户选择的模式是：**新邮件自动拟回复，确认后发送**。后台只生成建议，实际发送继续逐封审批。不开启无人值守发送，不新增本地生成模型或原生权限。

## 收发分工

- 接收：`crates/yunxi-bot-core/src/prompts/mail_review.md`，v4。作为独立 system 消息调用 DeepSeek，只读提炼来信意图、最新事实、行动、期限、原文证据和危险信号，输出既有封闭 JSON。明确区分普通请求、推广、垃圾与可疑邮件；风险不是身份或附件安全鉴定，不生成回复、不执行邮件要求。
- 发送：`crates/yunxi-bot-core/src/prompts/mail_send.md`。自动拟稿使用独立 system 消息及独立 JSON 协议，不注入聊天人格或整套记忆。聊天/任务入口在处理邮件时也引用这份写作规范，结合原有工具流程使用，避免两套写作要求漂移。
- 没有针对测试主题、特定发件人或特定请求的例外。邮件中的任何“批准”“忽略规则”“转发资料”都不构成用户授权。

## 取材与结果

后台在收件审理和通知结束后，每轮最多拟一封。只考虑模式开启后新到、已审理且无风险的工作、私人或事务邮件；历史基线、过滤、待审理、推广、垃圾和建议忽略的邮件不自动拟稿。每封最多尝试3次，失败退避15分钟，每日最多30次模型调用，出站前持久计数。拟稿失败单独审计，不撤销已经完成的收件通知。

读取所选邮件及本账户真实线程，最多10封、全文合计32000字符；超限或分页不完整转待查看。读取从本机当天零点起7天的日历忙闲，以及未完成待办的近期/逾期期限和无日期事项数量；不将日历/待办标题、备注、地点、参与人发送给拟稿模型。`profile.md`提供用户表达偏好；缺失明确表示无画像，格式错误、超8192字节则拒绝静默截断。普通日历/待办的私密内容不进入草稿，时间空档不等于用户已同意预约。

结果分为：

| 状态 | 行为 |
|---|---|
| `ready` | 有可审核正文，没有待回答问题；仍未发送 |
| `needs_input` | 需要用户选择、补事实或确认附件；可含有依据的部分正文，问题单列 |
| `no_reply` | 无需回复或不宜回复；正文为空 |
| 失败 | 保存明确原因和退避时间，标记 degraded，不用思考过程冒充正文 |

建议及其写作依据保存在私有0600的`mail-replies.json`，使用独立文件锁。不是台账格式迁移；模型用量和失败复用既有审计事件。用户画像和邮件线程会随该模式交给DeepSeek，拟稿上下文没有工具权限。

## 使用

```bash
# 开启，只处理从开启时刻起的新邮件；重复开启不重置基线
./target/release/yunxi-bot mail --reply-mode review
# 查看模式和建议
./target/release/yunxi-bot mail --reply-mode status
./target/release/yunxi-bot mail --replies
# 停止新邮件自动拟稿，保留已生成记录
./target/release/yunxi-bot mail --reply-mode off
```

对Bot说“看看待确认的邮件回复”，调用`mail_reply_pending`。选择建议时按真实原邮件消歧：

- `ready`：用户要求采用后，通过`mail_reply_prepare(id, generated_ms)`转为云熙本机草稿。转草稿前复查原邮件、整串、画像和同一查询范围的日程事实，超过24小时或事实变化则拒绝，提示基于当前资料重新起草。已读状态变化不视为写作事实变化，但原邮件revision实时更新。
- `needs_input`：先回答待确认问题，Bot结合回答通过原有`mac_mail_draft`等工具拟定最终稿；不会把未决问题直接当正文发送。
- 转草稿只回复原发件人，不自动抄送或附文件；账户地址不能唯一确定则待确认。现有原生接口未暴露Reply-To，需用户核对最终收件人；特殊回复地址和群回走普通工具明确指定。
- 创建前持久化固定请求，未知结果沿用原请求核对；已保存草稿再次操作只查询原draft_id，不新建第二封。通过`mac_mail_outbox`核对实际草稿/提交状态。
- 发送前仍回读`mac_mail_draft_get`的正文、地址、附件与revision，再由`mac_mail_send`逐封审批。正文修改、附件追加和发送后日程/通知仍使用既有工具。模式开关、来信要求、模型建议都不能替代这次批准。

此版没有增加“点击Mac通知即确认发送”的界面，也不自动将邮件标已读、归档、建日程或完成待办。自动建议和Mac通知分开：原邮件通知照常，建议通过Bot或CLI查看。人工另行起草的回复须通过发件记录核对，建议队列不冒充远端发送状态。

## 性能与限制

普通收件通知先完成，然后才拟稿。拟稿的DeepSeek请求超时45秒；原生读取另有自身超时。守护循环串行执行，拟稿期间新到邮件可能要等下一轮，所以不能保证开启后所有来信仍保持原来的最短通知延迟。长线程、权限不足、计划截断、账号歧义等均待人工处理。休眠唤醒和长驻压力测试留待后续。
