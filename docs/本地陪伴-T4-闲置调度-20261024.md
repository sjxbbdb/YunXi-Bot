# 本地陪伴 T4：闲置记忆调度

状态：2026-10-24，已实现并验证。

## 决策

- chat-server 启动后，如果 **N 秒没有新的聊天输入**，后台线程自动处理一条待整理对话。
  - 默认 `N = 600`（10 分钟）；
  - `YUNXI_MEMORY_IDLE_SECONDS` 可改；`0` 关闭；
  - 测试用 `2` 秒加速。
- 每次只处理一条 `ConversationObserved`；处理完继续等，不阻塞聊天请求。
- daemon 的 `--agent` 路径仍是兜底：App 关闭后，daemon 继续按自己的 60 秒轮询整理。
- chat-server 和 daemon 共用 `<data>/memory.lock`；拿不到锁就等下一轮，避免同一条对话被两边同时提炼。
- 本机模型未监听时返回 `Unavailable`，**不写已完成标记、不回落云端**，下次继续尝试。
- 处理流程复用 T3：Laya 门控 → 本地 Gemma 抽取 → 自动确认 → EmbeddingGemma 向量化。

## 验收

临时数据目录 `/tmp/yunxi-t4-final`，无 DeepSeek 密钥；本机 Gemma/Laya/EmbeddingGemma 在回环端口运行。

条件：`YUNXI_MEMORY_IDLE_SECONDS=2`，预置一条 `ConversationObserved`，不发送任何聊天输入。

结果：

```text

[陪伴记忆] 空闲整理写入 1 条，向量化完成
ledger: conversation_observed=1, info_triaged=2, memory_proposed=1,
        memory_recorded=1, memory_proposal_resolved=1
vector_exists: true
```

说明：
- `info_triaged` 包含 `gate_store` 与 `candidates_only`；
- `vectors/memory.json` 已生成；
- 线程在空闲期间持续等待，没有重复提炼同一条来源（`next_source` 已记录完成）。

## 已知限制

- 当前是“空闲后处理一条，再每 5 秒检查下一条”；大量积压会逐条处理，不会一次批量清空。
- daemon 兜底仍要求本机模型可运行；本机模型未启动时只降级，不上云。T9 再评估 daemon 的本地服务拉起。
- 本地抽取失败时 `save_consolidation` 会写降级完成标记，暂不会无限重试；后续加失败重试/退避。
