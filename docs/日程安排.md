# 日程安排（Mac）

用于“先安排一天，临时增加事项后再排剩余时间”。已接入 chat、do、resume、daemon 共用的工具注册入口，生成与自然语言理解继续走 DeepSeek；没有改动 Laya、微调或审批策略。第三批复用此排程器加入[出行住宿与多日行程](出行住宿与多日行程.md)，事项可用`details`保留预订来源和地址等资料，存于对应提醒事项。

最新统筹增补及验证见[日程统筹验收](日程统筹验收-20261016.md)：支持同日先后关系、必需事项阻塞、原时间与改排时间说明；6个真实场景、81项检查通过。下方早期验收数字按阶段保留。

## 怎么用

启动 `./启动.command` 后可以直接说：

- “今天要写报告90分钟、练习60分钟，帮我安排好，写进Mac日历和提醒事项。”
- “今天再加上买东西30分钟，必须17点前完成，重新安排并同步。”
- “报告已经完成，标记完成，再安排剩下的事情。”
- “查看今天已经保存的安排。”

用户已确认的默认可安排时段为 **09:00–12:00、13:00–18:00**，事项之间留 **10分钟**。可为某一天设置其他时段；已保存的当天设置会随待办保留。首次新日期使用默认值，不假定所有事情都能排下。没有时长时先询问使用者，模型不能把猜测当已确认时长。

## 两个工具

| 工具 | 行为 | 权限 |
|---|---|---|
| `mac_agenda_plan` | 读系统记录、合并新增或修改的事项、返回安排和具体变更；不写入 | 只读 |
| `mac_agenda_apply` | 复读并校验预排版本，批量同步日历和提醒事项，最后回读核对 | Outbound，显式批准或预授权 |

应用安排前会显示完整计划与创建、修改、删除的具体影响。系统授权不代替 Bot 审批；模型判断不能放行。用户明确要求同步时，模型直接调用 apply 交给审批层处理，避免再作一次口头确认。仅查看或只要方案时不写入。

参数示例（可用时间由 Mac 系统时区解释；事项的日期时间必须带偏移）：

```json
{
  "date": "2031-04-18",
  "tasks": [
    {"id": "report", "title": "写报告", "duration_minutes": 90, "priority": 3},
    {"id": "buy", "title": "买东西", "duration_minutes": 30,
     "deadline": "2031-04-18T17:00:00+08:00", "priority": 4}
  ]
}
```

apply 使用同一组参数，再添加 plan 返回的 `revision` 作为 `expected_revision`。追加时只传新增事项；修改/完成/取消时先读取原有 `task`，沿用 id，提交修改后的完整 task。`tasks: []` 或省略 tasks 表示保留全部已有事项，绝不表示清空一天。

- `priority` 为1–5，5最高；`status` 为 `pending` / `completed` / `cancelled`。
- `earliest`、`deadline`、`fixed_start` 可选，均为带时区的 RFC3339。
- `must_schedule`用于不可遗漏的事项；`after_task`指定同日必须先完成的事项ID。两者与准备通勤关联一起统筹，详见[出行与原日程统筹](出行住宿与多日行程.md#与原有日程统筹)。
- `settings` 可选，形式为 `{"windows":[{"start":"09:00","end":"12:00"},{"start":"13:00","end":"18:00"}],"buffer_minutes":10}`。
- 查询结果中的 `entries` 是完整事项及对应系统 ID；`changes` 是待写入的具体动作；`unscheduled_count` 表示尚未排入的事项数。
- `applied: true` 只确认当前 Mac EventKit 已保存并读回，不能声称其他设备已收到同步或用户已看到提醒。

## 排程规则

1. 先读取当天所有账户的日历，作为不可移动的占用。其他日历只读。
2. 已开始、过去以及用户在日历中手动移动的时间块保持原位；过去未完成的事项会提示核对，不擅自认定完成或重复安排。固定会议不随其他事项自动移动，但显式修改其 `fixed_start` 或时长时可以更新原记录。新时间有冲突则拒绝整次修改，保留原安排；已开始或手动改动的会议需要先核对。
3. 其余事项先满足先后关系，再在可处理事项中依次按固定开始、必须安排、截止时间、优先级、稳定 id 排进空档。普通时间块按5分钟边界展示，避开午休与已有约会，并保留间隔。
4. 普通事项排不下保留提醒事项并明确原因；必须安排的事项排不下或固定衔接矛盾时，返回`blocking_issues`与`ready_to_apply:false`，拒绝整次写入。不挤占固定约会、不偷偷延长工作时段。提醒时间设在计划开始；未排入的普通事项使用已给出的截止时间，没有截止就不设提醒。
5. 新事项加入后，重排仍可移动的时间块，沿用原有日历和待办 ID。完成或取消后，移除尚未开始且可移动的时间块，待办保留完成记录；已开始/过去或受保护的日历记录不删。
6. 已有受保护事项之间的冲突通过 `conflicting_preserved_tasks` 返回，不能因为不能移动就隐去冲突。

这是确定性的空档排程，不保证数学上的全局最优，不拆分单项任务，不会因为晚了一会儿就无限向后推迟所有事项。

## 自然表达与连续追问

不要求命令格式。可以连续说“我今天下午三点有个会”→“改到四点”→“一个小时”：先询问缺少的时长，再沿用同一事项预排；说“同步进去”后才进入实际写入审批。已保存事项可以接着说“改到四点”“半小时就够了”“取消刚才那个会”。

chat使用非阻塞的`ask_user`，问完结束本轮，外层循环接收下一条消息；提问的同批其他动作暂不执行并留痕，即使已有预批准也不会一边提问一边猜着执行。无提问工具时可直接用文字询问。独立任务步骤保留同步问答。回答只补信息，不替代审批。

追问和短答随原有会话保存，`chat --resume <会话ID>`可以恢复。每条原话附带当时的本机时间，隔天恢复不把旧的“今天”解释成新的日期；新说的“明天/后天”按当前发言时间理解。不改变会话文件或台账格式。

- 缺时长不按一小时试排，“好”不能补全时长；已知信息不重复问。
- “第二个”依上下文定位；“其中一场”无法确定对象时先问。
- 尚未保存的多事项草案，修改一件仍保留其余事项；已保存事项先回读，沿用原ID修改。
- 取消未保存事项不操作日历，换话题停止推进。引用台词、假设和过去的事情不自动创建日程。
- 只有真实工具成功回执才报告同步；已有固定会议明确改时/改时长可以更新原记录，冲突则保留原安排。
- 单日工具不能跨日迁移。第三批多日工具可在用户明确确认后组合“旧日取消、新日安排”，需整份重新预排；没有跨日原子迁移或自动结转。未保存草案可以修改日期。

## 准备和通勤

第二批工具支持把真实路线耗时与用户指定的准备时间放入当天安排。例如“明天下午三点开会一小时，从人民广场步行过去，提前准备15分钟”：先确认目的地、出行方式及日期，查询地址坐标、路线和天气，再生成会议及关联时间块。

```json
{
  "date": "2031-04-18",
  "tasks": [
    {"id":"meeting","title":"开会","duration_minutes":60,"fixed_start":"2031-04-18T15:00:00+08:00"},
    {"id":"travel","title":"准备并前往会议","duration_minutes":45,"travel_for":"meeting"}
  ]
}
```

此处45分钟仅示例：实际参数必须使用`mac_route`返回的分钟数加用户确认的准备时间。天气预报只支持近期16天，不能为示例里的远期日期编造天气。

- `travel_for`指向同日固定会议ID，每场会议只接受一个合并的准备/通勤时间块。
- 开始时间由会议时间减去间隔和总耗时得到；默认仍留10分钟间隔，不将赶路排到会议开始之后。
- 改会议时间后，关联时间块沿用原ID移动；取消/完成会议时同步处理关联事项，跨会话也可从系统记录恢复。
- 已开始或手动移动的关联事项继续受保护。对象缺失、链式关联、重复关联、跨日或冲突时拒绝整次预排，不能保存一个无法到达的方案。
- 会议时间、地点或方式变化后应重新查询路线和天气，并更新时长；排程器不会自动假定旧ETA仍然准确。

新增3项规则测试及1项真实EventKit生命周期测试已通过，另有真实模型“路线+天气+准备时间+会议预排”验证，见[第二批工具验收](第二批工具验收-20261016.md)。

## 数据、重试与并发

事项时长、截止、状态、当天时段等业务数据写在该事项的 **iCloud云熙提醒事项备注**中；对应日历时间块也带关联标记。格式以 `云熙日程 v1` 开头，请不要手工删除这段关联信息。换会话或重启后重新读取 EventKit 即可恢复；没有另建 Agent 状态数据库，不改变台账格式。

日程查询在原生端按当天备注前缀过滤，再应用200条上限，旧日期的已完成待办不会耗尽当天额度。元数据损坏、列表不完整、重复 id、失去关联记录、权限不足都明确失败，不当成空日程。

apply 的版本覆盖事项、系统记录版本、日历占用及具体写入动作。批准后如发生变化，拒绝写入并要求重新预排。不同 Bot 进程的日程应用通过文件锁串行；每次原生修改继续校验记录版本。创建使用稳定请求编号，删除时间块前保存下一代编号，恢复未完成时可以重新安排而不撞上旧创建回执。

Mac 日历与提醒事项之间没有事务。中途失败会返回 `degraded: true`、原因与已有回执，可能已经完成一部分；重新预排读取真实系统状态后再应用，不能换事项 id 盲目重试，也不会自动回滚用户已经看见的改动。系统应用及其他设备的同时修改不受 Bot 文件锁约束，采用保存前版本校验和批次结束回读，不能宣称跨应用原子事务。

## 范围与验证

首版每天最多40个受管事项、8个可安排时段，每次日历查询最多200条。所有全天日历事件保守地视为占用，暂不根据节日/生日推断“其实空闲”。支持同日固定会议的准备/通勤关联；重复事项、带参与者会议、跨午夜任务、跨日自动结转、后台持续监听及休眠补偿不在本次范围内。额外晚间时段可以显式设置。

```bash
cargo fmt --all -- --check
cargo build
cargo test
cargo clippy --all-targets -- -D warnings
bash scripts/build-macos-tools.sh
# 原生应用重新签名后可能需要再次允许系统权限
./启动.command mac status

# 需要真实权限，创建未来合成事项，退出时清理：
cargo test live_day_plan_replan_complete_reopen_and_recover_new_session -- --ignored --test-threads=1
# 真实DeepSeek对话；报告路径必须未存在：
.venv/bin/python sidecar/e2e_agenda.py --output /tmp/agenda-e2e-new.json
```

规则测试覆盖约会、午休、间隔、截止、优先级、临时插入、已开始/已完成保护、手动移动、取消和恢复、跨会话设置恢复、写入中断、重复请求、过期计划、损坏与截断数据、拒绝优先、并发锁及回读冲突；另有60组不同事项组合验证“不重叠、不越界、不超过截止”的不变量。
