## 发现的问题与本轮改动

**搜索服务故障已解决。** 初测没有博查凭证，DuckDuckGo Lite 返回反爬挑战页。工具及模型如实报错，该次不计通过。用户随后指出桌面“资料”文件夹中的 API 凭证，已在本机导入 `data/secrets/bocha.key`（0600，不入 Git、不入报告），沿用现有博查实现。

配置后发现第二个问题：原英文查询前三条是博客或镜像，模型就提前结束。现在 `web_search` 描述反映真实后端，新增可选 `domain` 参数；博查使用 `include` 参数，DuckDuckGo 使用站点查询，并对实际返回 URL 再做域名边界校验。无效域名、伪装子域名及用户信息伪装均有回归测试。聊天系统提示明确：首轮没找到目标时，在最多两次追加查询内继续缩小范围，不停在“需要的话可以继续搜”，不编造官网。

原题目没有更换，也没有放宽官网验收条件；反而增加了对真实 URL 主机名和最终回复引用的核对。修复后两轮真实调用均得到官方域名链接，最终完整基础工具回归再次通过。失败尝试分别保留；宽泛搜索仍不保证官网排在前三，完成目标依赖明确的限域续查。没有恢复模型微调。

**旧 `ask_user` 验收条件与 D143 不一致，已修正。** 旧脚本寻找同步工具结果中的“使用者回答”，新版实际返回等待提问的结构化回执，并在下一轮收到用户输入。现在核对工具回执、保存的对话中真实 user 回答及其后的 assistant 回复；缺少后续回答、只出现选项文字、错误回复或坏回执均不能通过。先加入复现测试，再修正验收器。产品运行逻辑没有因这项修复改变。

**初次基础工具整轮隔离断言失败，未计入通过。** 当时另一个验收进程同时向真实数据目录写测试日志，污染了前后目录快照。后续将其他报告暂存到 `/tmp`，完成独立复跑后再归档；最终 10 个基础工具的严格 `real_home_untouched` 检查通过，没有放宽忽略范围。

Mac 模型验收脚本补充了日历/提醒事项的直接查询场景、明确权限状态断言，并把日程工具也加入非预期调用的拒绝列表。基础工具脚本会在搜索验收时借用已配置的博查凭证到临时 0600 文件，以匹配真实默认后端；凭证不进入报告。
