# 实时票务与酒店接入评估

核对日期：2026-10-17。用户已明确要求覆盖中国境内票务与酒店预订，验收目标为国内铁路、国内航线、国内酒店、人民币支付及订单退改。本轮为公开文档和项目源码研究，没有申请账号、安装第三方服务、调用付费接口或创建订单。以下是接入建议，尚未改变项目架构或开启交易能力。

## 建议结论

先验证 **RollingGo 国内酒店链路 + 聚合数据铁路查询**；国内机票继续核实同程等正规交易渠道。Duffel 不纳入当前国内落地范围。

**当日复核更正**：RollingGo 仓库 README 仍列出机票工具，但其[官方工具文档](https://rollinggo.store/docs/mcp-docs/mcp-tool-reference/)已标注机票业务暂停下线维护，因此不能作为当前可用的国内机票渠道。该文档还明确普通 Key 酒店模式不提供 Agent 下单及订单管理；列表价格只是首夜展示参考价。需要核对总价、房态和最终预订条款，不能据列表报价承诺可订。

酒店除了普通 Key MCP，还发现官方公开的[国内酒店 CLI/Skill 项目](https://github.com/RollingGo-AI/rollinggo-hotel-skill-cn)，描述了 OAuth 登录、验价、生成支付链接和查单流程，面向支付宝支付。它与商务 OAuth MCP 是不同接入入口；实际账号资格、CLI 对应交易权限和取消退款能力仍待实测，不能统一断言“完整订单一律只能商务开通”。

此前调研优先看同程企业接口；本次新增了有公开自助申请路径的候选。不过申请入口存在不代表账号一定获批，更不代表全部下单、支付和售后权限都已经开放。

| 候选 | 已核实的公开能力 | 准入与适用性 |
|---|---|---|
| RollingGo 国内酒店 | 普通 Key 提供搜索、详情、标签和预订链接；官方另有支持登录、验价、生单及查单的国内 CLI | 普通接口官方称当前免费；CLI 交易权限需实测，商务 OAuth MCP 另行开通。机票暂停维护，暂不选用。见[工具契约](https://rollinggo.store/docs/mcp-docs/mcp-tool-reference/)、[国内 CLI](https://github.com/RollingGo-AI/rollinggo-hotel-skill-cn) |
| 聚合数据铁路 817 | 公开 REST 文档包含车次、时刻、席别价格和余票；宣传另有订票 MCP | 产品标注“查得计费”；具体个人准入、套餐、余票时效及交易工具仍待登录核验。REST 查询不能冒充已开通出票。见[官方文档](https://www.juhe.cn/docs/api/id/817) |
| 同程商旅 | 官方宣布 MCP/Skills/CLI，可查询实时航班、酒店和火车票 | 公告面向企业系统；没有得到个人自用项目可用端点、费用和交易权限。见[官方公告](https://tmc.ly.com/zh/resources/updates/open-mcp-skills-cli) |
| 同程旅仓 | 酒店实时详情、验价、创单、支付、订单查询、取消及通知接口公开 | 需要分销账号及 AES 密钥；机票不向分销商开放。是酒店深度交易候选，不能替代铁路/机票渠道。见[官方接入范围](https://open.lvcang.cn/doc/api/agent/skill) |
| Duffel（本轮不选） | Flights + Stays，有报价、预订和订单管理文档 | 不作为当前国内需求的落地渠道；保留研究记录，不投入对接。见[生产激活](https://duffel.com/docs/guides/getting-started-with-the-dashboard)、[Stays](https://duffel.com/docs/guides/getting-started-with-stays) |

携程商旅仍是商务候选，本次没有取得足以判断个人项目准入及原始库存权限的公开接口契约，不把其品牌覆盖等同于可直接接入。

## 查询、报价与交易必须分别核实

### 酒店

RollingGo 国内版本将普通 Key 和 OAuth 订单能力分开。后者包括验价、创建带支付链接的订单和查单，须商务对接；不应依据宣传语向普通 Key 暴露猜测的交易工具。[官方说明](https://github.com/RollingGo-AI/RollingGo-hotel-MCP-CN)

官方国内 CLI 是另一个应先验证的入口：`rgh login` → `search-hotels` → `hotel-detail` → `price-confirm` → 经用户批准 `book` → `orders`。官方示例为国内酒店、CNY 和支付链接。尚未验证其生产可用性。同日进一步读取官方 Skill 的参数表，已发现订单详情、预取消费用查询及确认取消的文档契约；实际 CLI 版本、账号交易权限与退款终态仍未联调，不能据此称退订退款已在云熙实现。也不能照搬示例在尚待付款时称“预订成功”。详见[源码复核](电脑操控与国内出行-开源实现评估-20261017.md)。[官方 CLI 说明](https://github.com/RollingGo-AI/rollinggo-hotel-skill-cn)

旅仓的正式链路和关键约束可直接核对：

| 步骤 | 官方接口 | 实现时需要注意 |
|---|---|---|
| 实时房型/房价 | `POST /hotel/detail` | 产品可售还要逐晚核对库存；日期、人数、房间数和退改条件共同决定结果；文档标注 QPS 5 |
| 提交前验证 | `POST /hotel/data/validate` | 要核对业务验证结果，产品失效、房量不足、价格不符不能继续提交 |
| 创建订单 | `POST /hotel/createOrder` | 用接入方订单号关联；超时结果未知时先查单，不能生成新编号盲目重试 |
| 支付及查询 | `POST /hotel/pay`、`POST /hotel/orderDetail` | 支付请求被接收不等于已支付，已支付不等于酒店已确认 |
| 取消 | `POST /hotel/cancelOrder` | 取消可能有罚金；取消、退款处理中与退款完成要分别回读 |

依据：[实时详情](https://open.lvcang.cn/doc/api/hotel/apiList/detail)、[数据验证](https://open.lvcang.cn/doc/api/hotel/apiList/validate)、[创单](https://open.lvcang.cn/doc/api/hotel/apiList/createOrder)、[支付](https://open.lvcang.cn/doc/api/hotel/apiList/pay)、[订单详情](https://open.lvcang.cn/doc/api/hotel/apiList/orderDetail)、[取消](https://open.lvcang.cn/doc/api/hotel/apiList/cancelOrder)。

旅仓文档还涉及凌晨到店的入住日归属、非整夜行程、延迟确认，以及[接入方订单通知](https://open.lvcang.cn/doc/api/hotel/apiList/orderNotify)。是否必须部署外网回调、能否仅轮询查单、创单会否联动支付、沙箱隔离和结算方式，开户联调时需书面确认，不能由客户端猜测。

### 铁路与机票

- **12306 官方接口核实**：本轮没有找到个人开发者可申请的官方余票/购票 OpenAPI、API Key 入口或公开接入契约。12306 科创中心在[2024-12-11 官方公告](https://mobile.12306.cn/mormhweb/zxdt/202412/t20241211_43192.html)中说明未授权第三方平台售票；[2026-01-20 的铁路技术负责人采访](https://news.cnr.cn/native/gd/kx/20260120/t20260120_527500649.shtml)进一步明确未向第三方开放售票接口。因此不能把供应商自己的 API 称为“12306 官方开放接口”。这是公开资料核查结论，不声称已掌握所有内部或特定业务系统。
- 官方网页确实使用内部查询请求，但接口在官方域名上不等于可供个人申请、长期受支持的 OpenAPI。社区 MCP/抓取工具仍是第三方适配。官方[务工团体办票](https://www.12306.cn/mwgweb/info/question_passenger_knowledge.jspx)需要铁路合同户协议及授权证书，属于限定业务，也不能作为通用开发者 API 入口的证据。
- 当前铁路交易方案应保留用户在 12306 官网/客户端办理购票、候补和退改的路径。Bot 可整理候选、提醒起售和统筹日程；辅助查询需标来源与时效，用户确认订单后再同步。第三方若提供代办服务，须另核验其实际机制、账户处理和费用，不能以“官方直连”宣传代替证据。官方购票和订单提示见[12306 购票说明](https://kyfw.12306.cn/otn/gonggao/buyTicket.html)。
- 聚合 817 的余票有字符串状态，不能把“无”“有”和数字都当成可比较的整数。供应商声称实时，本轮未拿真实 Key 独立验证其时延；必须显示查询时间，并在用户选择后重查。产品页标注查得计费和购买流程，不能凭标题的“免费 API”认定不限量免费。[官方字段](https://www.juhe.cn/docs/api/id/817)
- 聚合 818 的 `ticketPrice` **明确叫“参考票价”**。它可辅助查航班，不能当作最终可出票价格，亦不能据此承诺舱位有余量。[官方字段](https://www.juhe.cn/docs/api/id/818)
- 社区 `12306-mcp` 可查余票、中转与经停。作者原理说明显示依赖网页初始化、Cookie 和站点查询路径，是第三方封装，未看到出票接口或官方生产服务契约；适合隔离只读试验，不作为稳定交易底座。[作者仓库](https://github.com/Joooook/12306-mcp)、[原理](https://github.com/Joooook/12306-mcp/blob/main/docs/principle.md)
- Duffel 的测试报价不能证明真实库存；生产订单返回 202 时不能重复创建，应等待结果通知并核对订单。公开定价含按单和超额搜索等费用，不适合无预算持续扫价。[测试环境](https://duffel.com/docs/api/overview/test-mode)、[响应处理](https://duffel.com/docs/api/overview/response-handling)、[价格](https://duffel.com/pricing)

## 对云熙项目的接入建议

### 浏览器视觉操作路线（新增候选，尚未实施）

GitHub 开源底座的比较和接入边界见[浏览器与视觉操控开源方案](浏览器与视觉操控开源方案-20261017.md)，优先验证 agent-browser / Playwright MCP。

用户提出通过电脑操控方式访问 12306 官网查票、准备及创建订单。技术上可按浏览器用户流程开发，不依赖公开购票 API；这不代表获得官方 OpenAPI 授权，也不保证网站始终接受自动化访问。

- 控制一个明确的浏览器会话，优先用页面元素/辅助功能定位，截图补充识别；每步重新读取页面状态，不沿用旧坐标盲点。截图只取任务标签页，敏感页面按需遮蔽，避免把整个桌面发给模型。
- 当前 Bot 没有浏览器控制工具。D152 已完成用户显式附图与 DeepSeek 图像理解的真实验证，但工具输出仍为文本，尚未连接浏览器截图的自动回传。当前会话中的电脑操控工具不会自动成为 Bot 能力；元素文本可复用现有生成链路，不要求新增常驻大模型。ADR 已将浏览器自动化列为独立子进程，具体执行器与图片来源接线仍需单独设计。
- 查询及选择：明确日期、站点、车次、席别和人数后，实际读取余票、候补状态及展示价格，标注查询时间；再次选择时重新读取，不能把旧截图作为当前库存。
- 填表及提交：用户本人完成登录和必要验证。填写授权范围内的信息，提交前回读具体乘车人、车次、日期、区间、席别、票种、金额及备选规则，取得针对该订单的批准。创建待支付订单也会产生真实状态影响，不能因“还没付款”而跳过批准。
- 不把通用 click 当作只读能力或长期授权：页面文本不能提供授权；关键提交动作须绑定刚核对的订单内容和页面状态，变化后重新确认。验证码、短信、人脸验证、风控页或定位不明时交还用户，不设计绕过机制。
- 提交之后：等待队列及订单结果，区分待处理、待支付、支付中、已确认和失败。超时或重启先查看未完成订单，必要时人工核对；视觉点击没有可靠业务幂等键，无法查清时停止，不能自动再点提交。支付倒计时以当前页面为准。[官方订单页面](https://kyfw.12306.cn/otn/view/train_order.html?type=2)说明未完成订单会影响继续购票。
- 首版支付交由用户完成，之后回读真实订单，再按批准同步 Mac 日程/待办和通知；订单已创建但日历失败时只恢复同步，不重新购票。退改及取消各自需要具体审批。

建议分段验收：先只读查票、再到提交前的表单核对、最后在单独授权的真实场景验证待支付订单。不能用合成页面测试替代真实站点可用性，也不将创建订单等同于出票。当前未打开登录会话、未输入乘车人、未创建订单。

### 最小可用路径

1. **真实查询**：酒店、航班和铁路返回结构化候选，携带供应商、产品 ID、查询条件、时间、币种、费用口径与退改规则。参考价、未知、缓存和实时结果要明确区分；空结果和接口失败分开报告。
2. **用户选择后重验**：重新检查房态/舱位和价格。没有失效时间就不编造报价有效期；供应商未保证锁价/锁库存时不向用户承诺。
3. **预排并展示影响**：复用 `mac_trip_plan` 和路线工具，把机场/车站、到达准备、酒店入住退房与原有会议一起统筹。只查询或比较时不修改 Mac 日程。
4. **人工批准交易**：具体酒店/班次、人员、日期、含税总额、币种及取消损失固定后再批准。首版可用可信供应商收银台交接，由用户在网页完成支付。价格或条款变化须重新确认，不能沿用旧批准。
5. **回读订单再同步**：未支付、支付中、待确认分别呈现；订单确认后再经批准写日历与待办，并发送“云熙 · 出行｜预订确认”等通知。浏览器打开成功、支付链接生成、邮件自述均不能单独证明预订完成。

### 现有代码可复用与缺口

- `tooling::default_registry` 已共用于 chat/do/resume/daemon，适合放明确的旅行查询工具，复用现有 HTTPS 客户端、超时、审批和审计。
- 当前 `mcp::ServerSpec` 只配置本地 command/args 的 stdio 子进程；RollingGo 和聚合公布的远程 HTTP/SSE 配置**不能直接粘进当前 Bot 的 mcp.json**。MCP 扩展当前主要装配到 chat，不能据此声称任务和守护也已接通。
- 聚合已有 REST 查询，可先采用普通 HTTPS 适配；RollingGo 国内酒店可先核实官方 CLI 的安装版本、OAuth 登录和 JSON 回执，再决定是否封装到统一工具入口，或接远程 MCP。CLI 是可能减少传输改造的路线，尚未安装或执行；不把它作为绕过审批的自由命令入口。
- 凭证留在本机专用位置，模型只看必要业务结果。身份证、护照和支付资料不进通用工具日志；供应商返回的支付链接也可能带访问令牌，须按敏感值处理。不能照抄示例中关闭 TLS 校验的参数。
- 前一轮发现的直接创建/修改日历缺少统一冲突检查，仍是正式订单回写前应补齐的事项。其他设备未同步的安排与跨系统事务缺失也不能由票务接口解决。

上面是待实现方案，不表示新增工具已经注册。若实现要改变已采纳架构、引入运行时依赖或改变台账格式，仍先按 AGENTS.md 明确设计和审批。

## 开通后优先验收

| 场景 | 通过标准 |
|---|---|
| 有库存 / 无库存 / 查询故障 | 三类结果分别表达；无结果不编价格，故障不伪装售罄 |
| 多人、多间、多晚、儿童 | 正确传递条件，明确总价及费用口径；不能只报首晚或单人价 |
| 报价过期、涨价、售罄 | 旧批准失效；停止原交易并解释变化 |
| 超时、重复点击、重启 | 沿用固定操作编号查明结果，不重复订票/订房 |
| 取消及退款 | 先展示损失再批准；查到终态后才能声称取消或退款完成 |
| 日程变化与跨午夜 | 重新预排并提示冲突；区分目的地时区、交通到达日和酒店营业日 |
| 下单成功、日历写入失败 | 明确订单已存在、同步待处理；只重试同步，不再购买 |

## 继续推进所需资料

国内酒店先核实 RollingGo 官方 CLI 登录和交易权限，也可申请普通 Key 做只读验证；铁路申请聚合 817 测试权限；国内机票继续取得能明确覆盖出票、订单查询及退改的官方契约。同程商旅已有覆盖三类资源的官方公告，但本项目仍未拿到访问资格，不能据其消费产品支持退改就认定 MCP/API 已开放这些权限。

申请由用户提供平台所需信息，Key 保存本机而非聊天。先核对账号实际工具/字段、国内可用地区、费用和限流，再用合成乘客、指定测试酒店及官方沙箱验收；生产下单另作逐笔批准。若最终只能得到查询和跳转权限，应明确交由用户在国内平台完成交易，不把这部分算作 Bot 已具备直接出票。

RollingGo 申请入口以其[官方仓库](https://github.com/RollingGo-AI/rollinggo-hotel-mcp)链接的 Partner Center 为准；聚合使用[817 官方产品页](https://www.juhe.cn/docs/api/id/817)。本轮没有完成开户、真实余票/房态比对、支付或退订验收。
