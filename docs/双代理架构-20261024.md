# 双代理架构（2026-10-24）

## 目标

把“陪伴”和“工作”拆成两个独立代理，而不是让一个聊天 Handler 同时承担两种职责：

- **陪伴代理**：本机 MLX 生成，聊天提示词，无工具，私密上下文不离开本机。
- **工作代理**：云端 DeepSeek 生成，职业任务提示词，带工具与审批；有自己的工作人格、工作画像、工作记忆与工作向量库。
- **任务分类器**：输入先经本地 Laya 判断聊天/任务，再决定走哪个代理。
- **模型适配器**：把“角色 → 模型 → 端点 → 能力”收在一处，不在 Handler 里散落模型名。

## 数据流

```text
用户输入
  ↓
TaskClassifier（Laya，本地；显式 /task /work /chat 优先）
  ├─ chat → 陪伴代理（本机 MLX，CHAT 协议，无工具，个人画像/记忆可用）
  └─ task → 工作代理（DeepSeek，WORK 协议，工具+审批，data/work 独立上下文）
```

工作代理启动时只读 `data/work/`：工作人格、工作画像、工作台账、工作向量库。它**不读**陪伴的 `data/persona.md`、`data/profile.md`、`data/ledger.jsonl`、`data/vectors/`；从聊天切到任务时，只发送任务正文，不发送此前的私密聊天历史。工作会话独立为 `<session>-work`，不会反向污染陪伴上下文。

## 关键文件

- `crates/yunxi-bot-cli/src/model_adapter.rs`：陪伴/工作模型描述；`YUNXI_COMPANION_MODEL=qwen|gemma` 切换本机模型。
- `crates/yunxi-bot-cli/src/task_classifier.rs`：Laya 分类、显式指令、决策台账、`/task` 前缀剥离。
- `crates/yunxi-bot-cli/src/chat_handler.rs`：
  - `new_with_context(home, context_home, ...)`：`home` 放密钥/工具配置，`context_home` 放人格/画像/台账/向量库；
  - `with_chat_protocol`：工作/本机两套对话协议；
  - `route_for_spec`：由分类器强制指定模型，不再二次分类；
  - 本机聊天跳过二次审阅，避免多一次小模型调用。
  - 工作知识检索只在 `context_home != home` 时启用，读取 `data/work/knowledge`。
- `crates/yunxi-bot-core/src/prompts/local_chat.md`：本机陪伴协议（无工具、直接回答）。
- `crates/yunxi-bot-core/src/prompts/work.md` + `work_persona.md`：职业任务协议与身份。
- `crates/yunxi-bot-cli/src/chat_server.rs`：双 Handler 装配、路由事件、独立工作会话、本机未启动的明确报错。
- `sidecar/mlx_backend.py`：本机 32k 上下文；`thinking=false` 且无工具时直接流正文；只有开启思考时才按思考协议解析。

## 运行

macOS App 启动 `chat-server` 时会带 `--auto-local`：如果 17872 没有监听，自动拉起
`.venv-mlx` + 本机模型并等待健康，窗口副标题显示“本机 · 模型名”。不需要先手动开终端。

```bash
# 一键：App 自动拉起本机陪伴模型
open target/macos/云熙聊天.app

# 或手动控制（终端/调试）
./启动本地模型.command
YUNXI_BOT_HOME="$PWD/data" ./target/release/yunxi-bot chat-server

# 可选：本机换 Gemma 4 26B
YUNXI_COMPANION_MODEL=gemma open target/macos/云熙聊天.app
```

`--auto-local` 只在 App 路径启用；CLI 不传这个参数时仍由使用者决定是否加载模型。

本机模型未启动时，聊天直接报“本机模型未启动，这一轮没有上云”，**不会静默回落云端**。

## 当前验证

- 本地 Qwen3.5-9B：真实输入“你好”→ `route mode=chat / agent=companion / model=Qwen3.5-9B-4bit`，流式正文 + `reply` 成功；首轮约 52 秒（38k 字符人格/协议前缀的 prefill 成本）。App 自动拉起模型到 ready 约 2 秒，窗口副标题显示“本机 · Qwen3.5-9B-4bit”。
- 云端工作：`/task 用一句话说明 HTTP 是什么。`→ `mode=task / agent=work / model=deepseek-flash`，约 3 秒返回。
- 单测：分类器 3 项、适配器 2 项、双代理提示词/路由 2 项、核心提示词 2 项；Rust 全量测试与 clippy 通过；MLX 协议测试 11 项通过。

## 工作上下文（data/work）

工作侧不是“没有记忆”，而是“有一套只服务工作、不服务陪伴的上下文”：

```text
data/work/persona.md        工作人格（可用 work persona --init 创建后修改）
data/work/profile.md        工作画像/业务背景（work profile --init）
data/work/ledger.jsonl      工作会话、模型调用、决策、工具审计
data/work/vectors/          工作向量缓存（memory/knowledge）
data/work/knowledge/        工作知识文档副本（work knowledge add）
```

常用命令：

```bash
YUNXI_BOT_HOME="$PWD/data" ./启动.command work path
YUNXI_BOT_HOME="$PWD/data" ./启动.command work persona --init
YUNXI_BOT_HOME="$PWD/data" ./启动.command work profile --init
YUNXI_BOT_HOME="$PWD/data" ./启动.command work knowledge add 资料.md
YUNXI_BOT_HOME="$PWD/data" ./启动.command work knowledge search "客户A的交付格式"
```

工作 `chat_turn` 会检索 `data/work/knowledge` 并把命中片段作为“工作相关知识”注入，云端只收到任务正文、工作画像/记忆和工作知识；陪伴上下文不参与。工作模型调用/工具调用写 `data/work/ledger.jsonl`，不混入陪伴台账。

## 已知问题 / 下一步

1. 本机首轮 52 秒主要花在 38k 字符的前缀 prefill。下一步：本机专用短人格/短协议、prompt cache、或换 mlx-serve/MTPLX 做同机基准。
2. 工作代理尚未做正文级 PII 脱敏；当前边界是“工作上下文独立 + 只发任务正文与工作知识”，细粒度脱敏后续补。
3. 工作会话独立落盘但不自动恢复到 UI；当前 `--resume` 只恢复陪伴主会话。
4. 模型适配器目前覆盖本机 Qwen/Gemma + DeepSeek；任意 OpenAI 兼容市场模型的动态端点/密钥还在下一阶段。
5. 窗口副标题已显示“本机/云端 · 模型名”；工作人格/画像目前用 `work` 命令或设置窗口打开目录配置。
