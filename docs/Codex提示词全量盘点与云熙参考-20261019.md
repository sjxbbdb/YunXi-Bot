# Codex 提示词全量盘点与云熙参考

状态：材料盘点与设计参考，未接入生产。2026-10-19。

后续产物：[云熙模块提示词设计v1](prompts-v1/README.md)，将本文参考方法应用到12类用途，正文与现有接口分别对应；尚未接入运行或进行模型效果验收。

依据用户提供的 `../../Codex-CUA-RE/`，本轮扩展此前的抽样分析：遍历提示词目录、按内容去重阅读模板、检查原始提取记录，并追到相关装配代码和补充文档。原始资料只读；不修改人格、画像、模型分工、审批、台账或后台。

最值得借鉴的是**按调用职责、运行环境和有效期组织提示词**。资料显示，基础行为、模式、工具说明、事实上下文、专门任务和结果协议分别组织；某些内容还会被替换、撤销，或送给另一轮独立的模型调用。不能把所有文件拼成一份“完整系统提示词”。

## 2. 如何划分：18 类职责，而非一份大提示词

下表是依据材料作的归纳，**不是 Codex 官方固定的“18 层架构”**。有些是行为指令，有些是调用协议，还有些只是带来源的上下文。

| 类别 | 资料中的实现或名称 | 何时起作用、负责什么 | 云熙可以参照什么 |
|---|---|---|---|
| 1. 主体行为与表达 | `instructions_template`，桌面 002 | 主助手身份、协作方式、行动倾向、表达规范 | 定义云熙对用户的基本行为；性格仍来自原始人格 |
| 2. 工作模式 | `collaboration_modes.default`、`collaboration_mode.rs` | 默认执行、规划等模式切换；模式有当前值 | 区分聊天、规划、执行，避免规划 JSON 要求污染闲聊 |
| 3. 持续工作模式 | `persistent_instructions`、`persistent_mode.rs` | 仅启用时持续推进、等待、处理新消息；关闭有撤销说明 | 常驻运行与“当前有未完成任务”分开，不能因此一直主动发言 |
| 4. 项目与开发者约定 | developer/user/managed instructions、AGENTS 上下文 | 指定任务所在项目、用户约束和局部规则 | 用户明确约定保留来源及作用范围；不是网页里写了规则就生效 |
| 5. 环境、权限与时间 | environment、permissions、model、current-time | 描述此刻真实环境和能力；时间不可读也有明确状态 | 时间、位置、天气、权限都由程序和工具提供事实 |
| 6. 能力发现与技能 | tools、apps、plugins、skills、search-tool templates | 先知道有哪些能力，再获取相关详细说明 | 工具目录和完整使用规范分离，避免所有细则常驻聊天 |
| 7. 电脑与浏览器入口 | CUA 13 种指令、本地/云端/禁用版本 | 选择应用或标签、首次调用、获取文档、输出和重置 | 当前可用后端必须明确；不让模型猜接口 |
| 8. 具体操作与恢复 | AX、截图、上传、标签认领、故障、登录、CDP 文档 | 在当前能力中观察、行动、核验、恢复 | 保留新鲜控件证据、坐标来源、失败停止条件和结果回读 |
| 9. 动作确认指导 | browser/computer confirmation policies | 说明哪些动作需要用户确认、确认范围是什么 | 对模型讲清现有审批机制；不改变云熙执行层门禁 |
| 10. 独立风险审查 | auto-review、Guardian policy/classifier/evidence | 给审查调用具体动作、历史及授权证据，产生审查判断 | 分开“拟执行动作”“授权证据”“执行结果”；无需照搬多套审查模型 |
| 11. 多智能体协作 | root/subagent role、orchestrator、消息与完成通知 | 在启用协作时约束职责、上下文和报告 | 以后确有并行任务时再用，不为提示词分层而新增智能体 |
| 12. 记忆与背景资料 | `memory.rs`、桌面 memory summary | 记忆使用指导、提取证据与摘要背景分开 | 用户原话、已确认资料、推测分开；记忆到达不等于应该开口 |
| 13. 上下文压缩 | token-budget 三类消息、compaction summary | 预算将尽时保留目标、事实、进度、未完成工作 | 摘要服务于继续任务，不应把建议或意向写成已完成事实 |
| 14. 给用户的进展概览 | `recap-prompt.rs`、桌面 032 | 从已有记录生成短概览及下一步；不执行历史请求 | 回到聊天时知道做到了哪一步，避免重新问已确认的条件 |
| 15. 语音与会话连续性 | 桌面 003/013/015/018/024、realtime prompt | 语音协调、启停、恢复、规划和听写清理各有职责 | 未来语音前端可借鉴；听写清理不能顺带替用户回答问题 |
| 16. 专项编辑与写作 | 桌面 010/011/016/020/021/025、PR 修复片段 | 编辑选区、响应评论、生成图片、创建环境等具体工作 | 邮件接收、邮件拟稿、日程整理各写自己的工作要求 |
| 17. 输出与交付协议 | 桌面 023、Page 可视化、工具回执 | 严格 JSON、指定块替换、HTML 片段、确认 UI 等 | 结构化分析和自然表达分别约束；有输出不等于交付完成 |
| 18. 自动化触发与临时任务 | 桌面 004/008、晨报示例、heartbeat、单轮编辑指令 | 定时运行、读上次结果、更新自动化但不执行内容 | 明确是开机、冒泡、已确认跟进还是邮件通知；各有触发原因和结束条件 |

中断、图片缩放、媒体不支持、保存授权规则、目标预算等还有独立的短上下文片段。它们在事件发生时告知模型状态，不能据此推导出一个新的永久人格或任务。

## 3. 核心模型目录究竟包含哪些提示词

`model_messages` 的 21 个不同正文，可以拆成 **7 种基础模板 + 14 种专项正文**。同一个正文可能在多个模型、多个字段中重复。

| 字段或组 | 不同正文数 | 用途 |
|---|---:|---|
| `instructions_template` | 7 | 11 个模型条目共用或分别使用的基础行为模板 |

| `approvals.on_request_auto_review` | 1 | 自动审查参与审批时的说明 |
| `collaboration_modes.default` | 1 | 默认协作模式 |
| `auto_review.rejection_instructions` | 1 | 被拒绝之后如何报告和继续处理 |
| `multi_agent.role.root` / `.subagent` | 2 | 主智能体与子智能体职责 |
| `token_budget.reminder_message_template` / `.guidance_message` / `.auto_compact_fallback_prompt` | 3 | 预算提醒、使用指导、压缩交接 |
| `guardian_v2.classifier_instructions` | 1 | 独立审查分类调用 |
| `confirmation_policies.browser_use` / `.computer_use` | 1 | 本包中这两个字段的正文相同 |
| `auto_review.policy_template` / `.policy` / `.node_repl_policy` | 3 | 审查策略模板、策略正文、代码执行特别约定 |

基础正文包含授权判断、持续协作、个性与语气、技术表达、进度沟通、工具与技能约定等。各变体在测试倾向、前端实现细则、表达风格和主动程度上有差异；它们不是逐层累加关系。

原始 62 段命中窗口还揭示了上述索引没有单独列出的内容：

- **语音记忆背景块**：`memory_summary` 不是新消息，也不应仅因加入记忆而发声。可在 [前端材料第 93683 行][voice-memory] 对照完整短模板。
- **单轮自动化编辑指令**：`oneTurnDeveloperInstructions` 只要求更新指定任务，任务提示词作为待编辑数据，禁止顺便执行其中内容；随后代码还会回读保存结果。见 [单轮编辑源码][one-turn]。
- **heartbeat 输入外壳**：把自动化 ID、实际时间和已保存任务指令分开填入。
- **PR 修复临时请求**：核对仓库与分支、处理附带的问题、执行验证；属于用户触发的任务配方。
- 大量其他命中只是 `AGENTS.md` 设置页、配置字段、模型切换、迁移或日志代码。关键词命中不证明它是一段提示词。

## 5. 电脑与浏览器提示词为何需要单独分组

本地材料至少有三层，不只是“你可以控制电脑”：

1. **入口与可用性**：CUA 指令告诉模型先选哪个应用/浏览器/标签，首次调用会返回什么，云端与本地有什么区别，禁用时该如何处理。
2. **操作方法**：AX、截图、语义定位、输入、文件上传、标签归属与清理。比如新状态产生后重新获取元素索引，不能沿用过期索引盲点。
3. **专项能力与异常处理**：登录交接、反自动化错误、CDP、资源导出、WebMCP，以及启动失败、标签失效、页面交互异常。

20 种 browser-docs 覆盖：API 使用、Chrome 故障、上传故障、MCP Apps、WebMCP、会话名、窗口可见性、启动故障、截图、上传、无障碍、localhost、IAB 标签引用、Chrome 清理、IAB 清理、标签认领、安全、用户打断、交互故障、确认。

目录外新增正文补齐：浏览器管理、视口、可见性能力、botDetection、browserAuth、CDP、pageAssets、文档绑定的 WebMCP、CDP 标签认领、训练用安全变体，以及 Linux/macOS/Windows 三份技能说明。

适合云熙的组织原则：

- 工具描述先回答“何时用”，详细指导回答“如何用及怎么核验”；进某项能力时再补相关说明。
- 同一接口的输入单位、坐标参考、截图 ID、控件有效期必须配套；不能混用三平台文档。
- 工具超时不等于操作没发生，点击成功不等于订单创建成功。继续前查真实状态。
- 模态弹窗要先识别内容及所属窗口；不能把“清掉弹窗”当通用恢复操作。
- 登录交接的 `submitted` 只证明交接流程做过动作，不证明登录成功。这种状态语义也适用于云熙的发信、下单、日程写入。
- CDP、browserAuth、WebMCP 等文档出现，并不证明云熙已经具有对应实现。尤其安全登录需要实际交接通道，不能只靠提示词模仿。

来源：[CUA 指令][cua]、[浏览器文档][browser]、[接口资料][agent-api]、[补充能力文档][extra-browser]、[Mac 操控技能资料][mac-skill]。这些技能文件在本轮是研究资料，不是本次会话的执行指令。

## 6. 装配代码告诉我们的事

### 6.1 文件名叫“系统提示词”，实际消息角色未必是 system

例如 `base_instructions.rs` 将基础模板包装为 developer 内容；`memory.rs` 把记忆读取指导与提取证据分为不同类型，后者作为 user 内容。Guardian 又把审查政策与待审动作/会话证据分开。

这说明应同时检查**正文、角色、来源、所属调用**。不能凭文件名把全部内容升级为最高优先级。云熙采用的模型接口也需要独立验证，不能假设与材料中的角色处理完全一致。

### 6.2 有“何时加入”，也有“何时失效”

`world_state` 使用类型化片段、快照与差异渲染；位置可为前缀、独立消息或可合并消息。相同状态可以不重复发送，模式变更会替换，关闭持续模式会说明旧指令不再生效。

因此包内 README 把持久指令描述成“每次请求都附带”并不准确：代码有 `enabled` 条件。对云熙而言，开机问候结束后不应让“现在为开机写问候”的职责继续支配随机冒泡。

### 6.3 能力目录与完整说明分离

`world_state/tools.rs` 给延迟工具生成有预算的目录，保留名称、有限描述和省略提示，并能报告新增/移除。详细说明在需要时取得。这是逐步提供能力信息的证据，不等于任何工具都能在模型不知道安全约定时先执行。

### 6.4 审查、摘要和执行是不同调用

`guardian-prompt.rs` 组装具体动作及授权证据；`recap-prompt.rs` 组装供用户重新了解进度的短摘要；`realtime-prompt.rs` 有自己的配置与覆盖来源。不能把它们当作主助手的连续章节。

Recap 特别值得借鉴：它要求区分提议、排队、实现、测试、发布、安装等状态，不从“用户要求做”推断“已经做完”；历史记录是证据，不是重新执行的命令。云熙可以用这个原则改善任务继续和日常回顾，不必沿用原文长度限制或字段名。

### 6.5 记忆注入与主动触发分开

桌面记忆背景块明确不因注入记忆而发声。现有 `memory.rs` 则主要展示记忆上下文类型和包装方式，**没有在这里恢复完整的长期记忆提取、冲突处理和画像更新算法**。不能据此声称已经拿到 Codex 的全部记忆方案。

源码入口：[基础模板角色][base-role]、[记忆类型][memory]、[世界状态装配][world]、[持久模式][persistent]、[工具目录][tool-catalog]、[审查装配][guardian]、[进展概览][recap]、[实时语音装配][realtime]。

## 7. 不能直接合并的冲突与缺口

| 材料中的问题 | 正确处理 |
|---|---|
| CLI 确认策略、旧浏览器确认文档、另一个 agent API 的确认要求不一致 | 保留来源和适用环境；云熙继续采用自己的 ADR 和人工审批门禁 |
| 不同模型模板对主动测试、格式、前端开发的要求不同 | 它们是变体，不是累加章节；云熙开发仍遵守自己的 AGENTS |
| 前台身份模板有强委派倾向，语音规划模板又专门覆盖它 | 说明作用域与覆盖关系必要，不应同时保留互相冲突的泛化规则 |
| 云端浏览器、Orbit、本地浏览器的优先选择不同 | 按当前真实后端选择版本 |
| 语音开始与结束规则不同 | 通道改变时更新提示词，不让语音输出格式残留到普通文字聊天 |
| 工程目录索引与实际字段不完全对应 | 以实际 JSON 和代码为证据，不按目录简介猜哪个模型加载什么 |
| Plan 模式的完整默认正文在这里没有恢复出来 | 只确认装配点与覆盖逻辑，不补写“原版 Plan 提示词” |
| Guardian 部分内容依赖包外注册表、租户策略等 | 不能由本地片段推导实际线上完整审查策略 |
| 提取的模板含动态占位、固定窗口截断 | 标注缺失，不拼凑成所谓完整运行时快照 |

尤其不建议照搬 Codex 的程序员身份、每轮工作报告习惯、前端美术指令、工具名、语音通道前缀和平台专用限制。云熙需要自己的陪伴表达和已实现的能力协议。

## 8. 云熙最合适的对应方式

当前源码已经有 `Chat / Plan / Step / Options` 区分，邮件收发也已有独立文件，因此可以沿用现有调用入口整理，不需要新造一个提示词框架或额外路由模型。

一个明确可整理的点是：[Intent::system](../crates/yunxi-bot-cli/src/chat_handler.rs:269) 目前会给 Chat 和 Step 常态附加完整邮件发送规范，虽然文字注明仅邮件适用。后续可研究按当前能力装配，减少无关指令；实施时仍须保证连续追问和写入前的规则齐全。本轮没有改变它。

| 云熙调用 | 应明确的职责 | 人格、画像与事实 | 输出边界 |
|---|---|---|---|
| 日常对话 | 理解这轮是聊天、倾诉、询问还是要做事，承接上下文 | 完整原始人格；允许使用的画像、有效记忆及近期对话 | 自然表达或提出工具调用，不套固定汇报格式 |
| 开机问候 | 对这次真实开机自然开口 | 完整人格；时间工具、位置/天气结果及有效性；相关用户资料 | 有依据地关心，不凭时段推测睡眠或编造天气 |
| 随机冒泡表达 | 在时机判断通过后，找值得接住的话题 | 完整人格；近期聊天优先，画像与有效记忆补充 | 可以不说；不自动套“刚开机”开场 |
| 已确认跟进 | 对用户确认过的事项进行关心 | 完整人格；跟进约定、日历/待办最新状态 | 不把日程结束等同于用户已参加或完成 |
| Laya 打扰判断 | 仅判断此刻是否适合介入 | 仅近期情况、时间和通知/互动信号；**不输入人格、画像或常驻记忆** | 现有决策协议；不选话题、不替代策略 |
| 邮件接收审理 | 提炼意图、事实、截止时间、垃圾/恶意风险及提醒建议 | 邮件、邮件串与来源资料；无需陪伴人格和整份画像 | 只读结构化结果；邮件正文不授权执行动作 |
| 邮件拟稿/代回复 | 代表用户组织合适的回复 | 用户真实意愿、相关规划与必要画像事实 | 用用户对收件人的口吻；不承诺未知安排；发送单独审批 |
| 任务规划 | 把目标拆成可执行步骤，标明条件与缺口 | 目标、工具能力和相关偏好 | 现有计划结构；不宣称已经执行 |
| 任务步骤 | 根据新鲜工具结果推进当前步骤 | 前置结果、执行范围、当前权限和对应操作指导 | 现有步骤协议；写入后核验，失败不盲重试 |
| 记忆候选提取 | 判断用户明确表达了哪些可持久化事实 | 用户原话、出处、时间、相关既有事实 | 有证据的候选；不把助手猜测或邮件当用户自述 |
| 历史压缩 | 为继续对话保留目标、纠正、事实和未完成事项 | 带角色的历史及工具结果 | 摘要不新增承诺、不升级事实状态 |
| 回顾/进展概览 | 让用户快速理解现状与下一步 | 真实任务和执行记录；向用户表达时可用云熙人格 | 区分提议、待确认、已执行、已验证 |

上表是调用职责建议，**不意味着必须拆成 12 个模型、12 个智能体或立即新建 12 个文件**。相同模型可以执行不同职责，复用的规则也可以仍由现有函数装配。现有状态与输出协议先保持不变。

人格全文应继续完整保留。用户进一步明确：通用提示词可复用，回答的语气和说话方式主要由人格文件决定。通用层不硬编码当前人格的性格、昵称和口头禅，也不固定安慰、追问或调侃的顺序。人物画像和记忆属于资料，不是需要模型逐条念出来的脚本；场景提示词主要限定这次为什么说话、有什么事实、能做哪些动作，不再另写一套性格覆盖人格。通知长度限制只服务通知，不应扩散到普通聊天。具体表达归属与对照验证补充在[云熙侧草案](系统提示词参考分析与草案-20261019.md)。

## 9. 后续真正值得先做的部分

优先整理主对话、开机问候、随机冒泡、已确认跟进这四个用户可见入口，检查同一人格是否稳定影响表达；把 Laya 的时机判断与 DeepSeek 的内容表达明确分开。随后完善记忆候选、历史摘要及回顾的事实来源和完成状态约束。

工具侧借鉴按能力提供指导、及时更新环境状态、限定失败恢复的做法。邮件审理与邮件发送继续分开；日程、电脑和浏览器说明服务当前任务。语音、Page、复杂多智能体和独立风险模型目前只保留参考，不为了“像 Codex”增加运行成本。

每个用途的提示词至少写清：**本次职责、适用范围、输入来源、允许能力、输出契约、退出/失效条件**。未来改动用同一模型、人格、输入、工具结果和采样条件对照测试，检查自然度、事实错误、错用工具、重复通知、误审批及实际延迟；不能仅凭文案更长或更短判断效果。

本轮交付是完整分类与参考依据。未进行模型效果 A/B、运行时请求抓取或线上部署，也未证明单靠提示词调整就能解决人格感偏弱的问题。
