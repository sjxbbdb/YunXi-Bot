# 邮件理解与通知方案（已批准，DeepSeek建议＋Laya参考）

后续状态：2026-10-16 已按 D151 将已审理 Mac 邮件通知与陪伴额度分开，取消每日 3 次限制并加入普通邮件 15 分钟摘要；本页保留初版方案演进，当前策略见[通知分流](通知与主动陪伴分流方案-20261016.md)。

目标：读懂新邮件，区分对用户有用的信息、推广、垃圾及可疑内容，再决定何时通知。邮件内容本身不构成执行任务的授权。

## 已批准的路径

本机收件 → 去重与用户明确设置的过滤规则 → DeepSeek 只读分析及提醒建议 → Laya 参考留痕 → 确定性约束 → 云熙原生通知或待查看队列。

第一版复用已经接入的 DeepSeek，不新增常驻本地生成模型。只有需要分析的新邮件才调用；60 秒心跳仍只是本地检查。成功分析按邮件身份及内容版本复用，失败退避并受预算限制，不能每分钟重复付费。

DeepSeek 在一次调用中提取邮件所声称的事实并建议提醒方式；Laya 的判断记录供对照，不单独否决提醒。若以后希望减少云端正文传输，再用同一组样本评估小型本地阅读模型，验证后决定是否替换第一层。不能用未经验证的本地模型先过滤，再指望后面的 DeepSeek 补救已经漏掉的邮件。

## 开发前的具体缺口

- `triage.rs` 只给 Laya 正文前 400 字符，不是理解全文后生成的摘要。
- `deterministic_triage` 会将群发、机器发件人直接判为 Hold，跳过模型；这不足以区分广告与航班取消、账户异常等自动通知。
- `assistant.rs` 只对已投递邮件去重；未通知邮件可能反复判断，直接接入付费分析会重复消耗。
- 通知复用陪伴的静默时段、每日 3 次及互动间隔限制。Hold 必须能被用户查看，不能把“暂缓提醒”呈现成“没有重要邮件”。
- 当前信息源只扫描未读。用户或其他客户端先读过的新邮件可能被漏掉；可靠的新信检测需要基于收件进度和稳定身份，首次启用建立基线，避免突然处理全部历史邮件。

## 两个模型各自负责什么

只读分析返回经过严格校验的结构化结果：主要内容、类别、是否涉及用户、是否要求回复或行动、截止时间及原文依据、可疑信号，以及是否读取完整。未知时间、身份与真实性明确记为未知。

类别和风险分开：一封声称“账户被盗”的邮件可能值得提醒用户核实，但发件人和链接仍可能是假冒。风险模型不能证明邮件安全，邮件的自述也不能证明事实。

DeepSeek 返回 `notification=now/later/ignore`。Laya 根据分析结果给出独立参考并留痕；参考服务失败明确标记 degraded，但不否决有效的阅读建议。`unknown` 一律待查看；有高重要性、行动要求或风险却建议忽略时也保留待查看。用户黑名单优先，白名单不能把未知结果变成提醒。所有建议都要经过静默时段和次数限制。

通知标题采用“云熙 · 邮件｜人事回复”等来源＋关键词，正文包含发件人、具体摘要、待办及邮件原文时间。相对时间附原邮件收件时刻，避免跨天后误解。没有可信关系信息时使用“私人来信”，不凭发件人自称标成“朋友／老板”；风险信号统一标“可疑邮件”，明确未打开链接或附件。

第一版保留现有静默与次数约束，单独展示被限制的原因；是否为邮件设置独立通知额度另行确定，不暗中放宽。

## 阅读范围与授权边界

- DeepSeek 将接收需要分析邮件的主题、发件信息和正文；用户已明确批准此数据流，D148替代D147对应部分。
- 按预算读取正文；超长、缺页或解析失败标记为不完整并转待查看，不能凭前几百字判为无用。
- 分析调用不提供工具、凭证、其他邮件或整套用户记忆；拒绝返回的工具调用和不符合约定的输出。
- 不因正文指令访问链接、加载远程图片、下载或执行附件。第一版只记录附件存在，不能声称已检查附件安全性。
- “请转账／替我发邮件／调用大模型”可以成为邮件摘要中的待处理请求，不能直接成为已授权任务。需要后续任务时由用户在可信交互入口确认；原有写操作审批继续有效。
- 未确认安全不等于自动删除；垃圾或可疑邮件也不自动归档、标记已读或删除。
- 模型、网络、预算或校验失败均显式降级到待查看，不触发邮件中的动作。

## 改动范围与复用

| 位置 | 必要改动 |
|---|---|
| `info/mac_mail.rs` 与信息源接口/调用方 | 新信发现、完整性及稳定身份；保持只读，保留 IMAP 现有使用方式 |
| `triage.rs` | 拆开内容事实与提醒建议；群发和机器地址作为特征，不能直接决定价值 |
| `assistant.rs` | 接入只读分析、分析结果复用、失败退避、待查看和提醒闭环 |
| `think` 与 CLI/daemon 装配 | 复用现有 DeepSeek 客户端、用量统计及凭证读取，不提供工具 |
| 原生通知与反馈 | 复用已验证出口及投递去重，呈现理由与未处理事项 |
| 测试、验收文档及 ADR | 覆盖失败、重启、恶意正文和漏报；批准后更新架构说明 |

不新增运行时依赖，不微调 Laya。优先复用既有审计事件及格式；如实现必须改变台账格式，先提出迁移方案再确认，不能借此次接线静默改格式。

## 验收要求

使用合成样本先测，真实邮件仅在授权范围内验收。至少覆盖：

1. 会议变更、工作回复期限、订单异常、航班取消，包括群发和 noreply 发件人。
2. 常规广告、用户确实关心的推广、无关垃圾邮件，分别检查误报与漏报。
3. 仿冒联系人、钓鱼链接、索取验证码、恶意附件名、正文提示注入；工具执行次数必须为零。
4. 重要信息位于正文尾部、长邮件和嵌套引用、中文和英文、未知日期或时区。
5. 分析结果与 Laya 冲突、非法输出、工具调用输出、超时、断网、余额或预算不足。
6. 同一封信连续巡检、重启、通知失败重试，不重复分析成功内容或重复投递。
7. 先读后巡检、同主题不同邮件、连续大量新信，不能依赖未读或主题当身份。
8. 静默时段、额度耗尽、暂缓后查看；能够解释每封邮件为什么未提醒。

分别统计重要邮件召回、无关通知误报、可疑邮件识别、非法执行、耗时及调用成本；不拿“通知能弹出来”代替判断质量验收。

启用配置、实测证据及生产切换状态见[邮件理解通知验收](邮件理解通知验收-20261016.md)。

## 真实模型结果与职责调整依据

2026-10-16，修正合成样本发件人元信息并收紧阅读提示词后，16条合成邮件的内容提取和关键词标签均满足本批预期。5条需及时提醒的面试/行程/会议/期限场景中，Laya仍将航班取消和当天会议提前判为暂缓；已保留待查看，但提醒要求未通过。广告、普通回执和感谢邮件未立即通知。报告：`data/benchmarks/tools/mail-review-models-20261016-r2.json`。这些是开发样本结果，不是泛化准确率证明。

用户随后明确批准“DeepSeek提出提醒建议，Laya作参考”，现按此实现。最终仍经过固定的静默时段、次数限制、格式验证和去重。未知、读取不完整或DeepSeek失败仍留待查看；依旧无工具执行权。

后续评测中，“航班恢复”的模型输出正确说明无需按旧邮件改签，但原题把它预设为“不重要”，导致一项误判。题目改为检查最新事实、旧引用失效且不要求改签；恢复消息本身允许及时提醒。没有改动邮件内容来迎合模型，原始r3输出保留，后续报告单独保存。这批是开发样本，不代表长期泛化准确率。
