# 通知与主动陪伴分流方案

状态：用户已选择“先只修通知，陪伴稍后做”。以下原方案中的主动陪伴部分未实施、未启用；本轮仅修改已启用DeepSeek审理的Mac邮件通知，部署结果见末节。

## 已核实的问题

- `CompanionPolicy::default()`固定每日3次、最小间隔120分钟；邮件巡检直接复用该策略。
- 生产邮件路径按本机自然日统计同一台账里的有效`NoticeSent`，未区分邮件与其他来源。2026-10-16的三次实际投递已耗尽额度，20:03发现的招聘邮件即使获得DeepSeek的`now`建议，也被转为待查看。
- 当前LaunchAgent没有`--agent`且设置`--judge-every 0`，主动陪伴回路关闭。
- 旧主动陪伴回路生成的话只进入记忆和标准输出，未接Mac通知。其冷却还按“最近一次决策”计算，静默判断和邮件判断也可能持续推迟下一次开口；决策为Speak但生成失败也可能计入次数。
- 邮件`Hold`当前只是留存并每15分钟复查，不等于已经实现普通邮件合并摘要。

## 原始分流建议（陪伴部分暂缓）

| 类型 | 默认行为 | 防止重复打扰 |
|---|---|---|
| 需要及时处理的邮件 | 内容分析有效、策略允许时及时通知，不因此前已通知3次而延后 | 同一邮件去重；同轮多条合并呈现，保留每条来源、摘要和待办 |
| 可稍后看的普通邮件 | 利用现有缓存，每15分钟合并一次新增摘要 | 仅包含未提醒内容；没有新增内容不发送空摘要 |
| 推广、垃圾邮件 | 无需处理时保持静默，保留查询能力 | 无法判断进入待查看；具体风险保留原有核实提醒，不因邮件自称紧急就执行其要求 |
| 主动陪伴 | 结合已有用户记忆、实际事件和最近互动判断是否值得说一句，生成后通过“云熙 · 陪伴”Mac通知送达 | 与事务通知分别计时；不设每日3次总额，默认最短60分钟；无回应则间隔递增到2小时、4小时 |

“及时通知”只放开原来的次数总额，不绕过23:00–08:00安静时段、用户明确静默、黑名单、系统通知权限或macOS专注模式。夜间例外需另行明确；本次不启用。

模型提供建议，确定性策略检查输入完整性、类别、有效证据和允许的通知行为。无法判断时保持待查看；通知不授权发邮件、改日程、执行来信指令。

主动陪伴只根据已经授权且实际存在的上下文判断，不新增屏幕、应用活动或情绪监控。用户未回应只代表未观察到互动，不推断情绪或关系。没有可靠互动记录时不假装知道用户已读。冷却以本类实际投递回执计时，静默判断、失败生成和失败投递不算一次成功开口。生成内容为空或重复时不发通知。Laya仍作陪伴介入判断，DeepSeek负责表达，本轮不训练或替换模型。

本地检查复用守护循环；只在有未处理的新事实、符合用户已记录偏好或存在可跟进事项时产生候选。定时检查不等于每轮调用DeepSeek。取消每日通知总额不取消已有云端调用预算。

## 改动落点与验证

- `companion.rs`：区分事务通知与主动陪伴的频率约束，保留统一静默和失败关闭规则。
- `triage.rs`、`assistant.rs`、`mail_review.rs`：复用有效分析和原待查看缓存，补普通消息合并；重启或投递结果未知时继续用原生tag与回执去重，不清空历史记录。
- `agent.rs`及CLI后台：修正“判断过即互动过”的计时，连接现有Mac通知出口；生成结果与实际投递分开记录。
- 复用现有`NoticeSent`及决策事件，不增加事件类型或改变台账文件格式；以来源区分计时。上线时不补发历史已通知内容，不集中重放历史陪伴文字。既有待查看邮件按新策略重新评估并合并，不删除。
- 先离线复现与验证：已提醒3次后的重要邮件仍能通过；普通邮件成批时合并；重复扫描和重启不重复；静默时段仍生效；模型/原生接口失败留存；邮件通知不重置陪伴冷却；静默判断不重置计时；未回应后的退避与真实新互动后的恢复。
- 再进行隔离的真实模型和原生通知测试，最后切换生产。工程检查按AGENTS.md执行，所有实际发送邮件仍逐封审批。

## 确认结果与本轮实现

用户只批准先修通知，因此仅修订D24、D147/D148中Mac邮件审理通知共用陪伴次数限制的部分。`agent.rs`、主动陪伴的计时与表达、后台`--judge-every 0`均不在本轮实现范围。

- 已审理邮件的通知约束保留静默规则，移除陪伴的每日3次及120分钟间隔；未启用内容分析的旧IMAP/演练路径沿用原策略。
- `importance=normal/low`、类别为工作/私人/交易、建议now/later、无待办/期限/风险的普通信息进入摘要队列；重要、待处理或风险消息继续依有效分析建议处理，未知仍待查看。推广/垃圾的ignore及原有风险规则不变。这里不靠主题“紧急”绕过内容分析。
- 普通队列从首封入队起等15分钟，后来邮件加入同一窗口；两次成功摘要至少间隔15分钟。重要消息不等该窗口。同轮重要消息合并；单封保留原来的关键词标题。每轮最多各投递一个批次，通知正文不超过4000 UTF-8字节，放不下的邮件继续留存，未列出的不记作已通知。
- 私有`mail-review-state.json`兼容读取旧缓存：新增带默认值的投递批次和摘要时间、增加ready/digest内部状态。固定批次保存成员、原文版本、标题、正文、tag及实际回执；调用系统前持久化，取得回执后先保存再逐封记账。审计中断可恢复，不重新发送已记录的回执。失败/未知结果15分钟后沿用相同批次核对；新邮件不混入未知结果的旧批次。
- 投递前重新核对黑名单和原邮件。标题、身份、正文或审理输入版本变化时取消旧批次，重新分流；不能用新原文验证通过后继续发送旧摘要。干跑不清除真实待核对批次。损坏缓存显式报错，不重置。
- 复用现有NoticeSent、InfoTriaged事件和原生通知接口，未改变台账格式、审批词汇、模型、原生应用或云端调用预算。每个摘要成员复用同一实际回执记账，不能把一封摘要误称为多次物理弹窗。
- 正常重启不重放已通知邮件；原来因额度暂缓的邮件按已有复查时间重新评估。原生通知中心回读能确认记录，不证明横幅可见或用户已读；极端情况下系统已投递、进程未保存回执且通知又被移除，仍无法承诺绝对一次投递。
