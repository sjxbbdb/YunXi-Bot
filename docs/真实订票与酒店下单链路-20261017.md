# 真实订票与酒店下单链路

本轮补真实网页的结算核对和订单回读，复用已接入的Cua Driver、DeepSeek、工具循环与人工审批。不是供应商交易API，不开通后台自动下单或自动付款。

## 正常入口

`chat`、`do`、任务恢复和后台共用Mac工具注册表，新增两个只读工具，注册表由52增加到54。后台没有真人审批入口时，仍不能执行电脑动作。录屏验收使用同一ChatHandler及工具；测试中的有限查询授权不安装到后台。

1. `travel_prepare`整理日期、人数、间数和预算。Bot通过正常12306/携程网页查询余票、房态，选择车次、房型及平台保存的本人资料；不能从起价或搜索摘要推断可订。遇登录/验证码交用户，暂停私有窗口录屏。
2. 查看实际结算页，核对具体车次/席别或酒店/房型/餐食、完整年月日、已选旅客/入住人及数量、全部应付金额、税费与退改。无法确认的条款先补查，不能编造。非必需保险、服务包等不得默认为用户购买。
3. `travel_checkout`将上述原文与同一最新网页逐项匹配；酒店省略年份时仅采用[同标签日期证据](酒店结算日期证据衔接方案-20261017.md)，其余信息仍匹配当前网页，核对精确target/tab、120秒期限、共享观察版本、平台结算路径及实际提交ref。只返回核对预览和待审批的`computer_act`参数，明确`approved=false`、`submitted=false`。
4. 将返回动作原样送入既有`computer_act`逐次人工审批。审批预览自动带上核对内容，参数有任何改变则拒绝；另一轮观察会使旧核对失效。确认按钮只代表本次动作，不能批准整趟旅行或付款。
5. 提交前消费观察和本阶段核对，同进程记录已尝试的预订阶段，即使随后Driver失败也不能把超时当作未下单。铁路可能还有二次确认；必须重新观察、匹配同一方案并再次人工审批。不能重复原提交阶段。
6. 提交后重新观察实际订单详情/付款页，用`travel_order_read`核对订单号、对应预订条件、金额及独立状态文本。按钮上出现“支付”或Driver报告点击成功都不算订单回执。缺字段、未知状态、平台变化返回错误，先查实际订单，不再提交。
7. `pending_payment`明确未付款，不能标记已出票或已确认住宿。付款由用户接管。真实确认后的日程仍使用`mac_trip_plan`/`mac_trip_apply`，先检查全部受影响日期和revision，经审批写入并回读；取消日程不等于取消商家订单。

## 验证边界

核对工具匹配的是当前网页摘录，不能自动证明字段是已选项、价格已含全部费用、多个文本属于同一订单或报价不会动态变化；这些仍须在提交审批时核对实际网页。它不替代平台的出票/房态确认。严格节点/原文匹配不支持时会停下，不能改用猜测的状态。

已尝试记录只在当前ComputerTool控制器内存中保留，不是跨重启、跨进程的供应商幂等键。通用电脑工具仍保留逐次人工审批；这两个只读工具不是全站交易拦截器。任务恢复必须先看真实订单记录，禁止仅凭本地没有记录就重下。取消或退款仍走具体条款核对和单独审批，不自动清除提交记录再试。

结算原文、所选姓名、报价、订单号和核对预览采用已有private_io机制，仅在本进程模型上下文使用；工具台账与会话存占位信息，不新加台账字段。最终自然语言回复沿用现有会话规则，因此不应复述证件或凭证。录像仅保存在用户授权的桌面私有目录，不提交Git。

[Cua官方说明](https://github.com/trycua/cua/blob/main/docs/content/docs/how-to-guides/driver/drive-a-web-page.mdx)确认命名隔离配置保留而临时配置随会话移除；固定0.36.0源码同时显示，Driver会话结束会清理其拥有的浏览器进程。保留配置不等于浏览器永远运行，也不保证网站服务器认可旧会话。[Chromium会话Cookie恢复逻辑](https://chromium.googlesource.com/chromium/src/+/eb9f61f5cdd43a14e11bb624aee95333af8cf345/chrome/browser/profiles/profile_impl.cc)可供核查，仍需实际登录后重开验证，不能把目录或Cookie文件存在当作已登录。平台过期、风控、短信验证及用户主动退出仍交用户；不自动读取密码或验证码。
