# 邮件审理工具的独立系统提示词

用户要求工具有明确的审理职责，并强调泛用性，不能针对一封测试邮件加入特殊提示或关键词规则。

原实现已经使用独立的 `system` 消息，并非把正文直接交给聊天 Agent；问题是审理规范不够清晰，复杂样本出现了普通请求被判成危险的误报。本次将规范整理为独立文件：[mail_review.md](../crates/yunxi-bot-core/src/prompts/mail_review.md)，由 `mail_review.rs` 编译时加载。

## 通用职责

1. 阅读全文，区分背景、事实、请求、引用与最新变更。
2. 提取发件意图、需处理的事项、关键条件和原文期限；缺失的信息不猜。
3. 将“有请求”“是否危险”“是否获准执行”分别判断，无执行权限不能成为无意图或危险的理由。
4. 风险必须有具体内容证据；区分普通事项、推广、垃圾、欺骗以及试图操纵审理流程的内容。风险摘要明确指出线索，不能只写笼统结论。
5. 返回已有结构化结果，供后续决策和通知使用；审理阶段不回答发件人、不生成请求的成果、不执行动作。

提示词不含测试邮件正文、发件人、主题匹配、具体任务的特殊待遇或按关键词强制分类。测试样例与生产提示词分开保存；不能把开发样例通过当作泛化保证。

## 请求和返回

每次只发送两条消息：

- `system`：审理职责、通用判断规范、字段协议和本次分析时间。
- `user`：JSON 封装的邮件元数据与正文；始终作为外部不可信资料。

不带聊天 Agent 提示词、人格、会话历史、其他邮件、用户记忆或工具定义。返回字段保持兼容：`label`、`summary`、`category`、`importance`、`notification`、`needs_action`、`action`、`deadline`、`evidence`、`risks`。

垃圾内容可返回 `category=spam`；存在危险信号用 `suspicious` 并填具体 `risks`、证据和说明。具体风险继续按 D148 显示为“可疑邮件”，不把文本模型结论包装成已验证的诈骗或恶意软件鉴定。返回错误结构、编造证据、工具调用或未完成输出，仍转待查看。

本次另要求新风险结论必须有原文证据；无证据的风险输出不采纳。旧缓存仍可读取，不因收紧新回复校验而拒绝启动。

## 缓存与运行边界

输入增加 `review_prompt_version=2` 参与完整缓存比对。旧版已暂缓邮件在下次正常复查时重新审理，新版相同输入继续复用；每日／每轮调用次数预算与十五分钟退避不变。历史基线和已经通知、忽略的终态不会因提示词升级集中重放。版本字段在已有原始输入 JSON 内，不修改审计台账或审批格式。

不改变 DeepSeek 建议、Laya 参考、固定通知策略与人工审批的分工，不增加后台任务执行能力。邮件里的要求依然不会自动变成获准执行的 Agent 任务。

## 验证范围

工程回归先复现两项失败：旧提示词结论永久复用、无证据风险输出被接受；修复后检查重启兼容、正常缓存复用、终态不重放及系统／用户消息角色分离。

模型评测使用 25 条合成邮件，加一封用户授权的原邮件隔离重放。覆盖工作、人事、行程、普通私人请求、推广与垃圾、验证码、长背景中的请求、引用安全资料、混合风险和恶意操纵。全部使用同一份通用提示词；没有执行工具、发送邮件或投递桌面通知，也不改生产队列。


首轮记录保留在私有报告 `data/benchmarks/tools/mail-prompt-v2-20261016-r1.json`。其中两次回复用满 4096 个输出 token，未完成 JSON；一次回复被字段或原文证据校验拒绝。单次预算调整为 8192 token，继续启用思考，运行调用超时从 45 秒调整为 90 秒；不会因格式不合格而放行。每轮及每日调用次数上限不变，最坏单次 token 成本和等待时间会增加。

首轮也暴露两项题目歧义：验证码可能要求“若正在登录则及时使用”，不能强制其没有行动事项；“刷单日赚万元”有具体欺骗线索，不能预设为安全垃圾。保留原失败记录，将验证码改为检查无风险误报；保留高收益广告作为风险样本，另补一个无欺骗线索的重复群发广告。没有把这些内容加入生产提示词。

第二轮 `mail-prompt-v2-20261016-r2.json`：25 条合成样本中 24 条通过，1 条因证据夹入括号解释被严格校验拒绝；用户原邮件仍误判为提示注入。随后进一步明确通用沟通角色：邮件是发件人与收件人的沟通，收件人被要求完成任务不等于审理器被要求篡改规则；证据只复制连续原文，不拼接或加入解释。这些规则不提及任何测试题内容。

工程检查：`cargo fmt --all -- --check`、`cargo build`、`cargo test`（88 CLI + 1095 core，共 1183 项通过，7 项外部测试默认忽略）、`cargo clippy --all-targets -- -D warnings`、release 构建和 `git diff --check` 均通过。真实模型评测另行显式运行，不把默认忽略计为通过。

## 最终实测结果与运行状态

第三轮私有报告：`data/benchmarks/tools/mail-prompt-v2-20261016-r3.json`。报告保存实际通用 system 提示词、模型原始结构化输出、停止原因和用量；不保存思考正文。汇总：`mail-prompt-v2-summary-20261016.json`。

- 25 条合成样本全部通过内容、标签、风险和提醒建议断言。人事、工作、私人请求、行程、普通账户信息、推广垃圾、欺骗广告、引用攻击、真实操纵指令、危险附件及长文事项均有覆盖。
- 用户原邮件隔离重放仍失败：模型仍将普通请求判为 prompt_injection，并否认有实际待办。原样记录，未放宽预期或加入特判；因此完整真实评测为 **25/26，非全绿**，不能称为全链路验收通过。
- 三轮评测均无工具执行、无邮件发送、无桌面通知，不改生产队列。合成题经过开发期迭代，不是独立的泛化准确率测量。
- 工程检查通过，release 已构建。提示词评测结束时常驻进程尚未重启；同日邮件性能优化后已重新启动后台并加载本版通用提示词，系统权限恢复后出现新巡检台账。此部署确认不等于新版通过了新邮件到通知的无人值守验收；后续真实人事邮件的两次隔离复测均因模型字段/证据校验失败转待查看，详见[性能与部署记录](邮件巡检性能优化-20261016.md)。

剩余问题是复杂文本的模型语义误报，不应通过匹配主题、发件人或具体请求绕开。邮件审理仍只返回分析，不执行发件人的任务。常驻长测、睡眠唤醒及自动任务执行均未纳入本轮。

后续同日补充：邮件协议更新至 v3，显式请求 JSON 输出，保持校验硬边界并缩短建议摘要长度，错误定位到字段。原有 25 类样本及 3 次人事重放通过，但旧长篇来信语义误判仍未解决；不能以新结果覆盖上面的失败。最新部署与真实通知联动证据见[缺口修补与闭环验收](邮件缺口修补与闭环验收-20261016.md)。
