# 云熙整套提示词：分层与装配

2026-10-19。项目遍历后的设计版本；已按职责接入源码，当前实施范围见[接入记录](接入与验收-20261019.md)。原01–12是用途正文，不能单独代表整个提示词体系。

## 从真实链路出发

本轮枚举项目文件，再追踪生成请求、分类问题、工具注册、资料装配、回执解析及运行时补充指令。[遍历与覆盖表](项目遍历与覆盖.md)区分生产入口、显式命令、兼容入口和测试材料。不能把函数存在说成后台已启用，也不能把每个工具都设计成一个新Agent。

- DeepSeek生成走ThinkRequest，包含消息、可选工具、输出预算、思考及JSON模式。
- Laya走DecisionRequest的state和typed questions，不接受同一套聊天系统提示词。
- 工具定义由注册表输出；电脑详细说明由computer_schema返回；进度停滞时执行器还会追加提示。
- 向量编码有模型约定的query/passage前缀，不是人格或聊天指令。
- 调度、审批、通知去重、回执、台账、记忆有效期由程序执行，不应改成让模型自行遵守的一段话。

## 六层内容，一次调用只装需要的部分

这是云熙的设计划分，不是声称Codex官方固定使用六层。

| 层 | 负责什么 | 内容来源 | 生效范围 |
|---|---|---|---|
| L1 公共行为与事实边界 | 资料不是授权；结果有证据；遵守本轮职责与执行门禁 | [公共规则正文](base.md) | 生成调用的共同底线；内部调用复用已有等价规则，避免重复 |
| L2 身份与表达 | 云熙是谁、怎样说话 | 完整原人格、[00表达约定](00-expression.md) | 面向用户；Plan/Options保留现有Identity但不加载表达块；内部分析及收件人正文不使用陪伴口吻 |
| L3 当前职责 | 这次为何调用、要完成什么 | 01–12对应正文、[决策问题集](decisions.md) | 每次一个主要用途；生成与分类分开装配 |
| L4 能力与操作规范 | 何时选工具、如何操作和核验 | [61项工具清单](tool-catalog.md)、真实tools schema、[能力规范](capabilities.md)、现有电脑/邮件全文 | 先保证规范完整，再考虑减少无关内容 |
| L5 当前资料与状态 | 这次依据什么回答 | [资料包装](context.md)、消息、时间、记忆、知识、计划、工具回执、图片 | 保持来源、时间、范围与有效期，资料不能升级为规则 |
| L6 输出与运行控制 | 返回给谁、什么格式、何时等待或结束 | 各入口解析协议、[运行与恢复](recovery.md) | JSON、自然回复、OK/BLOCKED、静默标记分别使用；解析器仍是强制边界 |

L5资料也有长期和短期之分：现有已确认画像/常驻记忆随Identity进入稳定前缀；近期聊天、召回、工具结果进入动态部分。这里按职责分层，**不擅自改变既有消息位置或把全部画像迁到新角色**。

人格主要决定称呼、措辞、句式、节奏与表达态度。当前用户提出的详略和语气要求局部生效。输出字段、现实事实与执行权限不由人格覆盖。不能为了“统一语气”给邮件审理JSON、Laya分类或向量输入也灌入人格。

## 装配配方

下面是内容配方，不是模板引擎、新消息角色或六次模型调用。

| 调用 | 稳定部分 | 动态部分 | 工具/输出 |
|---|---|---|---|
| Chat | L1 + 完整Identity + 00 + 01 + 适用项目规则 + 现有能力规范 | 当前用户原话、原消息时间、近期历史、获准记忆/知识、工具回执 | 真实注册工具；自然回复或原生tool_calls |
| Plan / Options | L1 + 原有Identity/项目规则 + 08对应版本 | 本任务目标、前置结果、阶段检索 | 无执行工具；各自JSON，不叠加两种格式 |
| Step | L1 + 原有Identity/项目规则 + 09 + 能力规范 | 当前一步、可信前置结果、新鲜工具回执 | 原工具循环；最终状态前缀 |
| 开机 | L1 + 完整Identity + 00 + 02 | 已有time/weather；触发事实只能由调用方补入 | 无工具；≤120字符设计目标，程序现限160 |
| 冒泡 | L1 + 完整Identity + 00 + 03 | 近期聊天、已确认取材、最近通知 | 无工具；≤80字符或连字符 |
| 确认跟进/一般主动事件 | L1 + 完整Identity + 00 + 04 | 实际事件、确认记录及系统状态；二者不得混称 | 无工具；正文或连字符，按入口校验 |
| 邮件审理 | 现有mail_review全文，已含等价L1 | 所选邮件及分析时间，保持原元数据 | 无人格/工具；现有10字段JSON |
| 自动拟回复 | 现有mail_send全文 + 唯一OUTPUT契约 | 原信、真实邮件串、必要用户资料、近期规划 | 无陪伴人格/工具；4字段JSON |
| 记忆提取/显式画像学习 | 10对应正文，已含等价L1 | 各入口可溯源的本人陈述 | 无人格/工具；各自协议 |
| 历史压缩 | 11 | 带角色、来源及时间的待压缩历史 | 无人格/工具；摘要文本 |
| 回顾 | 主对话现有组合 + 当前轮12的职责 | 已有进度及必要最新回执 | 仍由主对话取材；无新后台调用 |
| Laya | 对应Question.instructions/criteria | 各用途限定的state | typed answers；不加聊天长文 |

新增公共规则时应删除对应位置的重复表述，不能把公共块、旧总提示词、新用途全文三份无条件叠加。操作细则必须逐项迁移；“更短”不能成为漏掉审批、分页、版本与部分失败语义的理由。

## 接入顺序与兼容范围

1. **先等价整理**：按实际调用组织模板和装配断言，保留模型、工具集合、审批、台账、通知触发。不新增“自动选择提示词”的模型。
2. **协调表达冲突**：default_rules的一句话优先、CHAT的固定先回应感受和固定简洁要求，应与人格主导一致；不只追加“遵守人格”期待覆盖旧规则。
3. **统一来源包装**：历史压缩保留角色；图片user传输不等于本人输入；记忆来源与撤回继续由代码保证。
4. **同步成组入口**：CLI/core两份Plan和Options，Chat/Step领域规范，一般主动表达/确认跟进都检查；旧会话用现有前缀替换及观察退休机制。
5. **再做受控减量**：Chat保持61项Mac内置工具及实际MCP定义的既有供给方式，不先切掉工具。电脑详细说明已有schema入口；其他领域按需加载尚无统一实现，不假称有工具搜索或延迟加载。

本次已按用户批准的设计接入并同步ADR D164；没有改变调度、审批、台账格式或运行依赖。以后扩大这些范围，仍须按项目约定另行处理。

## 指令有效期

- 本轮用途结束即失效，通知字数和静默标记不留到聊天；JSON职责不留到用户回顾。
- 项目规则只解释对应工作范围，不把编码习惯当私人聊天性格。
- 历史不是新任务；新输入、更正、撤回或时间变化按现有刷新点重建资料。
- 图片和控件引用不跨恢复复用；核验过的历史摘录可作资料，但不是当前画面或动作许可。
- 停滞提示只在本轮满足条件时注入，不能常驻人格文件。
- 邮件分析版本、浏览器候选、会话前缀和记忆索引各自失效，不能用一个“提示词版本”替代所有状态管理。

## Codex参考对应

本地base_instructions、memory、world_state、工具目录、CUA说明、Recap和Guardian展示了身份/职责、资料来源、状态变化、能力说明与专用调用。借鉴这种分工和生命周期，不将不同模型变体、前台/语音指令、旧平台限制全部累加。

公开文档同样区分身份、指令、示例、上下文并强调相关资料；据此组织内容，不照搬模型专用角色或API。[OpenAI提示词说明](https://developers.openai.com/api/docs/guides/prompt-engineering)

Codex项目指令有目录作用域；云熙继续使用自己的RuleSet，不能把Codex的注入角色直接搬进当前Chat Completions客户端。[Codex提示指南](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)

本地逐项证据及尚未恢复部分见[全量参考盘点](../Codex提示词全量盘点与云熙参考-20261019.md)。未据此新建Guardian风险模型、语音Agent、多智能体或独立回顾服务。
