# ADR-0001：架构与边界

- **状态**：已采纳
- **日期**：2026-10-05
- **决策者**：项目所有者
- **取代**：无（首份架构决策记录）

---

## 一、定位

### 1.1 设计哲学

> **陪伴型 · 通用 · 常驻 · Agent 助理**

四个词各承担一件事，缺一个就退化成别的东西：

| 词 | 承诺 | 缺了会变成 |
|---|---|---|
| **陪伴** | 对使用者状态有连续记忆，介入方式随关系状态变化 | 冷冰冰的调度器 |
| **通用** | 不预设领域；能力可扩展，内核不知道具体领域 | 又一个垂直工具 |
| **常驻** | 7×24 运行，任务与状态跨重启存活 | 需要主动打开的 App |
| **助理** | 既做判断也干活 | 只会聊天的壳，或只会排班的 cron |

### 1.2 不是什么

- **不是多租户产品**：单用户、单机自用。不为"一个实例多人用"付复杂度税。
- **不是纯调度器**：调度只是它的一项能力，不是它的身份。
- **不是编码 Agent**：不追求替代 CLI 编码工具。
- **不是元内核**：见 §六 D2。

### 1.3 与 YunXi 家族的关系

**脱身于、基于、且要优于** YunXi 家族。

- **基于**：陪伴策略、记忆模型、工具审批、fail-closed 默认值等设计直接继承。
- **优于**：差异**只落在三处**——决策层、内聚任务内核、常驻形态。其余部分不做无谓重写。
- **独立性**：本仓库代码独立（新语言栈、新结构），不与 YunXi 仓库形成编译期耦合。

YunXi 家族的既有资产与许可情况见 [`NOTICE`](../../NOTICE)。

## 二、核心判断：陪伴不是功能，是「介入策略」

YunXi 当前的陪伴实现是**规则优先**的：安静时段、频率限制、情绪线索、自动降级，全部硬编码。

而"什么时候该开口、什么时候该沉默、此刻该用关心还是汇报的语气"——**这些本质上全是分类判断**。

因此本项目的核心动作是：

> **把「何时介入、以何种方式介入」从硬编码规则，升级为决策模型在约束内的判断。**

### 2.1 三体问题

| 约束 | 后果 |
|---|---|
| **常驻** | 7×24 跑任务 → 产生大量事件 |
| **陪伴** | 需要介入，但介入多了就是骚扰 |
| **通用** | 事件种类无限 → 写不出穷举规则 |

三者**无法同时用规则满足**：规则要么漏（通用场景写不全），要么吵（保守阈值频繁打扰）。

**唯一能同时满足三者的是一个高准确率的「介入决策器」。** 这就是决策层必须是核心而非配件的原因。

### 2.2 一个必须守住的前提

**陪伴的温度来自「连续性」，不是来自「判断」。**

```text
记忆 / 关系状态  ──提供「凭什么亲近」──┐
                                      ├──→ 决策层判断介入
当下情境         ──提供「此刻发生什么」─┘
```

决策模型越强，越需要一个像样的 state；而 state 的质量取决于记忆系统。
**两者不能互相替代，记忆不能推迟到最后做。**

## 三、分层架构

```text
┌─────────────────────────────────────────────────────────────┐
│ 入口层      CLI · 本地 Web · 微信 · 语音                      │
├─────────────────────────────────────────────────────────────┤
│ 决策层      Laya 类 System-1 模型（非自回归，本地推理）        │
│   输入: state + typed questions                             │
│   输出: choice / score / noul + 概率                         │
├─────────────────────────────────────────────────────────────┤
│ 约束层      确定性规则；只能把决定往【更保守】方向修正          │
├─────────────────────────────────────────────────────────────┤
│ 陪伴层      情绪线索 · 追问 · 主动关怀 · 关系状态              │
├─────────────────────────────────────────────────────────────┤
│ 治理层      任务台账 · 决策台账 · 审批 · 审计                  │
├─────────────────────────────────────────────────────────────┤
│ 调度层      触发器（定时/文件/事件）· 单飞 · 崩溃残留回收       │
├─────────────────────────────────────────────────────────────┤
│ 执行层      子进程 · 凭证剥离 · 超时与进程组清理 · OS 级写入隔离 │
├─────────────────────────────────────────────────────────────┤
│ 能力层      工具 · 浏览器 · 语音 · System-2 大模型             │
└─────────────────────────────────────────────────────────────┘
```

### 3.1 决策流

```text
state（含使用者偏好与约束）+ typed questions
        ↓
   决策模型 → choice / score / noul + 概率
        ↓
   约束层（确定性）→ 只能往更保守修正
        ↓
      动作
```

**约束层永远不会「发明」一个决定，只会否决或降级到更保守的选项。**

示例：

| 模型判断 | 约束修正 | 结果 |
|---|---|---|
| 现在打扰 | 处于安静时段 | 延后聚合 |
| 这事不重要 | 涉及不可逆动作 | 必须人工批准 |
| 自动执行 | 未获批准 | 待批准 |

这与 YunXi 既有设计原则同源：**「只能更保守」**。

### 3.2 双模型结构（System 1 / System 2）

| | System 1 | System 2 |
|---|---|---|
| 实现 | **Laya 类决策模型**（本地、非自回归、毫秒级） | 通用大模型 |
| 职责 | **判断**：要不要打扰、要不要升级、紧急度、是否异常 | **干活**：写、推理、执行 |
| 调用频率 | 每次都跑 | 按需 |
| 输出 | 标签 + 概率 | 文本 / 行动 |

## 四、技术栈

**Rust 2024。**

理由（证据见 §六 D1）：

1. YunXi 家族已有 **12 万行 Rust** 的内核与治理实现可供参考，语言一致才能实质性复用其设计。
2. 常驻进程的长期诉求是**低资源占用 + 长期稳定 + 单二进制分发**。
3. Rust 的显式类型与编译期依赖，契合本项目"边界必须写死在代码里"的要求。

**跨语言能力通过进程边界解决，而不是通过统一语言：**

- 决策模型 → 本地 sidecar 进程（官方实现为 Python）
- 浏览器自动化 → 独立子进程（可复用既有 CDP 方案）
- 语音 → 复用 YunXi Voice Runtime 模式

运行时依赖目前**只有一个**：`chrono`。理由：cron 必须按本地时间解析，而 std 不提供本地时区。

## 五、决策层的具体边界

### 5.1 决策模型是策略的输入，不是策略的替代

此条来自决策模型官方文档原文：

> "The model's decision is an input to policy, **not a substitute for policy**."
> "**enforce approval outside the model**"

具体含义：模型给出概率与标签，**最终决定由约束层做出**。

### 5.2 命题必须可测试

问题库的写法直接决定判断质量：

| ❌ 不可测试 | ✅ 可测试 |
|---|---|
| "客户是否不开心？" | "客户是否明确威胁要取消？" |
| "这封邮件重要吗？" | "这封邮件是否要求 24 小时内回复？" |

**问题库是项目的一等公民**，需要随使用持续迭代并评估。

### 5.3 问题类型的选择

| 类型 | 用途 | 注意事项 |
|---|---|---|
| `choice` | 从命名选项中选择 | 选项必须有可区分的判据；避免"紧急"与"重要"这类重叠标签 |
| `noul` | 估计命题概率 P(true) | 命题必须可测试 |
| `score` | 有序等级评分 | ⚠️ **上游已声明这是弱项**；使用前必须用自己的数据测混淆矩阵 |

### 5.4 输入 state 的质量约束

> "A good state contains **the evidence needed for the decision**, not merely a long dump of everything your service knows."

**state 必须主动裁剪，只喂判断所需的证据。** 理由：决策模型上下文窗口有限，长输入会截断且准确率下降。

同时：**密钥与无关字段一律不得进入 state。**

## 六、核心决策与理由

### D1. 技术栈选 Rust，否决 TypeScript/Node

| 选项 | 结论 | 理由 |
|---|---|---|
| **Rust 2024** | ✅ 采纳 | 见 §四 |
| TypeScript / Node | ❌ 否决 | 曾因"Windows 常驻有现成配方、CDP 生态在 Node 侧"而倾向 Node。但该判断建立在**只看过 5 个开源项目 README**的基础上；在发现自身已有 12 万行 Rust 内核实现后，改选 Rust 可实质复用设计，而跨语言需求已由进程边界解决 |
| Python | ❌ 否决 | 常驻进程的长期资源与依赖稳定性不如 Rust；且无法复用既有 Rust 资产 |

### D2. 做内聚的具体内核，不做元内核

**否决元内核范式**（即"内核什么都不知道，只提供 Context / Service / Effect / Event 等通用原语，一切挂在其上"）。

理由：**该范式已经实现过**。重做一遍既没有学习，也构不成差异化。且元内核把具体功能拆散到各 Service，与"基础功能封装在一起"的目标相反。

**替代方案**：内核明确知道自己管什么——

```text
job      任务与状态机
ledger   台账（append-only，可重建投影）
trigger  触发（定时 / 文件 / 事件）
policy   约束（两个正交旋钮）
decide   决策（决策模型调用与结果归一）
exec     执行（子进程、凭证剥离、隔离）
```

**没有服务查找、没有 Effect 自动回滚、没有事件总线、没有 Fiber 生命周期。** 依赖是编译期显式的，调用栈是直的。

### D3. 暂缓插件框架，但保留直接子进程隔离

**这两件事经常被混为一谈，但必须分开：**

| | 插件框架 | 直接子进程 |
|---|---|---|
| 需要什么 | catalogue / manifest / 版本 / 依赖解析 / 生命周期 / 热替换 | `spawn` |
| 解决什么 | **能力生态**（第三方可扩展） | **故障隔离**（卡死不拖垮内核） |
| 本项目 | ❌ 暂缓 | ✅ 采纳 |

等真的需要第三方扩展时再谈插件框架。**暂缓不等于放弃隔离。**

### D4. 权限模型：两个正交旋钮

**否决单档 policy mode。** 采纳两个正交维度 + 命名预设：

| 旋钮 | 取值 |
|---|---|
| `sandbox` | `read-only` / `workspace-write` / `danger-full-access` |
| `approval` | `ask` / `never` |

- 预设（preset）只是旋钮值的**命名组合**。
- **`custom` 只作展示，永不作为切换目标或事件载荷**——未知状态不许写进日志。
- `approval = never` 的含义是 **"需要批准的动作自动拒绝"**，**不是"自动放行"**。这条反直觉但正确。

### D5. 审批结果使用封闭词汇表

| 结果 | 含义 |
|---|---|
| `allowed-once` | **唯一的授权**，且只对本次动作有效 |
| `rejected` | 被拒绝 |
| `cancelled` | 被取消（信号中止） |
| `unavailable` | **无可用应答者 / 应答者异常 / 返回值不在词汇表内** |

两条不可动摇的规则：

1. **缺少应答者 = fail closed**（`unavailable`）。
2. **不信任应答者返回值**：任何词汇表之外的值一律归一为 `unavailable`。

### D6. 台账：append-only + 边界 + 版本化迁移链

- **事件日志是唯一真相来源**，状态全部是投影，可丢弃重建。
- **审计事件必须成对，且被「边界」包住**。理由：落在边界之外的事件与**崩溃残尾无法区分**，reload 时会被静默丢弃。因此宁可直接返回错误，也不写入边界外的事件。
- **格式版本化 + 强制相邻迁移链**：`vN → vN+1`，不可跳版、不可重名、必须完整覆盖 `0..current`。
- **拒绝非无损 JSON**（包括 `-0` 这类 JSON 往返不稳定的值）。

### D7. 隔离声明：承诺到哪就说到哪

**诚实隔离（honest isolation）**要求声称的隔离级别与实现一致。当前实际状况：

| 平台 / 机制 | 状态 | 真实保证 |
|---|---|---|
| **Windows 低完整性令牌** | ✅ **已实现并自检通过** | 子进程**写不进**任何中完整性对象（用户目录里的文件全是中完整性）；可写区仅限低完整性沙箱 |
| **Windows Job Object** | ✅ 已实现并验证 | 进程树强制回收（`KILL_ON_JOB_CLOSE`）、单进程内存上限、进程数上限 |
| 其他平台 | ✅ 进程隔离 | 独立进程组 + 超时整组清理 |

#### 机制：为什么是完整性级别，不是能力 SID

写入隔离来自 **`SetTokenInformation(TokenIntegrityLevel)` 把令牌降到 Low**，
而不是最初设计的"受限令牌 + 能力 SID 限制列表"。后者被**四种变体对照实测证伪**：

| 限制列表 | flags | 结果 |
|---|---|---|
| **空** | `DISABLE_MAX_PRIVILEGE` | ✅ 子进程正常运行 |
| `Everyone` | `DISABLE_MAX_PRIVILEGE` | ❌ `STATUS_DLL_INIT_FAILED` |
| `Everyone` + 能力 SID | `DISABLE_MAX_PRIVILEGE` | ❌ 同上 |
| `Everyone` | `+ WRITE_RESTRICTED` | ❌ 同上 |

> **限制列表只要非空，子进程就无法完成初始化**（`0xC0000142`）。根因：限制列表对
> 读写一视同仁，而进程启动本身就需要访问只授权给用户 SID 的对象（注册表 `HKCU`、
> 窗口站等）。`WRITE_RESTRICTED` 把限制收窄到写，但进程启动**确实要写**，仍过不去。

另一条试过的路是给目录**打**低完整性标签，失败于 `ERROR_ACCESS_DENIED (5)`：
完整性标签存在 SACL 里，改 SACL 需要 `SeSecurityPrivilege`（管理员）。
最终方案改用系统预置的 `%USERPROFILE%\AppData\LocalLow`——它**已经**是低完整性目录，
在其下建子目录会继承标签，**不需要任何特权**。

`DISABLE_MAX_PRIVILEGE` 仍然保留（它不是隔离的来源，但与完整性降级同向叠加）。

#### 隔离声明由实测背书，不由代码注释背书

`yunxi-bot isolation-check` 会真起一个受限子进程，让它分别尝试写**允许**与**禁止**
的两条路径，只有"允许的写成功、禁止的写失败"才算通过：

```text
$ yunxi-bot isolation-check
授权区（低完整性）   : C:\Users\...\AppData\LocalLow\YunXiBot-isocheck-...\allowed
禁止区（中完整性）   : D:\...\temp\yunxi-isocheck-...\denied

授权路径写入 : true
未授权路径写入: false
stdout: OK   ...\LocalLow\...\allowed\yunxi-canary-allowed.txt
        FAIL ...\temp\...\denied\yunxi-canary-denied.txt -> 拒绝访问。 (os error 5)
判定: 写入隔离生效：授权路径可写，未授权路径被拒
```

**自检抓出七个能安静跑下去的错误**，其中第一个差点让整个努力建立在假结论上：

1. **canary 不能用 `current_exe()`**——在 `cargo test` 下那是测试二进制，它把
   `__canary-write` 当成测试名过滤器、跑 0 个测试后正常退出，于是自检连续几轮都在
   报告"两条路径都没写成"的**假结论**，而进程压根没执行到那段代码。直到把 canary 的
   stdout 打出来才看见"running 0 tests"。
2. `CreateRestrictedToken` 真实签名有 **9 个参数**，少声明中间两个会让调用错位读到
   栈上垃圾（表现为 Win32 错误 534「算术结果超过 32 位」，与任何一步都对不上）；
3. `TRUSTEE_W` 必须含 `TrusteeType` 且字段顺序与 Win32 一致（否则 87）；
4. `GetNamedSecurityInfoW` 拒绝带结尾反斜杠的路径（87）；
5. 空环境块对 `CreateProcess` 非法（87）；
6. `advapi32` 必须显式 `#[link]`，否则 `FreeSid` 链接失败；
7. 限制 SID 入参是 `SID_AND_ATTRIBUTES` 结构体数组，不是 SID 指针数组。

**必须明确写下的边界：**

> **它只隔离写入，不隔离读取。** 子进程仍能读该用户能读的任何东西。
> Job Object 也不构成文件系统沙箱。把"进程与资源隔离"说成"沙箱"是 §八第 4 条禁止的。

**失败契约（不可违背）：要求了拿不到的隔离级别时，子进程绝不无隔离派生。**

[`write_isolation_verified`] **是这条契约的执行点**：要求 OS 级写入隔离时，不会因为
"代码里有这个功能"就放行，而是要求自检真的跑过一次并成功；自检不通过就在**派生之前**拒绝。

差分验证（同一任务，开关隔离对比）：

| | 任务写用户目录的结果 |
|---|---|
| 不加隔离 | ✅ 创建成功 |
| `--require-os-isolation` | ❌ `error=拒绝访问。`，且台账记录 `isolation=Windows 受限令牌 + 能力 SID 写入隔离` |

### D8. 任务默认带资源护栏

每个任务默认施加 Job Object 资源上限（单进程 2 GiB、最多 16 个进程）。

理由：常驻 Agent 的价值建立在"它一直在"之上，而**一个失控的任务就能摧毁这个前提**。
护栏不是为了精确配额，是为了"一个任务不能把守护进程拖垮"。上限可按任务覆盖。

## 七、降级策略

决策模型本地运行，但仍会失败。**不同类别的正确降级方向是相反的**，因此必须先分类。

### 7.1 失败形态

| # | 形态 | 检测方式 |
|---|---|---|
| 1 | 服务未启动 / 端口不通 | 连接失败 |
| 2 | 超时 | 超过延迟预算 |
| 3 | 返回非法 | schema 校验失败 / 概率缺失 |
| 4 | 进程崩溃 / OOM | 连续失败计数 |
| 5 | 输入被截断 | 实际 token 超过模型上限 |
| 6 | 模型自身不确定 | 最高概率低于阈值 |

### 7.2 降级方向表

| 决策类别 | 正常 | **降级时** | 方向 | 理由 |
|---|---|---|---|---|
| **打扰 / 通知** | 模型判断 | **不打扰**，转待办聚合 | fail-closed | 宁可漏报，不可半夜吵 |
| **升级 / 人工介入** | 模型判断 | **升级给人** | **fail-open** | 宁可误报，不可漏掉危险 |
| **不可逆动作** | 模型 + 强制批准 | **强制批准，行为不变** | 不参与降级 | 批准是硬约束，不是判断 |
| **分类 / 归档** | 模型判断 | 归入**待分类队列** | 不猜 | 猜错比不猜代价高 |
| **紧急度评分** | 模型判断 | 按**普通**处理 | fail-closed | 不升级 |
| **异常识别** | 模型判断 | 按**可疑**处理并记日志 | **fail-open** | 安全侧倾向 |

> ⚠️ 第一行与第二行**方向相反**。统一的"模型挂了就走规则兜底"会同时犯两个错误。

### 7.3 五条降级纪律

1. **降级必须可见**：每条降级决策都带 `degraded: true` 与失败原因，进决策台账。绝不静默。
2. **降级期间不丢弃，只延后**：打扰类降级时写入待办；模型恢复后**重跑一遍再决定**，而非简单补推。
3. **连续失败要熔断**：连续 N 次失败后停止调用，转纯降级模式，并**通知一次**（这次通知本身走 fail-open）。
4. **降级方向可配置，但只能更保守**：默认值为上表；修改时不允许调得更激进。
5. **不使用未校准的概率阈值**：概率可靠性必须用本项目自己的数据验证后才可用于强制决策。

---

## 八、硬边界（不可违背）

1. **失败方向朝"不执行"**：判定不明一律转待批准，绝不放行。
2. **不可逆动作必须人工批准**，且批准不参与降级。
3. **凭证不进日志**：子进程一律剥离凭证；密钥只写环境变量名，不写配置文件。
4. **不把进程内策略包装成沙箱**：声称的隔离级别必须与实现一致。
5. **决策模型的判断不能替代策略**：模型给概率，约束层做决定。
6. **不静默降级**：任何降级都必须留痕。
7. **不写入边界外的审计事件**：宁可抛错。

### D9. 引入 TLS 依赖，但只此一个

**决策：** 新增 `ureq`（底层 rustls）作为唯一的网络依赖。

**理由：** Agnes 走 HTTPS，而 std 没有 TLS。本项目已有的 HTTP 客户端
（`decide/http.rs`）是纯 TCP 手写的——那对**本地回环**的 Laya sidecar 是正确的
（不需要 TLS，也不该为此拉依赖树）；但远端 API 不同：**自己实现 TLS 是不负责任的**，
必须用经过审计的实现。

选 `ureq` 而不是 `reqwest`：前者是阻塞式小体积，后者会把 tokio 整套异步运行时
一并带进来，而本项目的守护循环是同步的。

**代价（如实记录）：** 传递依赖从 3 个涨到 **57 个包**。这是本项目迄今最大的一次
依赖扩张，换来的是"不必自己写 TLS"——这笔账是划算的，但不能假装它没有成本。

### D10. 两层模型的分工，以及 10 RPM 决定的架构

**决策层（System 1）跑本地 Laya，思考层（System 2）接远端 Agnes。**

- **Laya**：只管"该不该介入"这一类判断。快、免费、离线可用。
- **Agnes**：Agent 的通用能力——推理、写作、规划、干活。慢、贵、有配额。

**Laya 不负责思考，只负责判断要不要打扰你。** 两者不是一回事。

**顺序不可颠倒：本地先筛 → 只有判定「开口」才动用远端。**

这不是省钱的优化，是配额决定的**结构必然**：Agnes 免费档文本模型
**实际 RPM 只有 10**（2026-09 从 20 下调 50%）。常驻进程若每轮都打远端，
几秒钟就把配额烧光并触发限流。

**推论：没装 Laya 时 Agent 是哑的。** 判断层不可用 → 打扰类降级为 fail-closed
→ 永远不开口。这是设计，不是缺陷——但必须让它**可见**（daemon 会提示一次），
否则用户会以为 Agent 坏了。

### D11. Agent 循环只以台账为事实来源

**决策：** 现状（situation）全部从台账投影得出，不引入第二份状态。

**理由：** 一旦 "当前状态" 有第二份副本，台账就不再是唯一事实来源，
"当初为什么这么决定"就无法回答。

**两个具体取舍：**

1. `interventions_today` 用**滚动 24 小时**而不是本地日历日。日历日会在午夜突然
   清零，而那正是最不该突然放开打扰额度的时刻。
2. 提示词必须包含**具体发生了什么**（哪个任务失败、报的什么错），而不只是计数。
   早先版本只喂"连续失败：2 次"这个数字，模型自然只能说"没什么好说的"——
   判断层看的是结构性信号，表达层需要的是具体事实。
### D12. 决策模型选 Verdict，不选 Laya；权重走 Release 资产

**决策：** 决策层后端从 Laya 换成 [Verdict](https://github.com/Manavarya09/verdict)。

**三条硬条件，Laya 一条都不满足：**

| 硬条件 | 出处 | Laya | Verdict |
|---|---|---|---|
| 中文可用 | 全程中文 | 非拉丁文字**静默失败**（高棉语在 95.2% 置信度下得 0 分） | multilingual-e5-small |
| 概率可当阈值用 | §7.3 第 5 条 | ECE 0.466，**且 multilingual 完全没带拟合温度** | ECE 0.014–0.030 |
| 选项顺序不影响答案 | 判断"该不该打扰" | **翻转率 0.23** | 结构上保证（已实测） |

**零样本这条路本身就是死的。** 三家在结构化 state 上的零样本成绩全部落在
0.32–0.36（多数类基线是 0.461）——**不如永远猜多数类**。真正的差距来自在
自己的标签上拟合。而 Verdict 的 `fit()` 在笔记本 CPU 上是 **0.9 秒**，
Laya 要 4–5 小时 / 2×T4。**能快速重训，比一次训得好更重要。**

**换后端没有改一行 Rust**：Verdict 暴露 `/v1/systemone`，与 `laya_server.py`
同一个线协议。当初把 sidecar 契约设计成"上游库差异关在 Python 侧"，这次兑现了。

**权重不进 git。** 单个 `model.safetensors` 有 448.8 MB，超过 GitHub 的
100 MiB 单文件硬上限，推送会被直接拒绝——这不是偏好问题。所以：

- **Release 资产**（`models-v1`，347.7 MB）：编码器权重，第三方产物；
- **仓库里**：下载+校验脚本、SHA256 清单、模型卡（归属声明）；
- **落盘位置**：`<数据目录>/models/verdict-small/`，sidecar 优先读本地路径，
  实测 `HF_HUB_OFFLINE=1` 下正常加载——**离线自包含**。

**校验失败一律拒绝使用，绝不"将就用"。** 一个哈希不对的权重会让决策层给出
无法解释的判断，比没有模型更糟。

### D13. 未校准的概率只做 argmax，不做阈值

**决策：** Verdict 报告 `calibrated: false` 时，Rust 侧**只用它的 argmax，
不拿它的概率卡任何阈值**。

这正是 §7.3 第 5 条"不设未校准的阈值"的落地。sidecar 把 `calibrated`
如实上报（而不是默认它可信），Rust 侧据此约束自己的用法。

要让概率真正可用，需要一批带标签的"该不该打扰"样例做 `fit` + `calibrate`，
拿到保形弃权的覆盖率保证。在那之前，约束层继续用**确定性规则**
（安静时段、每日上限、最小间隔）——那些是使用者设定的硬事实，不依赖模型概率。

### D14. 任务执行链路：人类给目标，系统拆解、逐步执行、循环到完成

**决策：** 增加一条与"调度"并列的链路，输入是**人类的目标**而不是命令：

```text
人类输入任务
     ↓
【拆解】系统提示词 + 人格 + 目标 → 模型给出步骤清单（带依赖）
     ↓
【逐个执行】取依赖已满足的步骤（可并行的是一批）
     ↓        ↑
     │        └── 完成一个，回填结果
     ↓
【决策点】模型产生选项 → 本地决策模型选一个
     │                        │
     │                        └─ 它弃权 → 升级人工
     ↓
【循环】直到所有步骤终态
```

**为什么与既有 `job` 那套分开。** `job` 是"定时/触发的一件差事"，跑完就完了；
这一套是"人类给的目标"，要拆解、要能跨重启续跑。两者生命周期不同。
台账里用独立的事件词汇（`TaskCreated` / `TaskPlanned` / `StepRunning` / …），
由 `ledger::task_from_events` 折叠成任务集合。

**步骤是任务，不是子任务的花招。** 每个步骤**各自路由一次**——按自己的类型和
调用次数选模型。这正好满足"复杂走 DeepSeek、简单走 Agnes"：同一个目标里，
"查一下日程"走 Agnes，"分析这周的邮件"走 DeepSeek。
而**某一步自己从开始到结束只用一个模型**，中途不换（换模型会把前缀缓存作废）。

**三条硬约束：**

| 约束 | 后果 |
|---|---|
| 台账是唯一事实来源 | 每轮从台账重新投影，不拿内存状态推进；重启后重放事件即可续跑 |
| 预算是硬上限 | 调用次数用尽就停，**不"再试一次"**。失控循环比失败的任务贵得多 |
| 失败方向朝「不执行」 | 成环、卡住、预算用尽、决策弃权 —— 全部停在原地等人 |

**"卡住"是一个必须存在的状态。** 没有它，"依赖成环"和"还在跑"会长得一模一样，
于是死锁表现为无限等待。所以 `Stalled` 是独立状态，且成环在**花钱之前**就查出来
（Kahn 拓扑排序，纯函数、不需要网络）。

**被打断的步骤要回收。** 预算中途用尽、或进程被杀，都会留下"标记为执行中、
但没人在跑"的步骤。而 `Running` 既不是终态、也不会被选中，于是任务卡死。
引擎在任务闲置时先把它们退回待执行——**退回而不是判失败，因为我们不知道
它做没做完**（可能已在远端产生副作用）。

**并行：设计好，但先不接线。** `ready_steps` 返回的是一批可并行的步骤，
依赖检查和状态机都为并行准备好了。但当前台账是串行的（`append` 要独占且每条
flush），限流器也是共享状态——**Agnes 免费档 10 RPM 下并行只会更快撞 429**。
并行的收益在远端调用，瓶颈在台账和配额。等真有并发需求再接。

### D15. 模型选择器有两个轴，不能合并

**决策：** 路由同时回答两个问题，判据不同：

| 轴 | 决定什么 | 依据 |
|---|---|---|
| **任务类型**（`TaskKind`） | **要不要思考** | 这活需要多少推理 |
| **调用次数**（`TaskProfile`） | **用哪个模型** | RPM 瓶颈 |

**我最初只做了第二个轴，而且因此把思考模式全局关掉了——那是错的。**

DeepSeek 的思考模式实测（同一个需要推理的问题）：

| 模式 | 输出 token | 思考字符 | 答案字符 | 耗时 |
|---|---|---|---|---|
| 默认（= 开） | 855 | 1037 | 218 | 4.2s |
| 显式 `enabled` | 815 | 941 | 253 | 3.9s |
| 显式 `disabled` | **340** | 0 | **558** | 2.1s |

省下的 60% 输出 token **正是推理本身**。所以正确做法不是"全局关掉省钱"，
而是**只在不需要推理的任务上关**——省掉的本来就是浪费。

**两个轴交汇处有一条必须显式处理的规则。** 一个只有一句话的分析步骤，
按调用次数算是轻量档 → Agnes。但 Agnes 不吃 `thinking` 字段，
于是**这一步永远拿不到思考**，而它恰恰是唯一真正需要思考的一步。
所以：**需要推理但端点不支持思考时，换到支持思考的端点。**
判据的优先级是明确的——调用次数决定"要不要换不排队的模型"（优化），
需要推理决定"能不能省这次钱"（硬约束）。

**实测确认：思考模式与工具调用不冲突**（带 `tools` 请求返回 `finish_reason=tool_calls`，
正常带回 `reasoning_content`）。这是把思考模式用在执行链路里的前提。

**任务类型由确定性信号判断，拿不准才问本地决策模型。** 顺序不能反：
每次都问模型判复杂度，等于为了省钱先花钱。有测试断言"确定性路径一次模型调用
都不发生"。

**`TaskKind::classify` 覆盖七类**：对话 / 查找 / 生成 / 修改 / 分析 / 规划 / 执行，
其中只有**分析与规划**需要推理。分类链的顺序即优先级，
**推理信号最强、排在最前**——一个带"对比一下"的短句是分析任务，
不该因为字少被当成寒暄。起草类（"写一封…"）有独立信号，
否则会全部掉进最后的"短句→对话"兜底。

### D16. 缓存布局与成本记账：先记账，后算钱

**决策：** 提示词强制三段式，顺序不可变：

```text
┌─────────────────────────────────────┐
│ 稳定段：系统提示词 + 人格 + 工具定义  │  ← 字节级稳定，跨调用完全相同
├─────────────────────────────────────┤
│ 追加段：已完成步骤的历史              │  ← 只追加，绝不重写前面的
├─────────────────────────────────────┤
│ 易变段：当前要问的问题                │  ← 每次不同，放最后
└─────────────────────────────────────┘
```

依据是 DeepSeek 缓存文档里那个反直觉的例子：`A+B` 之后请求 `A+C` **不命中**，
因为 `A+C` 无法完整匹配 `A+B` 这个前缀单元。
**在提示词中间插入任何变化内容，整段前缀就作废。**

`PromptLayout::fingerprint()` 让"前缀是否稳定"变成**可断言的东西**，
而不是一句写在文档里的叮嘱。`record_reply()` 会**消费掉待问的问题**——
让"同一个问题既留在易变段又进历史"不可能发生；早先的 `push_exchange(q, a)`
要求调用方把问题再传一遍，实测会让问题出现两次且下一轮前缀对不上。

**三个会话各自独立**（拆解 / 执行 / 选项），因为三者系统提示词不同；
混在一起会导致每次切换都作废前缀。**按 provider 分开记历史**，
因为两家的缓存互不相通。CLI 的 `do --show-prompt` 把三段前缀打出来，
这是使用者唯一能亲眼核对缓存前提的地方。

**成本记账先存原始计数，不存金额。** 每次调用把回执里的
`prompt_tokens` / `completion_tokens` / 缓存命中数写进台账（`EventKind::ModelCalled`）。
单价和时段只影响"怎么算钱"，不影响"花了多少 token"。这样单价变了可以重算历史。

**必须诚实的地方：** 服务端没回缓存字段时，`has_cache_data` 是 `false`，
汇总里单独列出**而不是混进"未命中"**——"不知道"和"确实没命中"含义不同。
实测 Agnes **不回**缓存字段，DeepSeek 回。所以两者在报表里的呈现必须不一样。

**缓存折扣不能共用常数：** DeepSeek 是 **50 倍**（0.02 vs 1），Agnes 是 10 倍。
我最初按 Agnes 类推写成了 10 倍，被测试纠正。
DeepSeek 还分时段——空闲时段**半价**，所以常驻 Agent 可以把重任务排到空闲时段。

### D17. 本地限流不是失败

**决策：** `ThinkError::LocalThrottle`（还没到下次可发送的时间）必须**等一等再发**，
不计入步骤的重试次数，也不判失败。

**这是真实运行逼出来的一条。** Agnes 免费档 10 RPM，一个任务连着几个步骤必然
撞上限流。第一版把 `LocalThrottle` 当普通错误往上抛，引擎把它算作"步骤失败"、
消耗重试次数，结果**三步里两步都跑不完**——而实际上什么错都没有，只是需要等几秒。

本地限流和远端 429 是同一类东西：**"现在不行"不是"不行"**。
等待有上限（单次 30 秒、最多 4 轮），超过就如实报错——
常驻进程不能无限阻塞。等待时间为 0 时立刻放弃，否则会变成吃 CPU 的空转。

`sleep` 放在客户端而不是引擎里：限流是客户端的属性，而且一次等待只扣一次预算。

### D18. 步骤产出有明确契约：模型必须自报成功或阻塞

**决策：** 每个步骤的产出**必须以 `OK:` 或 `BLOCKED:` 开头**。
`BLOCKED:` → 该步骤判失败且**不重试**；`OK:` → 成功（标记会被剥掉，不进结果正文）；
没有标记 → 按成功处理，但台账里记 `marked: false`。

**这条是真实运行逼出来的，而且它属于最坏的一类错。** 一个三步任务，
模型对前两步都回了"做不了。我没有联网能力，无法获取实时天气数据……"，
而引擎把它们**记成了成功**——因为在引擎眼里"模型返回了文本"就是成功。
于是任务报告"完成 2 步"，实际什么都没办成。

> **报告说做完了而实际没做，比直接失败危险得多。**

**为什么不靠关键词猜。** "做不了"有一万种说法（"无法"、"缺少"、"需要你提供"、
"暂不支持"……），而且模型可以用"做不了"描述*别人*做不了的事。
猜关键词会时对时错，而这类判定错一次的代价是使用者以为事情办好了。
所以用一条**格式约定**：可判定、可测试、不依赖措辞。

**为什么 `BLOCKED:` 不重试。** 模型已经说了缺什么（缺联网、缺权限、缺 key）。
再发一次请求，它还是缺同样的东西——重试只是浪费配额和等待。

**为什么无标记按成功算。** 内容确实在。判失败会让它白重试一次，
而"白重试"是明确的浪费；"无标记却按成功记"最多是漏报，
且已经在台账里留了痕。**两侧的代价不对称，所以选择偏向前者。**

**这不是新增的失败模式，而是让已有的诚实变成机器可读的。**
执行单步的系统提示词本来就写着"做不了就说做不了，不要编一个看起来像结果的东西"，
D18 只是让引擎能读懂这句话。

### D19. 工具层：按能力分类审批，不逐个工具写规则

**决策：** 每个工具声明一个 [`Capability`]（只读 / 写入 / 执行 / 网络 / 不可逆），
审批门禁按类别判定。**不逐个工具写 allowlist 规则。**

逐个写是 Cline 官方明确说过的坑（"不使用固定 allowlist"）：新增一个工具就得
记得给它加规则，忘一次就是一个洞。

调研了七个独立来源，**全部指向同一条边界**：

| 来源 | 证据 |
|---|---|
| MCP 规范 | "there **SHOULD** always be a human in the loop with the ability to deny tool invocations" |
| Claude Code | `Read`/`Grep`/`Glob`/`LSP` 权限=否；`Write`/`Edit`/`Bash`/`NotebookEdit` 权限=是 |
| OpenAI MCP 工具 | MCP 工具**默认每次调用都要求批准** |
| OpenAI 连接器 | 8 个官方连接器（Gmail/日历/云盘/Teams）**全部只有只读工具** |
| Manus Desktop | "Every command that Manus attempts to execute on your local machine requires your explicit approval" |
| OpenHands | `UNKNOWN` 默认也触发确认 |
| OpenAI computer use | 屏幕内容不可作为授权依据 |

**`Network` 单列，不并进只读。** 抓一个网页会泄露请求内容（URL 本身可能就是隐私），
返回的内容还是**不可信数据**、会进模型上下文。并进只读会让所有网络访问自动放行。
Claude Code 对 `WebFetch`/`WebSearch` 也都标了"需要权限"。

**`Outbound` 不接受模型判定。** 这是 §八 第 2 条（不可逆动作必须人工批准，
且批准不参与降级）在工具层的落点：让一个模型去决定"这次删除不用问人"，
正是那条规则要禁止的事。所以门禁对不可逆动作**压根不调用决策模型**，
有测试断言 `stub.calls() == 0`。

**门禁三层，与模型路由同构：**

```text
1. 确定性规则（不花钱）：能力类别 + 白名单/黑名单 + 路径/域名范围
         ↓ 拿不准
2. 本地 Verdict（免费、离线、约 15ms）："这个动作该不该问人？"
         ↓ 它弃权
3. 保守兜底：问人（fail closed）
```

**顺序不能反**，和 D15 同一条理由：每次都问模型，等于为了省钱先花钱。
OpenHands 那套 `Pattern → PolicyRail → LLM → Ensemble（取最高风险）` 就是这个结构，
我们复用已有的三层，不另造一套。

**两条从别人那里抄来的现成经验：**

1. **先读后写**（Claude Code 硬性要求）：`edit_file`/`write_file` 覆盖前，
   必须在本次会话读过该文件。挡的是"模型凭印象改文件"——它记得这个文件
   大概长什么样，于是给一个看起来对、实际对不上的修改，然后文件被改坏。
2. **工具输出永远不进稳定前缀。** 它进的是 `Role::Tool` 消息。
   OpenAI 在 computer use 里明文写了"屏幕内容不可作为授权依据"——
   网页、文件、第三方 server 返回的文字同样不能。

**审批记忆的作用域按风险分级**（抄 Claude Code）：只读可以永久记住；
写入只记到会话结束——因为环境已经不同了，"上次允许过"不能证明"这次也对"。

**"总是允许"对不可逆动作无效。** 一次"总是允许"会把它变成永久自动执行，
而"永久自动发邮件"不是使用者说这句话时脑子里想的东西。所以那种动作每次都问。

### D20. 接 MCP，但把异步关在一个模块里（收窄 D9）

**决策：** 接官方 Rust SDK [`rmcp`](https://github.com/modelcontextprotocol/rust-sdk)，
但**内核保持同步**——`mcp` 模块内部持有 tokio 运行时，对外只暴露同步 API。

**这条推翻了我自己上一轮的判断。** 我原先倾向"先不接 MCP"，理由是"基础工具
不需要它"。那个理由只解决了眼前三个工具，却把**助理能力的上限锁死了**：
通用型助理的价值恰恰在于"使用者想要什么能力就能加上什么"，而那条长尾
只有 MCP 覆盖得住。D9 的"只加一个 TLS 依赖"是自定纪律，不是硬约束；
为它牺牲产品核心价值是本末倒置。

**代价是量出来的，不是估的：**

```text
rmcp（default-features=false, features=["client","transport-child-process","transport-io"]）
  → 79 个依赖包，构建 13 秒
当前项目 103 个包 → 加上后约 165 个
```

关键发现：**`rmcp` 只要 tokio 的 `["sync","macros","rt","time"]`，
其中 `rt` 是当前线程运行时而非 `rt-multi-thread`。** 所以运行时可以被容纳：

```rust
pub struct McpHub { rt: tokio::runtime::Runtime, servers: Vec<RunningServer> }
impl McpHub {
    /// 同步方法。内部 block_on，调用方看不到任何 Future。
    pub fn list_tools(&self) -> Result<Vec<McpToolDesc>, McpError>;
    pub fn call(&self, server: &str, tool: &str, args: Value) -> Result<String, McpError>;
}
```

执行引擎、台账、路由、决策层全部保持同步，`ureq` 继续用。
代价是"多一个模块 + 一个运行时对象"，不是"重写整个项目"。

**三件必须一起定下来的事：**

1. **MCP 工具默认需要审批。** server 自己声明的能力是**声称，不是事实**。
   所以 MCP 工具的 `Capability` 默认未知 → 按失败方向朝不执行处理。
   使用者在配置里对该 server 的该工具显式写规则，才算预批准。
2. **工具名必须带出处前缀**：`mcp__<server>__<tool>`。
   两个 server 都叫 `search` 时会静默串台，而这种错极难排查。
3. **先只支持 stdio 传输。** `rmcp` 的 HTTP 传输要拉 `reqwest`，
   那是**第二套 TLS 栈**（我们已经用 `ureq` + rustls）。绝大多数 MCP server
   就是 `npx`/`uvx`/独立二进制，stdio 覆盖得住。HTTP 传输等真有远程 server
   需求再加，届时单独决策 TLS 栈要不要换。

**D9 的历史不改写。** D9 写的是"引入 TLS 依赖，但只此一个"，现在多了一个
运行时族——**新增本条说明 D9 的适用范围被收窄了**，而不是把 D9 改成
现在看起来对的样子。ADR 的价值在于留下"当时为什么这么想"。

### D21. 定位落在"助理"上：信息 → 判断 → 通知

**决策：** 在产品定位上，Bot 的重点是**通用常驻助理**——处理未读邮件、
处理信息、通知。它的核心链路是：

```text
信息进来（邮件 / 以后还有日历、消息、文件变化）
        ↓
值不值得打扰你？   ← 决策层（Verdict）的正业
        ↓
   值得 → 通知你
   不值得 → 静默记录，你要的时候能查
        ↓
你的处置（已读/忽略/以后别烦我）→ 回写，喂回下一次判断
```

**定位澄清改变了优先级。** 原先把"陪伴"和"助理"并列，实际澄清是
**重点在助理**。这不是措辞问题——它决定了先做哪一半：陪伴层会"开口"，
但 `out.spoken` 只被 `println!` 到守护进程的控制台，而后台跑的控制台没人看。
**一个不会把事告诉你的助理不叫助理，叫日志。** 所以通知出口是地基。

**为什么"通知出口"必须有投递证据（D22 详述）：** "调用了通知 API"和
"使用者看到了"是两件完全不同的事，中间隔着勿扰、应用被关、组策略。
把前者当后者就是**虚报送达**，而代价是使用者以后不再自己去看。

**与家族的分工写清楚：** 家族里已有的微信（`YunXi Agent`，约 11000 行）
与语音（`YunXi Voice Runtime`，17862 端口）是它们的领域。Bot 的重点是
"信息 → 判断 → 通知"，可以借鉴那条链的审计经验与能力边界写法，
**但不照搬其 crate 结构**。

### D22. 不许虚报送达，不许假报安静

**决策：** 投递与读取两类结果都必须**如实分档**，任何"不确定"都不许向
乐观方向取整。

**投递四档**，只有一档允许说"通知你了"：

| 结果 | 含义 | 能说"通知你了"吗 |
|---|---|---|
| `Confirmed` | 在系统通知中心里**查得到** | 是 |
| `HandedOff` | 交给了系统，但**无法确认你看见**（勿扰就是这档） | **否** |
| `Blocked` | 确定送不到（通知被关 / 被策略禁） | 否 |
| `Failed` | 发送本身失败 | 否 |

**"命令退出码是 0"不算证据**——那正是虚报的来源。所以 Windows 后端做三件事
而不是一件：查 `ToastNotifier.Setting`（有文档的 API）→ 发 → 查
`History.GetHistory(aumid)` **读回来才算 confirmed**。

**解析不出结果时返回 `HandedOff` 而不是 `Confirmed`**——失败方向朝
"没确认送达"。这条是整层的立身之本。

**读取侧同理，三种"没有"必须分开：**

| 情况 | 返回 |
|---|---|
| 连不上 sidecar | `Err`，提示怎么启动 |
| 连上了但没配邮箱 | `Err`，提示配置文件在哪 |
| 配好了但取不到 | `Err`，**转述 sidecar 的原话** |
| 取到了，真的没有未读 | `Ok` + 空列表 |

前三行都是 `Err`。**把它们压成"空列表"就是让故障伪装成安静**——
而安静是使用者最不会去查的状态。

### D23. 只读信息源：靠协议保证，不靠自觉

**决策：** 邮件信息源**只读**，且"只读"由三件可检查的事保证，而不是靠注释里
的一句承诺：

1. **用 `EXAMINE` 而不是 `SELECT`。** 这是真实协议测试逼出来的：
   `imaplib` 的 `select(readonly=True)` 在线上发的就是 `EXAMINE`——IMAP 里
   `SELECT` 的只读变体。**之后服务端会直接拒绝任何写操作**，
   这是协议保证，不是我们的承诺。所以命令白名单里只放 `EXAMINE` 不放
   `SELECT`（没有只读保证的读模式选择不该有入口），也不放 `CLOSE`
   （读写下会 expunge）。
2. **读正文一律 `BODY.PEEK[]`，绝不用 `BODY[]`。** 后者会**顺带把邮件标成
   已读**。一个"只读"的信息源把使用者的未读邮件变成已读，比读不到更糟。
3. **假 IMAP 服务器真的实现 `\Seen` 语义**，测试回头查标志位——
   「只读」由**服务端**验证，不是靠我们自觉。

**为什么走 Python sidecar：** MIME 解码是无底洞（中文邮件可能是
GB2312/GBK/UTF-8，邮件头要按 RFC 2047 解，multipart 会嵌套），
Python 标准库这些都做了；零新依赖；与决策模型 sidecar 同构。
**而且 Rust 侧永远看不到邮箱密码**——少一处传播就少一处泄露。

**明文 IMAP 只允许连回环**（为了能连本机服务器、以及让整条链路可测），
非回环强制 TLS，由程序强制而不是靠使用者记得。

**复用决策层的约束：** 回环 HTTP 客户端是共用的，于是**"只允许回环"这条
安全约束白拿**——决策 state 和邮件内容都是私人信息。加一个新 sidecar
就自动拿到这条保证，比每个 sidecar 各写一份客户端可靠得多。

### D24. 打扰判定复用陪伴层的三层，不另造一套

**决策：** `triage` 模块**复用** `companion` 的 `Intervention`
（Speak/Hold/Quiet）与 `constraint_ceiling`，只加邮件特有的那一层。

**理由：** `companion` 已经把"何时介入"做成了三层（模型判断 → 确定性约束
只能收紧 → Speak/Hold/Quiet）。`triage` 是**同一个问题的另一个触发源**——
那边由关系状态触发，这边由一条外部信息触发。两套词汇描述同一件事，
迟早会漂移。

**三层，顺序不能反：**

```text
1. 确定性规则（不花钱）：黑名单 → 白名单 → 验证码 → 群发 → 机器发件人
2. 本地 Verdict（免费、离线）
3. 保守兜底：Hold（不是 Speak，也不是 Quiet）
```

**顺序反了就是"为了省钱先花钱"**——邮件一天几十封，每封问一次模型
就是几十次调用。有测试断言确定性路径 `used_model == false`。

**兜底选 `Hold` 是有理由的：** `Speak` 会乱吵你，`Quiet` 等于把信息扔了。
**`Hold` 是"不打扰"和"不丢失"之间唯一同时成立的选择。**

**约束层对确定性规则同样生效：** 使用者说"现在别打扰我"时，
一条确定性规则也不能绕过去（凌晨三点收到验证码也只攒着）。

**发件人匹配必须有边界：** `@company.com` 要能命中
`a@company.com`，但**不能**命中 `a@evil-company.com`——后者是经典的前缀
伪造。和工具审批里 `docs.rs` 不该命中 `docs.rs.evil.example` 是同一个洞。

**显示名匹配是可伪造的**（发件人自己填），所以它是三档里最弱的一档，
文档与测试里都写明"精确形式优先"。

### D25. 反馈回写：两处都要落，缺一不可

**决策：** 使用者对一条通知的处置要同时落**台账**与**策略文件**。

| 落到哪 | 有什么用 |
|---|---|
| 台账 | 事后能说清这条规则**是谁在什么时候为什么加的** |
| 策略文件 | 下一次判断**真的会用它** |

只写台账不改策略 = **记了不做**。只改策略不写台账 = **做了但说不清来由**
——三个月后你会盯着 `block_senders` 里一条 `@x.com` 想不起为什么。

**四条刻意的设计判断：**

1. **只有"以后别烦我"改策略。** "已读"和"忽略"只记台账——忽略一封不等于
   永远不想看这一类，混起来会让系统悄悄越走越窄，最后什么都不告诉你。
2. **默认只屏蔽这一个发件人**（不是整个域名）。对着
   `noreply@shop.example.com` 的促销说"别烦我"，你多半不想因此收不到
   这家公司的发货通知。想扩大范围要显式说明。
3. **没有"屏蔽所有群发"这种选项。** 那类规则看起来方便，但使用者说那句话时
   心里想的是**具体的一封**，把他的意思扩大到一整类是在替他做他没做的决定。
4. **规则建在"当时那条"上，不重新联网取。** 两个理由，第二个更重要：
   不用联网（sidecar 没起来时这句话仍该生效——那正是最想说它的时刻）；
   重新取有可能取到同一 UID 的更新版本，于是规则建在了**另一条信息**上。

**"以后别烦我"会把冲突的白名单规则摘掉。** 不摘的话策略文件里留着一对
自相矛盾的规则——行为上黑名单赢，但下次看这个文件的人不知道哪条算数。

### D26. 常驻驱动：启动时的一次失败不许决定长期行为

**决策：** daemon 每一轮推进整条助理链路，**不依赖任何人工命令**；
信息源的健康状况**每轮重探**，且**只在状态变化时打印**。

**这条是端到端测试逼出来的，而且抓到了两个真 bug：**

1. **最初在启动时探一次健康，探不到就把通道永久关掉。** 后果是
   "sidecar 还没起来"变成了"这个守护再也不看邮件"。对一个要跑几天的进程，
   **任何"启动时的一次失败决定长期行为"都是错的。** 现在每轮都探，
   好→坏、坏→好时各打印一次，既不刷屏也不会永久失能。
2. **助理回合被包在 `if let Some(engine)` 里，而引擎只在 `--agent` 时创建。**
   后果是"只开助理不开陪伴"时引擎是 `None`，助理回合被**静默跳过**——
   启动日志说"信件：每 2 秒看一次"，然后跑了 25 秒一封邮件都没发现。
   现在只要有**任一**功能开着就建引擎。

**`already_seen` 在常驻场景下不是优化，是正确性。** 手动跑一次重复通知
只是烦一下；daemon 每轮都跑，没有这条记忆就意味着**同一封邮件被反复通知，
直到你把它读掉**。而"攒着的"（`Hold`）**不算通知过**——攒着的意思就是
"以后再说"，跳过它们会让攒着的东西永远不再被提及。

**按时间而不是按轮数触发巡览。** 轮数会和 `--interval` 耦合，
`--interval 1000` 配"每 5 轮"就是每 5 秒登一次 IMAP——那不是勤快，
是在撞服务端的连接频率限制。

**无事发生时不刷屏。** 每 5 分钟打一行"没有新邮件"，代价不是难看，
是**你会开始不看它**——然后真正重要的那行也被漏掉。而"这一轮没看全"
（`skipped > 0`）必须说出来：**一个助理说"没有新邮件"而其实有 3 封没读到，
比它不说更糟**——你会因此不再自己去看。

**每日打扰配额从台账数，不另存计数器。** 另存一个就有了两个真相，
而它们迟早不一致——那时"今天到底打扰了几次"就没有答案了。
演练模式的通知不占额度（它没到你眼前）。

### D27. 一份实现，两个调用方

**决策：** 助理链路的核心逻辑放在内核的 `assistant` 模块，
`yunxi-bot check`（你主动问）与 daemon 的每一轮（它自己看）**共用同一份**。

**抄两份的话两边迟早漂移，而漂移的表现最恶心：手动跑没问题，常驻跑就出问题**
（或者反过来）。那类 bug 极难查，因为你**会相信"我刚刚手动跑过是好的"**。

同一条纪律也适用于数据目录：`default_home()` 曾经在 CLI 里有一份、
Python sidecar 里又有一份。端到端测试抓到过一次真实的路径不一致——
表现是 sidecar 说"没配置"、而使用者的配置文件明明就在那儿，
**那是很难查的一类错**。修法不是"让两边神奇地一致"（不可靠），
而是**让不一致可被看见**（sidecar 报出自己算的 `config_path`，
Rust 侧发现不同就直接把两个路径摆出来），同时把源头收敛成一份。

### D28. 端到端脚本必须先重建二进制

**决策：** 所有端到端脚本调 `ensure_fresh_binary()`，
在跑之前**主动 `cargo build`**，绝不退回用旧的。

**理由是一条实践中的陷阱：`cargo clippy` 和 `cargo test` 都不刷新
`target/debug/yunxi-bot.exe`**——它们各自产出自己的中间物。

于是有这样的假结果：改完代码跑 `clippy`（干净）+ `test`（全绿），
接着跑端到端，**实际验的是上一次 build 的旧二进制**。结果要么假通过，
要么报一个已经修掉的 bug——**两种都会让人往错的方向查**。

这个坑真踩过一次（`NoticeSent` 缺字段的 bug 明明修了，端到端却还在报旧行为）。
多花十几秒重建，比一个假结果便宜得多。


MCP 的调研结论见 [`docs/工具层调研与设计.md`](../工具层调研与设计.md)，含：
当前规范版本是 `2026-07-28`（Roots 与 Sampling 已弃用）、官方参考 server
只剩 7 个（sqlite/puppeteer/slack/postgres 已归档）、以及联网检索方案的实测结果。
### D29. 任务推进：守护自己把没人管的任务接下去

**决策：** daemon 每一轮看一眼待办，把**安静够久、又不需要人介入**的任务推进下去。
在此之前任务只能由 `yunxi-bot do` 同步跑完——进程被杀、或跑到「等人工」之后，
唯一的推进方式是人在终端敲 `resume`。**那正是 goal 开头点名的第一条断链。**

**两条边界，都写在 `task::schedule` 里：**

1. **不碰 `AwaitingHuman`。** 自动续跑它**等于自动批准**，而那正是审批门禁
   存在的理由。这类任务只会被**报出来**（`attention_needed`），不是替他做决定。
2. **不碰刚刚还在动的任务。** 使用者在终端里跑时守护也在看同一本台账，
   没有这道闸两边会同时执行同一批步骤——而步骤可能有副作用。
   所以候选必须已经安静了 `--task-idle`（默认 120 秒）。

这不是"乐观锁"，是承认一件事：**没有租约机制时，时间是最简单的互斥手段**。
真要做并发控制，该由台账上的租约事件承担，而不是在这里假装做到了。

**无人值守 = 不获得新权限。** 守护构造的审批者是 `RefusingApprover`：
凡是需要批准的动作一律拒绝。守护拿不到 stdin（用 `StdinApprover` 会直接卡死），
而"自动批准"更不可接受——那等于让一个无人看管的进程自己给自己发权限。
**所以守护能做的事 = 使用者在 `--allow` 里预先写明的那些。**
其余一律失败并留痕——**失败是正确结果，不是缺陷**。

**"推不动"和"在等人"都必须报出来。** 一个卡住的任务如果只是静静躺在台账里，
使用者不会主动去查（`--console` 之外还走通知出口）。同一个任务只提醒一次
（`TaskAttentionNotified` 去重）——反复报同一件事会让噪音淹没真信号。

### D30. `Ledger::events()` 是快照，不是实时视图

**决策：** 明确 `events()` 的语义为**快照**，多写入者场景下读状态前必须
调 `Ledger::reload()`。

**这条是端到端测试抓出来的。** 同一个进程里可以有两本 `Ledger` 指向同一个
文件（任务 store 一本、工具调用记录一本、调用方自己一本）。**别人写的不
会出现在你的 `events` 里**——你只看得见"开台账那一刻读到的"加上"你自己写的"。

后果很隐蔽：守护每轮读状态做决策，而任务引擎在另一本台账上写状态。
于是守护**永远看不到引擎写的状态**，每轮都按最初那份快照决策——
一个已经 `Stalled` 的任务被无限重试。日志里的样子是同一个任务每轮都
"卡住"一次，而状态事件真的在台账里写着 `stalled`。

**这与 D31 是同一类问题的两个面**：一个是读（`events` 快照），
一个是写（`seq` 落后）。两者都源于"同一个文件被多本台账打开"。
修法也一样：不靠约定，靠**显式动作**（`reload()` / `sync_seq_from_disk()`）。

### D31. 端到端测试也会骗人：断言必须先证明它是活的

**决策：** 一条端到端断言如果没有"让它失败"的可能，就不算验证。

**两次踩到同一个坑：**

1. "不重复打扰"那条断言最初跑在**演练模式**下。而演练模式的通知按设计
   不算"已告知过"（不然跑一次演练就把邮件永久吞了）——于是那条断言
   比的是**两组空集合，永远相等**。改成真通知才是在测。
2. "守护不重复接手任务"最初只断言"没有新事件"，而它恰好也能因为
   **守护根本没跑起来**而通过。

所以现在的做法是：**每条断言旁边都有一条前置断言**（"有真的通知记录"、
"有多轮 Infofetched"），先证明这条链路是活的，再断言它做对了事。
一个虚空通过的测试比没有测试更糟——**它会让你以为那里被守住了**。

### D32. MCP 落地：rmcp 3.5.1，以及三条从实现里长出来的约束

**决策：** 按 D20 接 `rmcp` 的 stdio 客户端，内核保持同步。
实现过程中量到、撞到的东西记在这里。

**版本选择是量出来的，两条路代价几乎一样：**

| 路线 | 包数 | 构建 | 代价 |
|---|---|---|---|
| rmcp 2.2.0 + `rust-version = 1.85` | 67 → 105 | 19s | 协议库停在旧大版本 |
| **rmcp 3.5.1 + `rust-version = 1.88`** | 67 → **104** | **16s** | 声明门槛抬 3 个小版本 |

选后者：**更新、还更便宜**，而 MCP 规范变化很快，为一个新集成钉在旧大版本上
没有道理。`cargo add` 会自动退回 2.2.0（因为 `rust-version = 1.85` 挡住了
3.5.1），所以这是个**必须显式做的决定**，不能让它悄悄替你选。

**连带后果，也一并承担：** 抬到 1.88 之后 let-chains 稳定了，clippy 在整个
代码库上启用了 `collapsible_if`，19 个文件冒出建议。项目规矩是不加
`#[allow]`，所以用 `cargo clippy --fix` 全部修掉（690 个测试改后仍全绿）。
**这是抬版本门槛的真实代价，不该假装它不存在。**

**三条从实现里长出来的约束：**

1. **`Capability::Unknown`——新增一个能力类别。**
   D20 写的是"能力默认未知"，但当时没有这一类，只有五个"已知"的。
   而挑一个最像的（比如 `Execute`）等于**把 server 的自称当成事实**：
   它说自己只读，我们没有任何办法核实。
   所以新增 `Unknown`：不享受只读自动放行、**不接受模型判定**（和
   `Outbound` 同一条路）、只有使用者显式写的 allow 规则才能预批准。

2. **server 名不允许含 `__`——这是 `__` 分隔符能成立的前提。**
   `qualify("a", "b__c")` 和 `qualify("a__b", "c")` **会拼出同一个工具名**。
   我原本以为用 `__` 做分隔就够了，是测试当场抓到的。
   工具名那一侧管不了（那是别人定的），所以只能约束 server 名，
   由 `validate_config` 强制。

3. **配置校验必须前置。** 最初散在 `connect_one` 里，于是有个真实的坑：
   某个 server 起不来时它不会被加进已连列表，**重名检查就看不到它**——
   两个都叫 `same` 的 server 各报一句"程序找不到"，而真正的问题
   （重名会让工具名撞车）一个字都没提。

**实现上的两条判断：**

- **子进程不继承父环境**，只给配置里显式写的那些（外加 PATH 等几个
  没它就没法跑的）。继承会把我们的 API key 交给一个第三方进程——
  和 `exec` 剥离凭证环境变量是同一条纪律。
- **MCP 工具接成普通 `Tool`**，走**同一条**审批与留痕路径。
  给它另开一条执行路径的话，那条路径迟早会绕开审批门禁、台账或沙箱，
  而"另开一条"本身就是洞的来源。

**验收（真的连了第三方）：** 用官方参考实现 `mcp-server-time`
（`uvx` 拉起，stdio 传输）——真的握手、真的列出 `get_current_time`、
**真的调通并拿到真实时间**，且 `yunxi-bot tools` 里显示为"能力未知 / 否（要问人）"。

### D33. 交互式会话：通用 agent 的第一块地基

**决策：** 加 `yunxi-bot chat`——一个真正的 REPL，会话**跨进程存活**。

**为什么这是第一块地基。** 在此之前只有一次性命令：

```text
yunxi-bot do "改一下 X"     ← 跑完就退
yunxi-bot do "再改一下 Y"   ← 完全不知道上一句
```

那不是对话，是"发命令—等结果"。而通用 agent 的价值有一大半在
**上下文延续**上：你说了"这个文件"，下一句的"它"才有指代对象。
`ChatHandler` 里 `sessions: BTreeMap<SessionKey, PromptLayout>` 这套机制
早就写好了，缺的只是一个**让它活下去的循环**。

**三条设计约束：**

1. **走同一个 `converse`。** 工具循环、审批门禁、台账留痕、缓存前缀
   全都不变。**另起一条轻量路径的话，那条路迟早会绕开审批。**
2. **每轮落盘，不是退出时才存。** 退出时才存意味着一次崩溃（或 Ctrl+C）
   丢掉整场对话——而"丢失"在这里尤其难接受：**你刚解释完背景。**
   写盘用"先写临时文件再改名"：直接覆写时写到一半被杀会留下半个 JSON，
   下一次载入报"不可解析"，**整个会话就废了**。
3. **审批照常问人。** REPL 里有人在，所以用真审批者；答 `n` 就是拒绝，
   走的是和别处一样的 `GateDecision::Deny`。

**会话 id 是安全边界。** id 会被拼进文件路径，所以只允许字母数字和 `-` `_`
——`../` 能让"保存会话"写到数据目录外面去。拒绝发生在拼路径**之前**。

**对话用固定的会话键，不按 provider 分。** 使用者的对话是**一条**，
不该因为这一轮路由到了另一个模型就断开——那会让"刚才说的那个文件"
突然变成对不上话的悬空指代。而任务引擎那三条（Plan/Step/Options）
按 provider 分是对的：它们是不同的角色，交叉用同一个历史反而
会让提示词和内容对不上。

**稳定前缀提前算好（`chat_prefix`）。** 载入会话时要拿它和存档里的指纹比，
而"先建会话再比"会覆盖掉存档里的指纹，于是每次都报"前缀变了"——**假警报**。

**前缀变了不丢历史。** 保留历史、换用新前缀、如实报告。
丢弃是过度的（使用者会莫名其妙"失忆"），静默换前缀则会让使用者
以为缓存还在命中，然后对账单感到困惑。

**斜杠命令不进模型。** 理由很简单：如果交给模型，它就得猜"退出"是什么意思，
而猜错的表现是它试图调用一个不存在的工具。

**验收（真机）：** 三轮对话里第三轮能说出第一轮埋的词；退出后
`--resume` 起一个新进程，那个词还在；会话落盘有 turns/历史/前缀/指纹；
`chat list` 能列出来。

### D34. 上下文预算与压缩：把缓存损失摊薄到"每次压缩一次"

**决策：** 历史不再只增不减。引入 `ContextBudget` + `ContextUsage` +
`PromptLayout::compact`，超预算时把最老的一段换成摘要。

**为什么这条是"做错了比不做更糟"的。** 缓存纪律要求前缀逐字节稳定
（实测命中便宜 50 倍），而压缩天然要改前缀。所以设计必须做到
**把缓存损失从"每轮一次"摊薄到"每次压缩一次"**：

```text
[稳定前缀] [摘要] [近期消息……] [本轮问题]
           ^^^^^^ 两次压缩之间一个字都不变
```

摘要一旦生成就固定，后续只往后追加。于是压缩后第一轮未命中一次，
之后每轮命中，直到下一次压缩。

**token 怎么数：精确锚点 + 增量估算。**

**不靠纯估算蒙**——每次 API 响应里的 `usage.prompt_tokens` 是
"我们实际发出去多少 token"的精确值。所以：

```text
上一次响应报告的真实值（精确）
  + 自那以后新增内容的字符数 ÷ 每 token 字符数（估算，逐轮自我修正）
```

这个设计的性质：**估算误差不会累积**。每次响应把锚点拉回精确值，
最坏情况是"两次响应之间估偏一点"。`ContextUsage::is_exact` 如实报告
"我知道它多大"还是"我在猜"。

每 token 字符数取 2（中文约 1 字 1 token，ASCII 约 4 字符 1 token）。
**宁可高估**：高估只是早一点压缩，低估会撞上限。

**四个实现约束：**

1. **切割点不能劈开工具调用序列。** 丢掉带 `tool_calls` 的助手消息、
   却留下它的工具结果，服务端报 400——而错误指向"缺少 tool_call_id"，
   看起来像工具坏了。所以切割点要往前退到第一个不是 `Role::Tool` 的消息。
   **切错的代价（对话直接坏掉）比超限的代价（报错）更糟**，所以退到 0
   就如实放弃，不硬切。
2. **至少留住最后一轮交换。** 压掉它等于让模型失去眼前上下文，
   那比超限更糟——它会开始问你已经说过的事。
3. **`keep_recent` 是偏好，不是下限。** 最初的写法是
   `len <= keep_recent 就不压`，于是"消息不多但每条很大"的会话
   永远压不了，然后直接撞上限。**这个 bug 是端到端测试抓到的。**
   现在超预算就必须让出空间，且至少砍掉一半（只砍一两条毫无意义，
   而每次压缩都意味着一次缓存未命中）。
4. **压缩不能失败，但失败必须可见。** 摘要调模型；失败退回
   `DropMarker`（信息有损，但对话能继续）。**失败原因要留下来**——
   最初它被静默吞掉，三次压缩全是兜底而日志一个字没提，
   使用者的感受是"它怎么不记得了"，无从追查。

**摘要也要走限流等待（D17 的又一次应用）。** 压缩发生在对话中途，
而那时往往正好卡在 Agnes 10 RPM 上——绕过等待直接调，摘要必然被
限流打掉，于是每次都退兜底。**这个也是端到端测试抓到的**：
修之前 4 次压缩 0 次模型摘要，修之后 4 次全是。

**压缩必须留痕**（`ContextCompacted`）：丢了多少条、多少字、多少次工具调用、
省了多少 token、**摘要是不是模型写的**。最后一位很重要——
有损压缩和模型摘要在事后追查时是完全不同的两条线索。

### D35. 项目规则加载：通用 agent 的分界

**决策：** 从 cwd 向上找 `AGENTS.md`（兼容 `CLAUDE.md`），读进**稳定前缀**。

**为什么这条是分界。** 通用 agent 的价值恰恰在"换个项目直接能用"。
在此之前它不知道这个项目该用哪个测试命令、目录结构什么意思——
每次都要使用者在提示词里重说一遍。

**两个必须先定清楚的问题：**

**一、向上找到哪里停。** 从 `C:\Users\你\Desktop\foo` 出发往上走，
不设条件会把 `Users\`、`C:\` 下面不相干的文件也读进来。规则是：

1. **遇到含 `.git` 的目录，读完它就不往上找了**——那是项目边界，
   项目外面的东西不属于这个项目。
2. 到文件系统根为止（没有 git 仓库时）。
3. 深度硬上限 12 层，数量上限 8 份。

**二、优先级。** 顺序是**从远到近**：用户级（`<数据目录>/AGENTS.md`）
→ 项目根 → 逐级向下 → cwd。越靠后越具体，而
**模型读到最后说的那句印象最深**——和人类看"通用规范 + 本项目补充"
的顺序一致。

**每份规则都带来源路径。** 不标来源的话，模型说"按项目约定应该……"
而你无从知道它指的是哪一条；出了错也追不回去。

**同目录两份都在时 `AGENTS.md` 优先**：它更"通用"，而 `CLAUDE.md`
通常是给别的工具准备的。

**实现上的四个细节：**

- **BOM 要剥掉**：留在前缀里会让首行变成 `\u{feff}# 标题`，
  模型看到的是个乱码开头的标题。
- **超 32KB 截断并说明**：一份 200KB 的 AGENTS.md 塞进前缀会把
  缓存和预算一起毁掉，但"它被截断了"这件事必须说出来。
  截断要按**字符边界**——按字节切会把汉字劈成两半。
- **没有规则时不拼空段**：那会平白占掉前缀的 token，还每轮都一样地占。
- **读一次就定下来**：规则进稳定前缀，中途变会让缓存全废。
  cwd 变了导致的差异由 `PrefixMismatch` 处理（保留历史、换新前缀、如实报告）。

**一个差点查错方向的坑。** 调试时规则加载正常、`/rules` 列得好好的，
**而模型说"系统提示词里没有这一节"**。差一点就去查模型——其实是
**"加载了"和"真的进了前缀"是两件事**。

所以现在 `/rules` 会输出一行机器可验证的接线断言：

```text
稳定前缀 920 字；规则已进前缀：是
```

**端到端因此分两层**：第一层断言接线（确定性，不看模型脸色），
第二层断言模型确实用得上（在一个只有一个规则文件的干净项目里，
问一条**靠常识绝不可能猜到**的约定）。分开的理由：
混在一条断言里，失败时你不知道该修哪边。

**「让模型复述自己的系统提示词」是个坏测试** —— 模型不擅长这个，
它那次说"不存在这一节"其实是问法的问题。换成"这个项目用什么命令构建"
就答对了。**测行为，不要测自省。**

### D36. 并行工具调用：判定串行，只读并行

**决策：** `ToolRunner` 把"判定"和"执行"拆开。判定（门禁 + 问人）**永远串行**，
执行时**连续的只读调用并行**，其余串行。

**为什么判定必须串行。** 审批者是一个 `&mut`，同时问它没有意义；
更重要的是那是人的现实——**同时弹三个审批框，使用者根本不知道
自己在批哪一条**。

**为什么只有只读能并行（三条理由）：**

1. **并行写同一个文件是灾难。** 两个 `write_file` 同时改一个文件，
   结果取决于调度——而那种不确定性事后完全无法复现。
2. **有副作用的调用之间有隐式依赖。** 模型可能在一次里既建目录又写文件，
   并行就会让写文件先跑而失败。
3. **`Network` 也不并行**：搜索和抓取有各自的限流，并发打过去只会更快
   撞上配额——这和任务层"限流器是共享状态"是同一条理由。

**实现要点：**

- 用 `std::thread::scope` 而不是 spawn：**作用域线程能借用栈上的东西**，
  而 spawn 要求 `'static`，那会逼着把工具和参数都拷一遍。
- **每个线程一份自己的 `ToolContext`**（不然没法并行），跑完把
  `read_files` 并回主 ctx——**"先读后写"这条规则不能因为走了并行路径就失效**。
  漏了的话，模型读了文件再改会被拒，而报错说"还没读过"，
  看起来就像它没读。
- **结果顺序不变**：工具结果要按模型请求的顺序回灌，
  否则模型会以为结果和调用对不上。
- 工具 panic 只影响它自己那一条，**不把整个循环带走**。
- 只有一个只读调用时不走并行——**没有收益，还要多付线程开销**。

**"并行"必须可证。** 本地文件读得太快（2-4ms），光看总耗时看不出并行的
痕迹——串行 3 个 4ms 是 12ms，并行也是 4ms 出头，噪声比信号大。
所以 `ToolCallRecord` 增加 `started_at_ms` / `duration_ms` 并进台账：
**两个调用的区间相交就是并行最直接的证据**（串行时区间永远不可能重叠）。

真机证据：

```text
同一批 3 个读，3/3 对区间相交
  read_file  +0ms  耗时 2ms
  read_file  +0ms  耗时 2ms
  read_file  +0ms  耗时 2ms
```

### D37. 服务端 429 也要等，不只是本地限流

**决策：** `retry_throttled` 从"只等本地限流"扩展成"等所有可重试的错误"。

**这是 D17 那条教训第三次以新面孔出现。** 本地限流器说等多久就等多久，
而**服务端的 429 直接判失败**——两者是同一件事。

发现过程很说明问题：十个端到端脚本连着跑，后面几个开始报"这一轮失败了"，
**单独跑每一个都过**。差一点就去查限流参数了——其实是产品没重试 429。

现在按错误类型退避：

| 错误 | 等多久 |
|---|---|
| `LocalThrottle` | 本地限流器说的时间 |
| `RateLimited`（429） | 服务端 `Retry-After`；没给就按轮次退避 |
| `Transient` / `Network` | 短退避 |
| `Auth` / `Payment` / `Forbidden` | **不重试**（重试只是浪费时间和配额） |

修好之后，**十个脚本一次性连跑全部通过**——修之前做不到。
这既是修复的证据，也反过来确认了病因判断是对的。

### D38. diff 预览：批准之前先看后果

**决策：** `Tool` 增加 `preview(&self, args, ctx) -> Option<String>`，
`ApprovalRequest` 增加 `preview` 字段，审批框变成"先给后果，再给参数"。

**为什么。** 在此之前审批框显示的是工具参数的 JSON：

```text
│ 参数      : {"new_string":"新的这一行","old_string":"旧的这一行","path":"notes.txt"}
```

**那是参数，不是后果。** 而项目自己在 `specifier` 的注释里写过同一条担忧：
「审批提示上显示的是 `notes\a.md`，而工具真正动的是 `<cwd>\notes\a.md`
——**人在批准一个自己没看清的东西**。」

现在：

```text
│ 动的是    : D:\...\work\notes.txt
│ 会变成    :
│   要改 notes.txt（加 1 行、删 1 行）：
│       第一行
│     - 旧的这一行
│     + 新的这一行
│       第三行
│ 参数      : {...}
```

**顺序是有意的**：人读审批框是从上往下的，读到能判断"批不批"就该停下。
参数 JSON 是给"想再核对一眼"用的，不是判决依据。

**和 `specifier` 是两件事：** 前者回答"动的是哪个东西"（匹配规则用），
后者回答"**它会变成什么样**"。

**自己写 diff 而不引依赖（`similar` 等）。** 理由：只要行级 + 少量上下文
这一种输出，不需要字符级和各种格式；依赖纪律是先量代价再引。
所以用 LCS 动态规划，几十行，能被测试完全覆盖。

**四个实现约束：**

1. **默认返回 `None`。** 读取类工具没有"后果"可言，硬塞预览只会让
   审批框变长、让人更不想读——而"不想读"正是这套机制要防的事。
   没有预览时**如实说"这个工具没提供预览"**，而不是让人以为
   下面那串 JSON 就是后果。
2. **实现必须只读。** 它在真正执行之前被调用，自己不能有副作用——
   否则"看一眼"就等于"改一下"。
3. **`replace_all` 要如实算。** 只算一处的话**预览会骗人**：
   人看到"改 1 行"就批了，实际改了 5 处。
4. **只留改动附近几行。** 一个 100 行的文件只改一行的话，
   人要在 100 行里找那一行。远处的用 `@@ 跳过 N 行 @@` 说明——
   不说明的话上下两行看起来像是挨着的。

**真机验证**：`edit_file` 的审批框里出现了
`- 旧的这一行 / + 新的这一行` 和上下文。

### D39. 流式输出，以及一个"能用但不对"的 bug

**决策：** `Thinker` 增加 `think_stream(req, on_delta)`（默认实现退化成
一次性），`OpenAiThinker` 实现真 SSE，REPL 逐字显示。

**先说实测过的前提。** Agnes 支持 `stream: true` +
`stream_options.include_usage: true`，**最后一个 chunk 带 `usage`**
（实测 `prompt_tokens: 84`）。这一点必须先确认——上下文锚点全靠
`prompt_tokens`，流式如果拿不到它，压缩就退化成纯估算。
**先实测再实现，不是假定。**

**"并行"那条教训在这里重演：可见的功能需要可证的证据。**
捕获下来的输出**看起来和不流式一模一样**——都是那段文字。
所以证据只能来自时间：

```text
首段 +0.61s：'#'
末段 +4.17s
首末差 3.56s
```

不流式的话首末差接近 0（整段在同一个时刻到达）。

**抓到的 bug：中间层漏转发一个方法，静默改变了行为。**

主链路把 thinker 包在 `MeteredThinker` 里（负责限流等待和用量记账）。
它一开始只实现了 `think`，于是 `think_stream` 落到 trait 的**默认实现**上：
**等整段答完再一次性交出去**——流式在外层被整个吞掉了。

这个 bug 极难发现：功能"能用"（正文照样出来、工具照样调），
只是不再逐字显示。

定位过程值得记下来：

1. 端到端显示"2 批到达、首末差 0.00s"，但只跑过一次，证据不硬
2. 再跑一次变成"5 批、18.86s"——**两次矛盾**，说明证据不可靠
3. 于是**隔离**：写一个探针直接打 API，给每个 chunk 打时间戳
4. 探针显示 provider 确实在流（**304 个 chunk 跨 2.6 秒**）
5. 结论：问题在我们这边 → 顺着调用链找到 `MeteredThinker`

**修之后：209 批到达、首末差 3.56s。** 差别一目了然。

**顺带修的两件事：**

- `MeteredThinker.inner` 从 `Arc<OpenAiThinker>` 改成 `Arc<dyn Thinker>`
  ——用具体类型的话，"这个 wrapper 有没有转发 `think_stream`"
  **根本没法用替身测**，而那个 bug 正是漏转发造成的。
  **不能测的地方就是会长 bug 的地方。** 现在有两条回归测试盯着它。
- **Python 的管道缓冲会把时间戳抹平。** 第一版用 `readline()` 读子进程输出，
  结果所有行在进程退出时一起交付——看起来像"一次性出来的"。
  改成 `os.read` 按字节读，拿到的才是真实到达时刻。

### D40. 对话的成本也要进台账

**决策：** `chat` 每轮把 `records` 写进台账（`ModelCalled`）。

**发现方式：** 端到端查 `model_called` 事件时发现 `chat` 路径一条都没有。
而 `records` 是被收集了的——只是没人写。于是**对话的成本在台账里
完全隐形**：`yunxi-bot cost` 少报，缓存命中率也测不到对话这条链路。
**"成本看不见"是最容易被忽略、也最容易失控的一类问题。**

**放在 `match` 之外**：失败的调用也是调用（它照样花了 token，
有些还花了钱），漏掉失败的那些会让账单对不上。

**同样暴露的一个测试坑：** 第一版 E2E 查的是 `data.prompt_tokens`，
而 `Usage` 是**嵌套**的（`data.usage.prompt_tokens`）——于是永远读到 0，
差一点就去查"流式是不是把 usage 丢了"。**测试读错字段，
会把你送到一个不存在的问题前面。**

**D38 补充：预览最大的价值是"发现这次编辑是白问的"。**

端到端测试又抓到一个：模型发来的 `old_string` 里是字面量 `\r\n`
而不是真的回车换行，于是它在文件里一个都找不到，`call` 必然失败。
而预览当时说的是**"内容没有变化"**——人看到那句会以为
"没什么可批的"，**而实际是"批了也会失败"**。

这是两件完全不同的事，混在一起会让人做错决定。所以现在分三种情况：

| 情况 | 预览说什么 |
|---|---|
| `old_string` 一次都找不到 | **"文件里找不到这段内容，这次编辑会失败"**，并把想找的内容前 3 行显示出来 |
| 出现多次而 `replace_all` 没开 | **"出现了 N 次，这次编辑会失败"**，并给出下一步怎么办 |
| 能成 | 正常的 diff |

**预览最大的价值正在这儿：在问人之前就发现这次编辑是白问的。**
`edit_file` 最常见的失败模式就是"找不到"，而在此之前，
人要批准之后才知道失败——那时候模型已经拿到"被拒绝"的信号，
会去尝试别的写法（实测它立刻改口说"那我用 write_file 整体覆盖"）。

### D41. 回环地址的连接超时：2000ms 比 Windows 报拒绝还慢

**决策：** 回环地址的连接超时单独设成 300 ms，并把"没人监听"和"超时"
分成两句不同的话。

**这是接真实 Gmail 时量出来的。** Windows 上连 `127.0.0.1` 一个
没人监听的端口，内核要**约 2070 ms** 才回"积极拒绝"（实测）。
而决策客户端的默认超时是 2000 ms——**于是先超时了**：

```text
报出来的：决策模型不可用：调用超时
真实原因：没人监听（Verdict sidecar 没起来）
```

**两种原因的下一步动作完全不同：**

| 报什么 | 该去查什么 |
|---|---|
| 超时 | 服务为什么慢 |
| 没人监听 | 服务为什么没起来 |

而且每次白等两秒——一轮 `check` 里那些要走决策层的邮件，
会白等十几秒。**本机服务要么立刻接受，要么就是没起来**，
300 ms 足够区分。

**实测效果：`check --dry-run` 从 28-29 秒降到 21 秒。**
消息也变成了 `127.0.0.1:17870 连不上（回环地址 300 ms 内没接受连接）
——多半是这个服务没起来`。

**同一条教训第三次出现**（D38 的"没有变化" vs "找不到"、
D39 的"调用超时" vs "没人监听"）：**把两种不同的原因混成一句话，
会让人查错方向。** 而这次的代价是实打实的两秒 × 每次调用。

**未解的一条：** `yunxi-bot check` 至今仍报"调用超时"，
而同一个二进制上 `yunxi-bot decide` 报的是新消息。
`DecisionError::Timeout` 只有一个来源（`HttpError::Timeout`），
而 `HttpError::Timeout` 现在只剩"非回环超时"和"读写超时"两条路——
**说明 `check` 那条路上连接曾经成功过**，或者走了另一个客户端。
如实记在这里，没有猜。

### D42. 复杂任务全线失效：DeepSeek 的 `usage: null` 与思考预算

**真实任务测试第一次跑就炸了**（`do "修一个边界 bug"`）：

```text
拆解路由 : deepseek/deepseek-flash
错误: 工具循环失败: 模型调用失败: 响应结构异常: 流结束了，但既没有正文也没有工具调用
```

因为**复杂的任务走 DeepSeek**，所以这一条等于"所有复杂任务都跑不起来"。

**根因一：`usage: null` 让每个 chunk 都解析失败。**

DeepSeek 在**每一个** SSE chunk 里都带 `"usage": null`，只有最后一块是对象。
而我们的结构体是：

```rust
#[serde(default)]
usage: Usage,     // ← null 不是 struct
```

**`#[serde(default)]` 只在键"不存在"时生效；键存在但为 `null` 时照样失败。**
于是每个 chunk 都解析失败 → 被那段"单块解析不了不致命"的静默跳过全丢了
→ 最后报"流结束了，但既没有正文也没有工具调用"。

**这个报错把方向指反了**：看起来像模型没回内容，其实是解析器不认这个形状。
（Agnes 不发送 `usage: null`，所以之前一直没暴露。）

修法两处：`usage` 改成 `Option<Usage>`；**并且把"全都解析不了"和
"模型没回内容"分开报**——记下解析成功/跳过/有 choices 的块数，
以及首个解析错误原文。

**根因二：思考模式的输出预算不够，回复被从中间截断。**

`max_tokens` 是"**思考过程 + 正文**"的总和，不是正文的额度。
实测同一个拆解请求：

| max_tokens | 结果 |
|---|---|
| 512 | 思考 214 token，`finish=tool_calls` |
| 1024 | 思考 541 token，**`finish=length`（截断）** |
| 2048 | 思考 287 token，`finish=tool_calls` |
| 4096 | 思考 431 token，**`finish=stop`** ✓ |

而 `PLAN_MAX_TOKENS = 2048`。截断的回复是 `{"steps":[{"id":"s1",...`——
**残缺的 JSON**。

**根因三：截断被报成"没有 steps 字段"。**

`extract_json` 用括号配对找候选片段。截断时最外层 `{` 没有配对的 `}`，
于是它返回了**内部每个完整的步骤对象**——那些能正常解析，但没有 `steps` 字段。

报出来的是「顶层对象里没有 steps 字段」，**指向完全错误的方向**：
人会去查解析逻辑，而真正的问题是输出预算不够。

修法：`looks_truncated()` —— 文里出现了 `{`/`[`，但从**第一个**开始
找不到配对闭合，就是截断。错误信息里明确说出来。

**修法：`THINKING_OUTPUT_HEADROOM = 2048`，在 `converse` 里统一加。**
放在那里而不是各个调用点：**一处覆盖所有意图**，不会出现"某个意图忘了加"。

### D43. `edit_file` 的"找不到"必须诊断出真正的原因

**同一个任务暴露的第二条链。** 模型放弃 `edit_file`、改用
`run_command` 写 PowerShell 脚本去改文件，**把一个 19 行的文件截成了 1 行**。

起点是一句没有信息量的报错：

```text
在 src/billing.py 里没找到 old_string（匹配 0 次）。
它必须与文件内容逐字符一致，包括缩进和行尾；建议先 read_file 看一遍原文再改
```

"包括行尾"等于没说——模型不知道**差在哪**，于是开始乱试，
试了几次之后升级到用脚本绕开。

**诊断出"你用的是 LF、文件是 CRLF"之后，模型一步就能改对。**

`diagnose_miss()` 只报**能确证**的原因，每种都实际验证过
"改掉这一点就能匹配"：行尾不一致（CRLF/LF 两个方向）、
行尾空白差异、以及都说不出时的可操作下一步。
**猜错比不说更糟**——模型会照着改，然后还是失败。

### D44. 人工介入是一条死路（未修，先记下）

同一个任务还暴露了第三个问题，比前两个更严重：

拆解正确地把「满减在金额恰好等于阈值时该不该触发」标成了 `decide:` 步骤
（这是**对的**——那确实需要人拍板）。但任务停下等人之后：

```text
$ yunxi-bot resume <id>
仍在等人 : 决策模型弃权：步骤 s4 需要人工判断…；候选 = [opt0..opt5]
```

**`resume` 只是把状态放回 `running`，没有接收人的答案。**
于是 s4 再跑一次、再弃权、再停下——**死循环**，而且每次 resume
都白花模型调用。

**人给出了答案，而系统没有地方接。** 这是"人工介入"这个机制的
根本缺口：它只能停在人这里，不能带着人的决定继续。

修法（下一步）：`resume <id> --answer "<人的决定>"` 落一条台账事件，
引擎遇到 `decide:` 步骤时先查有没有人已经答过。
