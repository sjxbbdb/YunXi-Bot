# Gemma + Laya 任务链路验收

2026-10-15，在这台 Mac 上使用真实本地权重和 Rust CLI 验证。

链路为：目标 → Gemma 拆解依赖步骤 → 工具取得证据 → Gemma 生成候选方案 →
Laya 根据原始证据选择 → 策略与人工审批门禁 → 工具执行 → 结果与决策写入台账。
决策服务不可用时，决策步骤停下等人；人工答案入账后，`resume` 继续剩余步骤。

## 使用

在项目目录运行：

```bash
./启动.command do "你的任务目标" --provider local
./启动.command tasks
./启动.command tasks <任务id>
./启动.command resume <任务id> --provider local --answer "对当前待决步骤的回答"
```

`--answer` 回答业务选择，不会替代工具审批。只需重试、不需要回答时可省略。
`--provider local` 只作用于本次命令；续跑也要带上。它不能把任务自动回落到云端。
默认复杂任务与 daemon 仍沿用原路由，本次未改为全部本地常驻执行。

## 验收方法

复用已启动的 17870 Laya、17872 Gemma 服务，串行运行：

```bash
python3 sidecar/e2e_local_task.py
```

脚本会重新构建 CLI，使用临时数据目录、临时工作目录，保留原始输入文件，
只预批准目标结果文件的新建。其他写入、命令和联网受原策略与显式拒绝规则约束。
临时目录用于限制测试副作用，不等于 OS 沙箱。

不仅检查退出码，还检查实际文件内容、工具执行记录、模型身份、思考开关、
决策来源、degraded、人工答案和台账重新加载。异常 JSON 行不会被测试跳过。

验收包括：正常四步任务、决策服务失联后人工续跑、拒绝写入、文件不存在、
工作区外只读工具的 Laya 门禁，以及交换选项顺序的六个决策小样本。

## 本轮修复

1. `do/resume` 增加显式本地入口，共用 provider 解析与回落约束。
2. 健康检查从空问题推理请求改为读取 `/health`，消除 Laya 离线误报。
3. 自动思考依据任务需求计算，Gemma 规划与分析可以开启思考。
4. 原始目标和前置证据直接传给 Laya，修复只给方案生成器提供证据的缺口。
5. 修正“写文件只给内容”的执行提示；步骤明确点名工具时，缺少真实成功调用记录会被判为 BLOCKED。

第 5 项不是完整的语义验证器：它不能证明工具参数、目标文件或内容正确；
否定和备选工具表述也可能被保守拦住。自然语言目标仍需要与业务要求对应的验收。

## 实测结果

最终 5 条真实任务链路全部通过，另有 6/6 个 Laya 证据与选项顺序样本通过。

| 场景 | 实际核验 | 用时 |
|---|---|---:|
| 正常任务 | Gemma 拆解 4 步，Laya 选红色，真实写入后再读取核对 | 80.32 秒 |
| 决策失联与续跑 | 先停下、无写入、degraded 留痕；人工答案入账后完成 | 98.46 秒 |
| 策略拒绝写入 | write_file 被拒绝、文件未创建、步骤未报成功 | 24.18 秒 |
| 读取不存在的文件 | read_file 错误入账、未编造文件、步骤未报成功 | 43.49 秒 |
| 工具风险判断 | Laya 判断外部临时样例只读操作可放行，工具实际读取正确暗号 | 36.14 秒 |
| 决策证据矩阵 | 红色/蓝色/满减边界各交换选项顺序，共 6 次均正确 | 非速度测试 |

正常任务最终文件经测试脚本独立检查为：

```text
苹果=3
草莓=4
合计=7
```

上述任务共记录 26 次 Gemma HTTP 模型调用，全部 provider=local；
规划实际开启思考。两种成功任务都验证了真实文件与台账重载，
写入拒绝和缺失文件属于预期失败，验收通过不代表工具本身执行成功。
用时是这台机器本轮运行的观察值，不是性能基准。

原始记录：最终验收（本机私有报告：`data/benchmarks/task-chain/acceptance.json`，不随仓库发布）；
修复前失败记录（本机私有报告：`data/benchmarks/task-chain/before-evidence-fix.json`，不随仓库发布）。
记录保存在本机忽略目录，未提交模型权重或运行数据。

回归：1,076 条 Rust 测试、9 条 MLX 工具解析/线程测试通过；
格式检查、构建与 Clippy 均通过。

## 移除 Agnes 后复验（2026-10-15）

真实 Gemma + Laya 串行复跑以上场景，42/42 项检查通过，六个证据选择样本也全部正确。
五条任务链路分别用时 92.71、105.54、15.31、24.93、27.75 秒，属于单次观察值。
原始记录：移除 Agnes 后复验（本机私有报告：`data/benchmarks/task-chain/after-agnes-removal.json`，不随仓库发布）。

另用 `python3 sidecar/e2e_local_auxiliary.py` 验证无远端凭证的默认 think、聊天落盘、
画像候选、真实模型摘要和陪伴表达；同时检查旧 provider 拒绝、旧密钥变量不串用、
候选 ID 唯一、画像不自动接受、用量归属本地和思考开关显示。
陪伴介入选择使用固定替身以触发表达分支，表达由真实 Gemma 生成。
结果记录：辅助链路（本机私有报告：`data/benchmarks/task-chain/local-auxiliary.json`，不随仓库发布）。
辅助链路 11/11 项检查通过；当前 Rust 回归 1,077 项全部通过。
格式检查、构建和 Clippy（`-D warnings`）通过。

辅助验收还修正了三个问题：本地 think 的 provider 被误记为模型名前缀；
同一毫秒的画像候选共用 ID；think 终端显示了模型能力而非本次思考设置。
上述改动不改变台账格式。旧 Agnes 费用表仍用于历史数据重算。

## 未覆盖

本轮不验证联网搜索、远端模型、外部 MCP、长时间 daemon 常驻与崩溃后的副作用幂等性。
没有训练或校准 Laya；小样本通过不能推导真实任务准确率。

另观察到既有计数口径限制：正常任务 CLI 显示“本次模型调用 6 次”，
台账实际有 8 次 Gemma HTTP 调用，因为工具循环内部的再次请求没有逐次
计入任务推进预算。因此当前 `--budget` 不能视作严格的 HTTP 请求上限。
本轮没有改动预算架构；该限制需在更长的自动任务验收前解决。
