## 暴露的问题与修复

1. 携程部分日期输入框的语义契约只声明 `type/pointer`，直接 `browser_click(ref)` 会被 Driver 拒绝。酒店日历通过已声明的指针操作打开，再选择带完整日期的 gridcell。人数减号及旧版机票日历缺少完整语义引用，依据当前截图换算 CSS 坐标后点击，并回读确认；没有强写只读字段或执行脚本。这些步骤仍依赖准确的视觉定位，不能由本次结果推导出全站模型自主操作稳定性。
2. 实测 Driver 返回 `structuredContent.effect="refused"` 时，可能既没有 `isError` 也没有 `status/refusal`。原解析器把它作为成功输出；新增回归先复现，再在共享 `parse_response` 中将明确的拒绝/失败 effect 返回错误，避免记成成功执行。保留 `unverifiable` 的含义：请求可能已送达，必须观察实际结果，不能把回执当完成证明。错误不回显页面 hint。
3. 页面导航或新开标签会使旧引用失效。酒店详情新开标签、12306转入乘客页面后，重新绑定精确原生窗口并使用新 target/tab 能继续工作；没有重复点击提交或猜测目标。
4. 多个独立浏览器资料互不共享登录。用户登录成功的是后开的携程测试浏览器；后续酒店和机票在这个已登录的自有资料中复用，酒店最初的未登录浏览器未被复制 cookies。正式使用仍需确定固定的助理自有资料及登录接管流程，不能直接套用用户现有浏览器资料。

## 结论

拒绝回执修复已通过真实 Cua Driver 的本地合成页面回归：明确 `effect=refused` 现在返回错误，页面保持未执行；随后 DeepSeek 自主填写、截图回读和其他浏览器动作继续通过。工程检查 `cargo fmt --all -- --check`、`cargo build`、`cargo test`、`cargo clippy --all-targets -- -D warnings` 全部通过，1243 测试通过、0 失败、17 项环境测试默认忽略；release 已构建。

修复版已重载现有后台，进程回读为 running，stderr 无新增错误。结束临时验收进程后，三个测试浏览器窗口残留回读为0；临时操控程序已移除，没有保存截图或迁移登录资料。

已证实：在人工完成登录后，Bot 电脑操控适配器可以读取真实余票和酒店报价，并将火车票、酒店推进到订单填写页。登录门槛、只读字段、异步页面、标签变更和特惠协议都需要识别与接管处理。

尚未验收：模型无人指导的整单自主预订、真实订单创建及回读、支付、取消与退款、确认回执后的Mac日程联动。取得订单号以前不得报告“已预订”。机票当前只到组合产品条款提示，不能列为填单通过。
