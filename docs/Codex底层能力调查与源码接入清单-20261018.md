## 选择取舍

优先接入能够改善当前失败的机制，而不是按安装包模块数量衡量进度：

1. **电脑任务进度和完成条件。** 已能调用工具，但最新跨应用任务仍反复读取；先解决“哪些步骤完成、剩下哪个条件、何时停止”。源码参考任务事件/上下文组织，执行仍走现有Cua和策略。
2. **连接、取消和恢复。** 同一任务的迟到回包不能污染新状态；失联后不盲目重放发送/下单。先做假服务和故障测试，再接真实工具。
3. **压缩后续跑与附件来源。** 用户约束、审批和真实执行事实不能被摘要替代；旧截图/控件token不能因恢复被复活。
4. **通知与语音的任务状态联动。** 从真实事件说明“正在查、等批准、未通知原因”，不再调用模型猜当前状态。保持邮件原生通知已有实现。

暂不引入：Codex桌面UI、私有运行时、完整app-server作为云熙引擎、插件市场、多用户协作文档、复杂语音预热、远程宿主和自动安装。这些目前不是补齐助理任务闭环的必要前提。

不照搬的已见细节：浏览器有限帧等待后仍可使用最后边界框；部分命中检查异常存在宽松处理；通知去重可能先于实际展示；审批broker只是传输结果。云熙的失败不执行、送达核验和封闭审批不能因此放宽。

## 接入验收清单

- 电脑：窗口/页面切换、旧引用、弹窗、动作后读取、取材跨应用、保存文件独立回读；耗尽轮次算失败。
- 生命周期：未派发取消、已派发结果未知、迟到结果、断连重连、重复call ID、待人工后恢复；任何恢复不能变成重复发送或自动批准。
- 上下文：压缩后保留用户条件与已完成事实，私有界面不进持久状态，审批仍有独立依据；摘要失败明确降级。
- 通知：未运行、被阻塞、已分析不通知、已交付/未知分开；重要通知不受普通陪伴额度误伤。
- 附件/文档：来源错误、不可读、过大、部分内容、导出失败、保存但未同步都给准确状态。
- 每项改动仍需fmt、无warning构建、全量cargo test及边界测试；新增依赖/台账格式/既定架构变更按AGENTS处理。

## 第一项实际接入：完整、有界的MCP目录发现

公开源码入口为`codex-rs/codex-mcp/src/pagination.rs`和`connection_manager/tool_catalog.rs`，`rmcp-client`提供分页请求。对照发现云熙的`McpHub::connect_one`原来仅读取第一页，后页工具不会注册。已在现有`mcp.rs`独立实现标准MCP分页，不复制上游crate、不给Bot增加Codex运行依赖。

沿用整个列工具过程60秒超时；最多128页、4096工具、64KiB游标。重复游标、工具重名、后页返回错误或超限时明确失败，不把已取第一页当完整目录。全部页成功后才加入server。外部工具的审批和来源前缀规则不变。

验证：先复现“期望first/second却只有first”，再修补；新增9个协议级用例覆盖后页、空页带游标、异常页、重名、循环、限额和总超时。聚焦MCP52项通过；最终`cargo fmt --all -- --check`、无warning构建、`cargo test -- --test-threads=1`共1321项通过（CLI97/core1224，24项环境测试默认忽略）、`cargo clippy --all-targets -- -D warnings`通过。显式运行真实CuaDriver只读窗口目录检查1/1通过。普通测试没有验证所有第三方服务；只读Driver检查不能代表跨应用任务成功。

日志在`data/acceptance/codex-cua-rea/assistant-capabilities/`，未推送或部署。其余能力保留“已取得/已分析/待适配”状态，不随这一项验收升级为已接入。
