# Qwen3.8-27B Uncensored + mlx-serve 试跑

状态：2026-10-24，mlx-serve 26.10.3；**prefix cache 有效，但该 27B uncensored 权重输出损坏，不能采用**。

## 环境

- 模型：`data/models/Qwen3.8-27B-Uncensored-4bit`（orcarouter 4bit，约 15GB）
- 引擎：`mlx-serve 26.10.3`（Homebrew tap ddalcu/mlx-serve）
- 端口：17880 / 17882；`ctx-size=32768`；本机 M2 Max 64GB

## 结果

首轮（5,531 prompt tokens）：

```text
57.15s；prefill 103.1 tok/s；decode 14.0 tok/s
output: '%-"'.02-/+-02,...（乱码）
```

热轮（5,584 tokens，同一系统前缀）：

```text
4.82s；reused 5500/5584 tokens；prefill 59.8 tok/s；decode 14.2 tok/s
output: 仍是乱码
```

简单 `你好` / `temperature=0`：

```text
completion ids=[0,0]，bytes="!!"，finish_reason=stop
```

## 诊断

- 同一引擎跑 `Qwen3.5-9B-4bit` 正常：`你好！`，说明 mlx-serve 引擎本身可用。
- 27B 的 `tokenize/detokenize` 端点报 400，raw completion 也直接输出 token 0；不是聊天模板或采样温度问题。
- 加 `--no-vision` 仍然乱码；加 `--config-overrides '{"text_config":{"num_experts":0,"enable_moe_block":false}}'` 仍然乱码。
- mlx-serve 日志把模型识别为 `qwen3_5_moe`，并执行 “Precomputing MoE layer weights”，但这个 orcarouter config 没有专家字段；高度怀疑该 uncensored 27B 转换与 mlx-serve 的架构/量化加载不兼容，不是 prefix cache 的锅。
- 根权重在 `mlx_lm`/当前 Python sidecar 下能正常生成，排除权重缺片；问题集中在 mlx-serve 对这个转换的加载/前向。

## 结论

- **不能把 mlx-serve 作为当前 uncensored 27B 的替代**；虽然 prefix cache 证明热轮可到 ~4.8s，但输出不可用。
- 当前继续用 Python MLX sidecar；它首轮 64s、热轮 68s，输出正常。
- 下一步可选：
  1. 用 mlx-community/OptiQ 等**不同转换**的 uncensored 27B 再测 mlx-serve；
  2. 用官方 Qwen3.8 27B 验证 mlx-serve 架构支持，再判断是转换问题还是引擎问题；
  3. 走 GGUF + llama.cpp/gmlx 的 prompt cache；
  4. 无审查 + 可用速度优先，改测 uncensored Gemma 4 26B（MoE）。
