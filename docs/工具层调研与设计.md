### 1.3 三件必须纠正的常见说法

1. **MCP 当前规范是 `2026-07-28`**，不是 `2025-06-18`。服务端原语仍是三类（Prompts 用户控制 / Resources 应用控制 / Tools 模型控制），但**客户端侧的 Roots 与 Sampling 已正式弃用**（最早 2027-07-28 后移除），Logging 与 Dynamic Client Registration 同期弃用，Elicitation 是当前特性。所以"MCP 有五类原语"这句话已经过时。来源：[版本页](https://modelcontextprotocol.io/specification/versioning)、[弃用登记表](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)
2. **MCP 官方参考 server 只剩 7 个**：Everything / Fetch / Filesystem / Git / Memory / Sequential Thinking / Time。传得很广的 sqlite、puppeteer、slack、postgres、github 等**已全部移入归档仓库**，官方原文是"仅供参考、不提供任何安全保证"。来源：[servers](https://github.com/modelcontextprotocol/servers)、[servers-archived](https://github.com/modelcontextprotocol/servers-archived)
3. **OpenAI 的 8 个官方连接器全部只有只读工具**——Gmail、Outlook 邮件、Google/Outlook 日历、Dropbox、Drive、SharePoint、Teams 的工具清单里只有 `search` / `fetch` / `read_*` / `get_profile` 这类动作，**没有任何发送、创建、删除类工具**。来源：[连接器文档](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)

**查不到公开文档的三处，不推断**：ChatGPT Apps/连接器帮助页（403）、Operator/ChatGPT agent 系统卡（403 或不可解析）、AgentGPT 工具清单（无此内容）。

## 二、一条几乎所有家都同意的边界

这是调研里最有价值的部分。**七个独立来源指向同一条规则：读可以自动，写必须问人。**

| 来源 | 原文或事实 |
|---|---|
| [MCP 规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) | "there **SHOULD** always be a human in the loop with the ability to deny tool invocations" |
| [Claude Code](https://code.claude.com/docs/en/tools-reference) | `Read`/`Grep`/`Glob`/`LSP` 权限=否；`Write`/`Edit`/`Bash`/`NotebookEdit` 权限=是。`Bash` 另有一份**只读命令白名单** |
| [OpenAI MCP 工具](https://developers.openai.com/api/docs/guides/tools-connectors-mcp) | MCP 工具**默认每次调用都要求批准**，可用 `require_approval` / `allowed_tools` 收窄 |
| [OpenAI 连接器](https://developers.openai.com/api/docs/guides/tools-connectors-mcp) | 邮件/日历/云盘**只发只读工具**，干脆不提供写动作 |
| [Manus Desktop](https://manus.im/docs/features/desktop.md) | "Every command that Manus attempts to execute on your local machine requires your explicit approval" |
| [OpenHands 安全指南](https://raw.githubusercontent.com/OpenHands/docs/main/sdk/guides/security.mdx) | `AlwaysConfirm` / `ConfirmRisky(threshold)` / `NeverConfirm`，**UNKNOWN 默认也确认** |
| [OpenAI computer use](https://developers.openai.com/api/docs/guides/tools-computer-use) | 购买、数据传输、破坏性变更须保持用户控制；**屏幕内容不可作为授权依据** |

还有两条可以直接复用的细节：

- **审批记忆的作用域按风险分级**（Claude Code）：只读命令可以**永久**记住；文件修改只记到**会话结束**；WebFetch 按**域名**记住。风险越高，记忆越短。
- **网络访问也要问**（Claude Code 对 `WebFetch`/`WebSearch` 都标"需要权限=是"），只对一批预批准的文档域名免问。

### 2.1 「谁来判定要不要问」——这一格正好是我们的位置

| 产品 | 机制 |
|---|---|
| Claude Code | 自动模式下**由一个分类器代替人回答大部分权限提示** |
| [Cursor](https://cursor.com/docs/agent/security/run-modes.md) | Auto-review：allowlist 直跑，其余交**后端 LLM 分类器**。官方明确"Auto-review 不是安全边界" |
| [OpenHands](https://raw.githubusercontent.com/OpenHands/docs/main/sdk/guides/security.mdx) | 可组合的 security analyzer：`Pattern`（`rm -rf`、`eval`、`curl \| sh` 正则）→ `PolicyRail` → `LLM` → `Ensemble`（**取最高风险**） |
| [Cline](https://docs.cline.bot/features/auto-approve) | 由**模型自己**给每条命令打 `requires_approval`，官方明确"不使用固定 allowlist" |

**这就是决策层该站的位置**，而且它正是项目最初要解决的问题——"新邮件要不要通知人工，新问题是否需要人工介入"。工具审批门禁和陪伴介入判定**是同一件事**：在不确定时决定要不要占用人的注意力。

而且 OpenHands 的分层结构和我们的路由完全同构：**确定性规则 → 本地模型 → 取最保守结果**。我们已经有这套三层结构（见 ADR D15），不需要为工具层再造一个。

## 三、建议接的工具

分三档。判据是"**没有它，通用助理这个定位成不成立**"，不是"别家有所以我也要有"。

### 第一档：不接就不是通用助理

| 工具 | 能力 | 为什么必须有 |
|---|---|---|
| `now` | 只读 | 常驻 Agent 不知道"今天几号"就没法处理任何含时间的任务。纯本地、零成本 |
| `web_fetch` | 网络（只读） | **天气那个任务就是死在这里**。抓网页转 Markdown |
| `read_file` / `list_dir` / `search_files` | 只读 | 只读文件操作，对标全体同行的"不询问"档 |
| `write_file` / `edit_file` | 写入（审批） | 能读不能写就只是个搜索框。有 `exec.rs` 的隔离与凭证剥离兜底 |
| `run_command` | 执行（审批） | `run_command` 已经实现（无 shell 解析、隔离级别、凭证剥离、进程树清理），只差接成工具 |
| `ask_user` | 交互 | 缺信息时唯一正确的动作是问，而不是编。D18 的 `BLOCKED:` 就是缺了这条路 |

### 第二档：陪伴定位特有

| 工具 | 能力 | 说明 |
|---|---|---|
| `remember` / `recall` | 只读（写记忆走本地） | `memory.rs` 已有 |
| `schedule` | 本地写入 | `trigger` / `job` 已有。让助理能说"我明天早上提醒你" |
| `notify` | 本地副作用 | 桌面通知。对应 Claude Code 的 `PushNotification` |
| `recall_task` | 只读 | 查历史任务结果（`tasks` 命令已有，工具化） |

### 第三档：走 MCP 扩展，不做内置

邮件、日历、笔记、Slack、GitHub 这类**账号级数据**。理由：

- **所有厂商都是这么分的**：产品内置通用能力（检索/文件/命令/浏览器/记忆），账号级数据一律走 MCP 或连接器。OpenAI 用 connector，Manus 用 MCP Connectors，AutoGPT 用集成块。
- **YunXi Bot 是单人本机**，内置 Gmail OAuth 的复杂度换不来什么。
- 而且**OpenAI 把邮件/日历做成只读**这件事值得抄：读取自动、**发送走显式人工动作**。原点的"发求职邮件"就该是"助理起草 → 人确认 → 发"。

### 3.1 能力分类：审批策略的唯一依据

不要按工具名逐个写规则（Cline 官方明确说这是坑），按**能力类别**：

```rust
pub enum Capability {
    ReadOnly,   // 无副作用 → 自动放行
    Write,      // 本地写入 → 审批，记忆到会话结束
    Execute,    // 执行命令 → 审批，只读命令可白名单
    Network,    // 出站网络 → 审批，按域名记忆
    Outbound,   // 不可逆 / 对外发送 → 永远人工，不参与任何自动放行
}
```

`Outbound` 是 ADR §八 第 2 条（不可逆动作必须人工批准，且批准不参与降级）在工具层的落地。
**`Network` 单列**是因为 Claude Code 对 WebFetch/WebSearch 标了"需要权限"——
出站网络会泄露信息，和只读本地文件不是一回事。

审批门禁的三层（与路由同构，不另造一套）：

```text
工具调用
   ↓
1. 确定性规则（不花钱）：能力类别 + 路径/域名 specifier + 白名单/黑名单
   ↓ 拿不准
2. 本地 Verdict（免费、离线、15ms）："这个动作该不该问人？"
   ↓ 它弃权
3. 保守兜底：问人（fail closed）
```

**顺序不能反**，和路由同一条理由：每次都问模型，等于为了省钱先花钱。
另外抄 OpenHands 一条：**ensemble 取最高风险，UNKNOWN 也确认**。

### 3.2 两条从别人那里抄来的现成经验

1. **先读后写**（Claude Code 硬性要求）：`Edit` 前必须在本次对话读过该文件，`old_string` 必须唯一匹配。这能挡掉一大批"模型凭印象改文件"的事故。
2. **模型生成的内容不能作为授权依据**（OpenAI computer use 明文）：网页、文件、工具返回里的文字**不能**被当成"使用者同意过"。我们的工具输出进的是易变段，天然满足——但要写进不变量里，别哪天顺手把工具输出拼进系统提示词。

## 四、MCP 怎么接：接，但要隔离

**决策：接 `rmcp`（官方 Rust SDK），把异步关在一个模块里。** 我最初倾向"先不接"，
理由是"基础工具不需要 MCP"——**那个理由是错的**，它只解决了眼前三个工具，
却把助理能力的上限锁死了。通用型助理的价值恰恰在于"使用者想要什么能力就能加上什么"，
而那条长尾只有 MCP 覆盖得住。D9 的"只加一个 TLS 依赖"是我们自己定的纪律，
不是硬约束；为它牺牲产品核心价值是本末倒置。

### 4.1 代价是量出来的，不是估的

```
rmcp (default-features=false, features=["client","transport-child-process","transport-io"])
  → 79 个依赖包，构建 13 秒
当前项目 103 个包 → 加上后约 165 个
```

关键发现：**`rmcp` 只要 `tokio` 的 `["sync","macros","rt","time"]`——`rt` 是当前线程运行时，
不是 `rt-multi-thread`。** 所以异步运行时可以被容纳，不必让整个代码库变成异步。

### 4.2 隔离办法

MCP 客户端住在一个 `mcp` 模块里，对外**只暴露同步 API**：

```rust
pub struct McpHub { rt: tokio::runtime::Runtime, servers: Vec<RunningServer> }

impl McpHub {
    /// 同步方法。内部 block_on，调用方看不到任何 Future。
    pub fn list_tools(&self) -> Result<Vec<McpToolDesc>, McpError>;
    pub fn call(&self, server: &str, tool: &str, args: Value) -> Result<String, McpError>;
}
```

**内核永远不见 `Future`。** 执行引擎、台账、路由、决策层全部保持同步，
`ureq` 继续用。代价是"多了一个模块 + 一个运行时对象"，不是"重写整个项目"。

### 4.3 三件必须一起定下来的事

**1. MCP 工具默认需要审批。** 这是 OpenAI 的默认行为（"MCP 工具默认每次调用都要求审批"），
也是唯一诚实的选择：**server 自己声明的能力是"声称"，不是"事实"。**
所以 MCP 工具的 `Capability` 默认是"未知"→ 按失败方向朝不执行处理。
使用者在配置里对某个 server 的某个工具显式写 allowlist，才算预批准。

**2. 工具名必须带出处前缀**：`mcp__<server>__<tool>`。
否则两个 server 都叫 `search` 时会静默串台，而这种错极难排查。

**3. 先只支持 stdio 传输。** rmcp 的 HTTP 传输要拉 `reqwest`，那是**第二套 TLS 栈**
（我们已经用 `ureq` + rustls 了）。绝大多数 MCP server 就是 `npx`/`uvx`/独立二进制，
stdio 覆盖得住。HTTP 传输等真有远程 server 需求再加，届时单独决策 TLS 栈要不要换。

### 4.4 这条决策要改 ADR

D9 写的是"引入 TLS 依赖，但只此一个"。现在多一个运行时族。
**不改写 D9 的历史，而是新增一条 D19 说明它的适用范围被缩窄了**——
ADR 的价值在于留下"当时为什么这么想"，而不是把记录改成现在看起来对的样子。

## 五、联网检索：实测过的可用方案

上一轮"查天气"失败的直接原因是**没有联网工具**。所以这一项不靠调研结论，直接实测。

### 5.1 实测结果（2026-10-05，本机）

| 方案 | 要 key | 实测结果 | 结论 |
|---|---|---|---|
| **Jina Reader** `r.jina.ai/<url>` | 不要 | HTTP 200，321 字节，返回 `Title` + `URL Source` + `Markdown Content`。直连与走代理都通 | **可用**。抓网页这件事不用自己写 HTML→Markdown |
| **DuckDuckGo lite** `lite.duckduckgo.com/lite/?q=` | 不要 | HTTP 200，22911 字节，正则解析出 **10 条**结果 | **可用但会烂**。是抓 HTML，改版或反爬就失效 |
| **SearXNG 公共实例** `?format=json` | 不要 | `searx.be` 返回 **`Content-Type: text/html`**，不是 JSON；`priv.au` 429；`search.bus-hit.me` TLS 失败 | **不可用**。公共实例普遍关掉了 JSON 接口（防滥用），要 JSON 得自建 |
| **DuckDuckGo Instant Answer API** | 不要 | 只给百科式摘要，不是网页结果 | 不适合当搜索 |
| **Wikipedia API** | 不要 | 结构化 JSON，但只覆盖维基 | 只适合知识类查询 |
| Brave Search API | 要 | 号称 2,000 次/月免费 | 未实测（没 key） |
| Tavily | 要 | 号称 1,000 次/月免费，输出为 Agent 场景设计 | 未实测（没 key） |
| Google Programmable Search | 要 | 号称 100 次/天免费 | 未实测（没 key） |
| Serper.dev | 要 | 号称 2,500 次一次性免费 | 未实测（没 key） |

**没有 key 又能出网页结果的，实测只有 DuckDuckGo lite 一条路。**

### 5.2 建议

- **`web_fetch` 用 Jina Reader**：零配置、返回干净 Markdown、省掉自己写正文抽取。**但要留回退**——它是个第三方免费服务，挂了要能退回自己抓 HTML 再剥标签。
- **`web_search` 做成可换 provider**：默认走 DuckDuckGo lite（零配置，今天就能用），把 provider 做成配置项。它哪天失效，填一个 Brave/Tavily 的 key 就能换掉，不用改代码。
- **诚实的预期管理**：抓 HTML 的方案**一定会烂**，不是"可能"。所以默认方案的价值是"今天能用"，不是"长期可靠"。这也是为什么 provider 必须可换。

### 5.3 一片没验证的区域

用户的网络在境内，DuckDuckGo 与 Jina 都可能需要走代理才通。本次实测是在**本机已开代理**的环境下做的，所以**不能据此断言"无代理环境也通"**。真正部署时要按实际网络再测一次，并把这个结论写进使用说明。

## 六、实施顺序

原则：**先把"能干活"打通，再把"能扩展"接上。** 两者共用同一套工具抽象，
所以顺序不影响架构，只影响多快能看到效果。

### 阶段一：工具层骨架 + 原生工具

1. **`Tool` trait + 注册表 + `Capability` 分类**（第一节 3.1 那张表）
   这是 MCP 也要插进来的那个口，所以必须先定。
2. **审批门禁三层**：确定性规则 → 本地 Verdict → 问人（fail closed）。
   复用路由已有的三层结构，不另造一套。
3. **原生工具**：`now`、`web_fetch`（Jina Reader，留回退）、`web_search`（provider 可换，默认 DuckDuckGo lite）、
   `read_file`、`list_dir`、`search_files`、`write_file`、`edit_file`、`run_command`、`ask_user`。
4. **接进执行引擎**：模型的 `tool_calls` → 审批 → 执行 → 结果回灌易变段。
   实测已确认思考模式下带 `tools` 不冲突，所以这一步没有未知数。

验收：**"查北京今天天气"这个任务能自己走完**——搜到网址、抓到数据、给出温差。
这条链路走通，才说明工具层真的活了。

### 阶段二：MCP 客户端

1. `mcp` 模块 + 隔离的 tokio 运行时 + 同步 API
2. 配置里声明 server（`command` + `args`）
