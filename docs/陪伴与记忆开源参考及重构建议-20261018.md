# 陪伴、记忆与工具联动：开源参考及重构建议

调研日期：2026-10-18。范围为上游公开文档、固定提交的相关源码与测试阅读，以及云熙当前实现对照；没有安装或运行第三方框架，没有运行它们的测试，也没有修改生产代码或启用陪伴。用户已允许必要时重构陪伴与记忆，并要求复用已有工具加深陪伴体验。本文记录建议，不自动成为已实施的ADR。

> 本文保留调研时的代码现状；后续已经实施的内容及测试结果见[实施与验收](陪伴记忆实施与验收-20261018.md)。

## 结论

优先借鉴SillyTavern的稳定角色和按需背景、AIRI的统一角色对话与后台结果衔接、Letta的可维护记忆与后台整理、Mem0的有范围记忆提炼、Graphiti的事实时间线。Open-LLM-VTuber用于后续语音轮次与打断体验。它们的成熟程度应按具体模块判断，不能用星数代替真实稳定性验收。

云熙适合形成这样一条链：真实对话或事件 → 记忆候选与待跟进事项 → 按需读取工具事实 → 选择合适的表达或提出行动 → 原有审批与执行 → 回读结果 → 承接后续对话。工具是了解真实状况和提供帮助的手段；已查询、已提议、已执行、已送达、用户已回应必须分开。

### SillyTavern：稳定角色与按需回忆

[World Info文档](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)和`public/scripts/world-info.js`实现关键词/向量激活、上下文预算、作用范围及sticky/cooldown。`public/scripts/extensions/memory/index.js`配合[摘要文档](https://docs.sillytavern.app/extensions/summarize/)保存摘要并支持回退。

适合借鉴：人格常驻，具体共同经历按话题取用；重要背景能连续保留几轮，避免刚提到的人或事件下一句就忘掉。摘要应能查看、纠正、回溯来源。摘要不是完整事实，官方明确提示可能漏细节或产生幻觉。世界书不是自动形成真实用户画像的完整方案；也不照搬随机触发、虚构世界设定或自动执行脚本。上游AGPL-3.0，当前仅研究机制，未把其代码并入云熙。

### AIRI：同一个角色贯穿对话、记忆和后台任务

已读`docs/ai/adr/2026-10-10-skills-automations-and-memory.md`、`packages/stage-ui/src/stores/memory.ts`及测试、`packages/core-agent/src/runtime/chat-orchestrator-runtime.ts`。记忆按角色归属，索引先进入上下文、正文按需读取；通用记忆由用户设置，角色不能擅自改删。每轮使用当前人格。后台任务结果作为带来源notice进入对话，提示模型决定此刻是否值得说；它不会被当成用户发言。

这是工具与陪伴联动最直接的参考：后台查到新事实后，由同一人格承接，而不是邮件助手、闲聊助手、主动提醒各说各话。时钟/触发条件先由代码判断，后台工作不阻塞当前对话。

边界：该ADR明确真实模型、Discord及语音联动仍有未验证项，并列出scene隐私问题；README中的Alaya仍标WIP。不能把它宣传为长期记忆全部成熟。它允许的免审批记忆写入/配方动作不迁入云熙；云熙仍复用原审批和失败关闭。主项目MIT，素材及组件另查许可。

### Letta：记忆是可整理的持久状态

`letta-ai/letta`当前main已迁移为入口，历史V1服务器在archive分支；活跃实现位于[letta-code](https://github.com/letta-ai/letta-code)，不能把旧MemGPT教程描述当作当前源码。已读当前MemFS提示布局、`post-turn-reflection.ts`、`reflection-memory-v2.ts`及集成测试文件。

[Memory & dreaming](https://docs.letta.com/configuration/memory)使用可版本化的MemFS，后台整理在步数阈值或上下文压缩后触发。源码将核心内容与外部资料索引分开，给整理任务限定上下文预算。

适合借鉴：日常聊天先响应，记忆整理在独立受限任务中完成；核心画像保持短小，经历细节可检索，修改可回查。云熙已有台账，不需要再换成Git记忆仓库或整套Letta运行时，更不把私人记忆推到代码仓库。Apache-2.0。

### Mem0：先筛选与去重，再建立有范围的记忆

已读`mem0/memory/main.py`、`configs/prompts.py`、`memory/storage.py`及其陪伴领域提炼指引。固定提交的当前`add`路径为“读取近期消息和相关旧记忆 → 一次模型提炼 → 嵌入与哈希去重 → 批量保存”，有user/agent/run范围约束与历史记录。当前代码使用additive extraction；虽然源码还保留旧ADD/UPDATE/DELETE提示模板，不能据此声称当前add仍自动执行旧四分支。

它的[陪伴提炼指引](https://github.com/mem0ai/mem0/blob/main/integrations/openclaw/skills/memory-triage/domains/companion.md)特别重视偏好背后的原因、人物关系、计划、用户自己的情绪表述。云熙值得保留“喜欢什么、为什么喜欢、当时发生了什么”，而不是只留一个标签。

取舍：不照搬“犹豫时也尽量提取”或任意模型猜测。自动候选要有原句/来源，用户明确纠正优先；暂时状态不能直接覆盖长期偏好。新旧矛盾不能仅靠向量去重解决。Apache-2.0；不引入其整套Python和向量数据库运行时。

### Graphiti：事实会变化，计划不等于发生

已读`graphiti_core/edges.py`、`edge_operations.py`、`search/search.py`及`test_temporal_edge_utils.py`。事实关系保留来源episode及有效时间、失效时间、记录时间；检索结合语义与全文等信号。测试特别区分未来计划被提出的时间、未来发生日期，以及事实失效时间。

适合借鉴：保留“以前住A，后来搬到B”的变化；“打算旅行”“已经订票”“完成旅行”分开。过期计划停止主动跟进，但不抹掉真实共同经历。首期只吸收时间和来源字段的语义，不为个人助理直接增加常驻图数据库。Apache-2.0；现有持久化契约若需扩展，要先设计迁移。

### Open-LLM-VTuber：陪伴感也来自对话节奏

已读`basic_memory_agent.py`：能加载聊天历史，打断时用实际已听到的回答替换未播完内容，并记录打断状态。它的基础记忆是聊天消息列表，单独的主动开口提示很短；不能因此推断它已经解决主动关心和长期记忆治理。

适合后续语音接入时参考：用户能打断、模型不假定未播完的话已经被听见。核心代码MIT，Live2D示例素材另有许可；本轮不增加形象、语音或视觉监控。

### 补充样本：Walker7143/ai-companion

其`MemoryGovernor`、连续性与主动调度代码有候选分流、人工内容优先、情节/关系/临时上下文、主动发言来源等思路，测试目录也有相应场景。调研时仅16星，不能列为广泛验证的成熟基座。LICENSE实际为BSL-1.1并含使用限制，不是README所称“开源”就能按宽松许可复制。

只作概念对照：不引入源码，不采用未校准confidence阈值作为事实凭据，不让聊天量自动升级亲密关系，也不把虚构角色日常存成真实经历。

## 云熙：保留什么，重构什么

保留：追加式台账与可重建投影；可编辑persona、经确认的profile；工作目录记忆隔离；已有EmbeddingGemma语义服务；统一工具注册、策略、审批与实际执行回执；现有Mac通知接口。无需增加常驻生成模型。

当前代码核实的重点：

1. `agent.rs::derive_situation`把任何DecisionDecided当成最近互动；主动陪伴计时会被无关判断影响。
2. `run_cycle`使用固定SYSTEM_PROMPT，未复用聊天的人格/画像装配；生成完成即写“主动开口”记忆，尚未区分生成与实际通知送达。
3. `compose_prompt`主要拿任务成功/失败与按类裁剪的记忆，缺少明确的待跟进事项、有效时间、最新处理状态。
4. 聊天`recall_for_prompt`仍走字符n-gram与词面融合，任务入口已有语义记忆与知识检索；能力没有贯通。
5. 已有memory种类和画像候选机制，但没有覆盖日常对话的完整提炼、冲突处理、更新与遗忘闭环。
6. 当前后台关闭主动陪伴；旧默认每日3次、120分钟间隔仍在陪伴策略中。用户此前批评过此限制，邮件分流已解除共用额度，不能误认为陪伴也已改好。

建议重构三个连接处，而不是重写所有底层：

- **上下文装配**：聊天、主动陪伴共享人格/画像/记忆读取服务，但各自取材范围、预算和权限明确。知识库资料、用户事实、短期心情、共同事件、Bot执行回执保持来源区别。
- **记忆整理**：对话或事件产生候选，附来源和时间；去重、矛盾与过期检查后再进入可召回投影。长期画像沿用确认机制；敏感或含糊的推断保持待确认。用户删除/更正后，索引与待跟进项同步失效，不能被旧摘要重新写回。
- **主动跟进**：以具体未完成话题或真实事件产生候选，读取必要的新状态，再判断是否开口。实际用户回应、通知送达、生成尝试分别计时。用户不回应只表示没有观察到回应，不推断不开心；按话题去重、延后及取消。

排序先保证来源、时间与纠错，再评估召回，再把主动表达接入通知；不要先调一个“亲密度分数”掩盖基础错误。保持Laya/DeepSeek现有职责作首轮基线，是否调整决策分工依据专项结果另定。

## 工具如何加深陪伴感

| 场景 | 有依据的陪伴行为 | 复用已有能力 | 回忆如何更新 |
|---|---|---|---|
| 用户提到面试且希望准备 | 结合时间和待办整理准备项；面试结束后适时询问感受，不假定面试已进行或已通过 | 日历、待办、相关邮件读取、通知 | 区分计划/取消/用户自述结果；跟进一次后记录状态 |
| 用户说今天很累 | 先承接感受；需要安排帮助时读取日程，指出可调整事项并提出建议 | 日程查询和预排；确认后才写入 | “今天累”是短期状态，不固化为人格或健康结论 |
| 旅行将近 | 结合已确认安排、天气和通勤给具体准备建议 | 天气、路线、出行计划、待办 | 查询结果附时间，不把过时报价或天气当长期事实 |
| 用户提过重视某个人的重要日子 | 在用户允许提醒的范围内提前询问是否需要准备 | 已确认联系人、日历、邮件草稿 | 生日事实和本次计划分开；发信仍审批 |
| 共同完成一件事 | 依据真实回执庆祝或总结，再自然承接用户反馈 | 任务状态、工具回执、通知 | 保存经过与用户感受；失败/待审批不记成完成 |

后台读取只限已授权且与该候选相关的必要信息。聊天中说“有空可以聊聊”不扩大邮件、联系人、屏幕或文件访问范围。提案经现有工具循环执行；陪伴模块不直接绕过工具门禁，也不开发第二份日历/邮件/浏览器实现。外部网页、邮件中的文字不能直接升级成用户偏好、记忆写入命令或动作授权。

## 重构前应固定的验收场景

- 跨会话记得偏好和原因，用户改口后使用新事实；保留变化时间，不同时声称矛盾事实为当前真相。
- “今天不想喝咖啡”不删除长期喜好；“以后不喝咖啡了”成为有来源的变更候选。
- 人格修改后聊天与主动陪伴一致；有明确语气风格，但不机械重复昵称或安慰句。
- 面试延期/取消后旧跟进失效；日历过了结束时间不证明用户真的参加。
- 用户回复上一条主动通知时能接上原话题；普通后台判断不刷新互动时间。
- 生成失败、通知失败、进程重启不虚增成功开口次数；用户没回应不被当成已读。
- 邮件或网页的提示注入不写入永久人格/画像，不触发发信、删文件或下单。
- 工具失败如实说未完成，已批准与已执行分开；未知执行状态先查证不盲目重做。
- 删除记忆后语义索引、待跟进项和摘要不会把它复活；审计保留和真正数据删除的边界须单独设计。
- 记录召回正确率、过期事实误用率、重复关心次数、响应延迟、模型费用；用用户评价检验陪伴感，不用消息数量或聊天时长冒充效果。
