# Laya 项目微调：首轮实测与上游调研

2026-10-15。**训练、导出和真实服务复测已跑通，但没有得到优于基础模型的候选。生产继续使用原始 multilingual 权重，calibrated:false。**

## 本机实际结果

用户已认可32个中文合成场景、46个判断。按场景组固定为训练16个场景/22题、验证6/8、校准6/12、测试4/4。只有训练组参与梯度更新，验证组选 epoch，之后才拟合校准和计算其他分组结果。由于样例和基线已经用于诊断，这些留出题是开发期诊断，不能继续当作最终独立盲测。

同一已校验的 laya-multilingual 底座、laya 0.4.7、seed 20261015、soft-ce、choice 选项置换。micro_batch=1、grad_accum=8、8 epochs，共24次优化器更新；编码器学习率1e-5，决策头5e-5。每次只有一个训练或候选评估进程，使用原生 MPS。

内存值是每个 epoch 末的采样最大值，不是连续监测的峰值，也不是整机已用内存；MPS 分配器限额为12 GiB，不代表整机或 CPU 内存硬隔离。全参数/决策头训练的进程峰值 RSS 分别2.969/2.914 GiB，不能与共享内存指标直接相加。

全参数候选表现出过拟合：训练全对，未训练题与原回归却下降。决策头候选在这个预算下没有改善；已逐张量确认其134个编码器张量与底座一致。**这不能证明冻结编码器路线无效，也不能证明增加训练步数会改善泛化。**

两个有效候选都选到第8轮。校准集仅含6个 choice、6个 noul，均不足上游每类至少10题的拟合门槛，温度保持1.0；更不能据此声称概率可靠。

最初 pilot-01 发现上游 save_checkpoint 默认转 FP16，导出后验证结果从6/8变成5/8。已用回归测试复现并让项目导出保持训练的 FP32；pilot-02 重新训练后复测，重新加载仍为6/8。pilot-01 留作诊断记录，不参与候选推荐。基础权重未修改。

## 作者和社区实际说了什么

以下为2026-10-15读取的一手资料。区分上游作者、贡献者实验与独立项目，第三方数字没有在本机复现。

### 官方支持监督适配，也支持原生 Mac

上游现有 laya-train / laya.train 可以直接训练带 expected 硬标签的 JSONL，也支持 gold 教师概率；不用为采用官方接口而编造概率。设备支持 MPS、CUDA、CPU。校准数据必须与训练分开，温度缩放只改变置信度，不修正答案类别。资料：[官方训练文档](https://github.com/NandhaKishorM/laya/blob/main/docs/finetune.md)、[Apple Silicon 训练入口](https://github.com/NandhaKishorM/laya/blob/main/notebooks/laya_finetune_typed_decisions_mps.py)。

因此沿用当前 PyTorch/MPS 是有效路径，无需为训练另装 CUDA 栈。中文继续使用 multilingual 底座。

### 小数据要查更新步数，但不能把加轮数当作万能修复

作者在 #963 的回复强调：同样4轮，5,600题是352次更新，1,100题仅72次；应明确计算训练预算，复测不同随机种子，并用“在输入中故意编码答案”的独立正控诊断优化器能否学会简单信号。352不是通用最低门槛；正控通过也不是业务泛化证据。来源：[作者回复及后续实现状态 #963](https://github.com/NandhaKishorM/laya/issues/963)。

我们只有24次更新，但全参数训练题已全对，不能把未训练题下降直接解释为更新太少。作者在 #887 的21行 CSV 实验中，也将训练损失近零而留出题未全对归因于数据限制。来源：[训练接口与作者实测 #887](https://github.com/NandhaKishorM/laya/issues/887)。

### soft-ce 不是已证实胜过 RLCD

初期单种子结果有利于 soft-ce，但后续3个种子的受控实验中，平均准确率约77.63%与77.62%，基本相同；soft-ce 的跨种子标准差约1.55个百分点，RLCD约0.16个百分点。上游保留 RLCD 默认。不能只引用旧单次实验宣称交叉熵更好。来源：[消融实验及后续三种子结果 #741](https://github.com/NandhaKishorM/laya/issues/741)、[#887 后续讨论](https://github.com/NandhaKishorM/laya/issues/887)。

现有 soft-ce 作为管线试跑和基线有效。下一轮在补足数据后，应在同一划分、同一预算上比较 RLCD 与 soft-ce，至少3个种子；不把另一项目的最佳损失直接当作本项目答案。

### 第三方数据量实验有参考价值，但没有中文万能样本数

tehtommeh/laya-finetuning 公布英文 typed-decisions 的嵌套样本实验：30个训练场景/150个判断时约51.4%，300个约65.7%，600个约73.5%；增加到1,075个未继续明显提升。150场景从4轮增加至12轮，只从59.1%到62.3%，仍低于300场景4轮。来源：[复现实验记录](https://github.com/tehtommeh/laya-finetuning/blob/main/docs/EXPERIMENTS.md)。

该项目建议每组问题先用20–40个场景试跑，之后按学习曲线加量，并保持训练/推理问句一致、覆盖每个选项。这个范围来自其英文任务，不能当作 YunXi 的合格门槛。来源：[该项目训练指南](https://github.com/tehtommeh/laya-finetuning/blob/main/docs/FINETUNING.md)。

我们16个训练场景分散于六类功能，明显比“每类20–40个”更稀疏。缺标签比更换训练框架更值得先处理。

### 原生 Mac 上还有 LoRA 路线，但不需要现在迁移

biplovgautam/LayaStudio（现名 System One Studio）实现 MLX 编码器 LoRA 加完整决策头训练。其报告在 M4/16 GB 上，900条 Banking77 训练样本使 multilingual 从34.2%到64.2%；这是该项目的英文公开数据结果。源码和结果：[项目 README](https://github.com/biplovgautam/LayaStudio)。

它证明有可参考的 Mac 训练实现，不证明 LoRA 对我们这批中文小样本必然更好。我们的全参数训练采样内存已约6.45 GiB，当前优先解决数据；没有安装该项目或改变运行依赖。其 README 中“只有双云端GPU notebook 可训练”的说法已与目前官方 MPS/CLI 支持不符，采用前需逐项核对，不能整份照搬。

### 任务状态和负例比漂亮的汇总分更重要

上游收录的 browser-agent 实验发现，“只要有历史就选 DONE”等数据捷径会毁掉任务链路；加入真实完成状态、未完成的中间状态负例、修正输入截断，才能改善。来源：[上游收录的浏览器任务案例](https://github.com/NandhaKishorM/laya/blob/main/docs/finetune_browser_agent.md)。

对 YunXi 的启示：任务完成必须有独立执行证据；工具结果里的引用、错误、旧状态，不能等同于新指令或完成。数据应包含同样表述但不同实际状态的成对场景，而不只把正例换词。

## 下一轮方案

1. **先补训练覆盖。** 当前训练组缺 knowledge、mixed、hold 介入、is_anomaly=true、triage=quiet、needs_action=false。新增[12条待审核补充](Laya微调-第二批补充审核.md)只填这些空白，不足以完成正式微调；44条草案/70题已通过 tokenizer 预检，新增12条未训练。
2. **扩成有独立场景的中文数据集。** 本项目建议先以每类30–50个训练场景作为下一阶段试验规模，六类约180–300个训练场景，另外建立足量验证/校准/最终测试。这个数量是工程起点，不是上游承诺；用学习曲线决定是否再加量。合成场景覆盖否定、引用、多轮回指、混合意图、罕见标签与缺证据，保留人工审核及来源，再加入脱敏真实反馈。
3. **固定生产问句与数据划分。** 同一事件及改写不能跨组。原32题与原40题都保留为开发回归；建立新终测后只在方法选定时使用。多数类基线、每类召回、误打扰/误放行建议和选项顺序敏感度都要看，不能只报总准确率。
4. **控制变量比较方法。** 在已审核数据上串行比较 RLCD/soft-ce、至少3个种子，记录实际更新步数。冻结编码器作为低资源对照；LoRA仅在效果或资源证据支持时另做实验。验证集选参数，校准集拟合温度；测试结果不回流调整当前候选。
5. **以项目链路验收决定部署。** 先核对 checkpoint 导出重载一致性，再在独立端口跑分类、记忆、工具建议、任务证据和陪伴/邮件；候选不能绕过规则和人工审批。数据不足时继续 calibrated:false。
