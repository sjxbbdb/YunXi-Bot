# 本地上下文 128K 实测

状态：2026-10-24，Gemma 4 26B-A4B，M2 Max 64GB，Mlx Python sidecar。

## 结果

| 输入 | 结果 |
|---|---|
| **64K 级（66,084 prompt tokens）** | ✅ 成功，224.7s，回复“收到。” |
| **120K 用户 + 系统约 125.5K** | ❌ 281.6s 后 HTTP 500，不是超时 |

64K 测试使用 60,000 token 中文材料 + 约 6K 系统人格；128K 测试使用 120,000 token 用户内容 + 约 5.5K 系统。

## 结论

- 模型原生支持 **262,144 tokens**，但当前 Python MLX sidecar 的**可用上限约 64K**。
- 128K 不是“改个常量”就行：120K 在 prefill 阶段失败；当前 `mx.set_memory_limit(48GB)` 和 MLX 长上下文路径无法稳定承载。
- 64K 能工作，但 prefill 要 **224.7s**；只适合长文分析/离线整理，不适合日常聊天首轮。
- 已把运行上限收回到 **81,920 tokens（80K）**，给 64K 内容 + 系统人格前缀留余量；不要把它当成“已验证 80K”的证据，已验证的是 66K 总量。

## 相关位置

- `sidecar/mlx_backend.py`：`CONTEXT_LIMIT = 81920`
- `crates/yunxi-bot-cli/src/chat_server.rs`：`local_budget.window_tokens = 81920`，`reserve_for_reply = 10240`

## 下一步

要真正稳定 128K，需要：
1. 更强的长上下文 attention/缓存实现（非当前 mlx-lm）；
2. 降低权重/KV 内存（更小量化或分块）；
3. 或接受 128K 仅用于离线批处理，不用于聊天首轮。
