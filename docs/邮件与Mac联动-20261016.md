# 邮件与 Mac 联动

2026-10-16。本轮将邮件接入既有通知、日历和提醒事项流程，沿用联系人、附件、路线及邮件发送工具。没有增加另一套日程数据库、常驻模型或原生应用权限。

## 可以怎样使用

1. 收到 `云熙 · 邮件｜人事回复` 之类的通知后，在对话中说“看看刚才通知的那封邮件”。Bot 查询已通知／待查看记录，再定位真实邮件；多封符合时先确认，不默认挑最新一封。
2. 说“按这封邮件安排面试，并留半小时准备材料”。先读取正文及原有安排。原文起止时间完整且用户要求按邮件安排时可以采用；时长、时区或对象不明则追问。通知摘要不能替代原文。
3. 预排考虑现有日历占用、待办期限、工作时段与间隔。用户已要求同步时进入原有动作审批；成功回读后才报告保存。会议、材料准备、回复确认可以是同一封邮件下的不同事项。
4. 后续说“把这封邮件的面试改到四点”“准备材料做完了”，读取系统事实并更新原记录，保留来源和其他约束。跨日改期复用多日工具，同时处理旧日和新日；必要事项冲突时停止保存。
5. 在 Mac 提醒事项中手动完成任务后，下一次查询会看到实际状态。再要求“同步完成状态并重排”才调整日历；当前没有后台持续监听系统编辑。

“回复确认”待办完成不代表邮件已发送。只有用户另外提出回复／发送请求，才查联系人、起草和进入发送审批。安排日程不自动标已读、归档、回复或打开附件。涉及现场地址时继续复用地点、路线、天气与 `travel_for`，缺少信息不猜通勤时间。

发送侧已补本机草稿/提交状态查询和附件替换，真实发件来源衔接跟进日程、Mac 通知及跨会话回查的验收见[邮件发送与 Mac 联动](邮件发送与Mac联动-20261016.md)。

## 实现与边界

- 新增只读工具 `mac_mail_context`：用真实 Mail 线程头找到相关邮件，再查专用提醒事项中的来源关联；返回 `source_mail`、`linked_tasks`、实际完成状态及原日程日期。正文仍由 `mac_mail_read` 逐页读取。工具回执不能被误当作已经读完整串正文。
- 关联身份为 `account_id + Message-ID`，不使用主题当主键。日程和待办的既有业务备注增加可选 `source_mail`；旧记录缺省为空，不改审计台账格式。后续邮件通过真实线程关联原来源，修改时自动保留原关联，不能用新信覆盖旧来源。
- `mail_review_pending(include_notified=true)` 可回查已通知邮件；默认仍只返回待查看和暂缓项。发现时的邮箱位置可能因归档而过期，须重新搜索，不猜同主题邮件。
- 所有保存仍经 `mac_agenda_apply` / `mac_trip_apply` 的公共审批、版本核对、失败报告及原生回读。邮件内容和来源字段都不是执行授权。预排回执明确区分继续审批、冲突停止和已保存，避免要求同步后只停在方案上。
- 后台继续按 D148 只读分析新邮件、提出提醒建议并过固定通知策略；本轮没有赋予后台邮件分析工具执行能力，没有放宽静默、额度或去重。

查询入口：

```bash
./启动.command mail --pending
./启动.command mail --pending --include-notified
```

当前是**通过对话承接通知**，没有实现点击横幅直接跳转邮件、通知按钮或新的图形界面。只关联带来源的云熙日程；旧的自由文本记录不会自动补来源。系统备注损坏、线程或列表不完整、缺少 Message-ID 时明确报错。已删除原待办时不能仅凭标题恢复原关联。

## 验收方法

`sidecar/e2e_mail_mac.py` 使用真实 DeepSeek、Laya、Mac Mail 与 EventKit。用 `--sender` 显式指定本次授权的测试发件邮箱，读取主题为“测试”的来信，当前版本要求该信在生产队列中已经分析并通知，且有唯一 confirmed 通知台账，再复制真实记录到隔离对话环境；不能凭合成状态声称通知已发生。早期 r1–r6 使用合成的已通知入口，其证据范围保持原记录。测试日期、会议和待办是用户输入中的合成数据，不伪装为该邮件原文。只在 2031-05-18 创建带唯一验收前缀的日历和待办，完成后回读确认清理；禁止发送、归档和标已读。运行时用 --expect-term 指定原文关键事项，核验阅读结果。

覆盖通知回查、首次关联保存、新会话改期、不重复建立、Mac 手动完成回读、完成同步重排、固定占用冲突七个场景。通过工具台账、完整回执和独立系统回读交叉核对；不能只看模型说“完成”。单元测试另覆盖后续信关联旧信、归档位置变化、跨账户隔离、旧备注兼容、非法来源、损坏元数据与不完整扫描。

r1 和 r3 暴露了测试允许列表过窄：合法的账户查询和多日预排被测试策略拒绝，未发生误写。已允许两条排程路径及相关只读查询，保持系统结果断言和邮件写操作禁令。r2 暴露模型只预排后重复询问；共享预排回执已明确授权后进入 apply 审批的下一步。失败报告保留于 `data/benchmarks/tools/mail-mac-ecosystem-20261016-r*.json`，没有删掉失败记录。

r4 中模型拿读取原安排的版本保存改动，工具在写入前拒绝；重新预排后写入回读成功，但达到八轮上限，没有完成对话收口，整例仍判失败。工具回执与提示补充：关联查询已含原 task，可以直接修改后预排，不能拿旧参数的版本保存新参数；未放宽版本校验或循环上限。

r5 前六项通过，末项改期冲突正确拒绝写入，但错误回执缺少具体占用，模型把冲突误归到弹性待办。先补失败回归，再让共享排程器返回实际重叠占用的标题和时间。既有改期冲突以错误返回，验收现在接受带 `no_writes=true` 与真实固定占用证据的预期拒绝，同时要求模型说明正确对象，并独立核对系统没有变化；其他工具错误仍判失败。
