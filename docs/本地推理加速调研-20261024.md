# 本地推理加速调研（2026-10-24）

> 目标：为“聊天本地、任务云端”的混合架构挑选推理引擎与本地模型。
> 结论基于公开资料与厂商基准；**没有在 M2 Max 64GB 上独立复测**，下一步要做同机基准。
> 本文不改变现有代码。

## 0. 结论先行

1. 现在最大的加速不来自“换一个更小的模型”，而来自**引擎 + 投机解码 + KV cache 量化 + 合适的量化格式**这一整套。
2. 64GB M2 Max 的甜点区是 **27B–35B 的 4-bit 模型**：Qwen3.8-27B（约 16GB）、Qwen3.6-35B-A3B（约 20GB，MoE 3B 激活）、Muse Glimmer-30B（约 19GB）。125B 级模型不适合本机。
3. 本地模型不再只有 Gemma 4 / Qwen3.5 两个选择；2026 年出现了面向 agent 的 Muse Glimmer 30B、带原生 MTP 头的 Qwen3.6/3.8、以及 ternary 量化的 Bonsai 2。
4. 不建议把模型名写死。适配器应把“引擎 / 模型 / 量化 / 工具协议 / 上下文 / 许可证”都当作可声明能力，由任务分配器按能力和隐私选。

## 1. 加速技术栈

| 层 | 技术 | 作用 | 注意 |
|---|---|---|---|
| 模型 | MoE（Qwen3.6-35B-A3B） | 总参 35B，激活约 3B，速度快于 dense 同级 | 内存仍按总参占用 |
| 模型 | 原生 MTP 头（Qwen3.6/3.8、Gemma 4） | 模型自己草拟多 token，一次前向验证 | 需要模型带 MTP head |
| 解码 | 投机解码：MTP / DFlash / EAGLE-3 / draft model | 1.5–3× decode；精确拒绝采样可保持分布 | 草稿质量差会拖慢；需验证等价性 |
| 解码 | DFlash 块扩散（Muse Glimmer） | 一次草拟 16 token 块，主模型并行验证 | 需要配套 drafter |
| 缓存 | KV cache 量化（q8/q4） | 长上下文省内存、提吞吐 | q4 可能损质量；要测 |
| 缓存 | Prompt/prefix cache | 多轮/长系统提示复用 prefill | 需引擎支持；注意隐私隔离 |
| 调度 | 连续批处理 / batched sequences | 多请求并发时提高利用率 | 单用户收益有限 |
| 运行时 | MLX / Metal kernels | Apple Silicon 统一内存 + GPU | 模型格式需匹配 |
| 分布式 | MLX distributed / Exo | 多 Mac 跑更大模型 | 64GB 单机不需要 |
| 量化 | 4/6/8-bit、K/IQ-quant、MXFP4/NVFP4、ternary | 降内存、提速度 | 质量/工具调用要逐项验收 |

关键点：**投机解码是“验证”而不是“贪心截断”**。MTPLX 明确使用拒绝采样 + 残差校正；选型时要拒绝会悄悄改变输出分布的“假加速”。

## 2. 引擎候选

| 引擎 | 形态 | 关键能力 | 适合 | 风险 |
|---|---|---|---|---|
| [mlx-serve](https://github.com/ddalcu/mlx-serve) | 原生 Zig 服务；MIT | MLX + GGUF；OpenAI/Anthropic/Ollama API；投机解码、MTP draft、KV quant q8/q4、batched sequences；无 Python | 统一本地后端；兼容现有 OpenAI 客户端 | 新项目；默认 `0.0.0.0`，必须改回环 |
| [MTPLX](https://github.com/youssofal/MTPLX) | 原生 Mac app + CLI；Apache-2.0 | 用模型自己的 MTP 头做精确投机解码；Qwen3.8/3.6/3.5、Gemma 4、Ternary Bonsai 2 | Qwen MTP 模型的速度上限 | 只覆盖带 MTP 的模型；需要按其支持矩阵选权重 |
| [gmlx](https://github.com/asher/gmlx) | GGUF-on-MLX；BSL 1.1 | K/IQ GGUF、MXFP4/NVFP4/ternary；投机解码、prompt cache、KV quant；LoRA | 已有 GGUF 资产；长上下文 prefill | **BSL 许可证**，商用前要确认 |
| [llama.cpp](https://github.com/ggml-org/llama.cpp) | C/C++；MIT | 1.5–8 bit 量化、Metal、MTP 已合入（PR #22673）、KV quant、广泛模型支持 | 稳定兜底、GGUF 生态 | 新模型 Day-0 支持略慢；需自己调参 |
| [mlx-lm](https://github.com/ml-explore/mlx-lm) | Python 库；MIT | 原生 MLX、LoRA、`mx.distributed` | 现有 sidecar 基线、实验 | 非服务化；需自己写 HTTP/并发 |
| LM Studio / Ollama | GUI/服务 | 易用、模型管理 | 快速试用 | 新模型/新优化跟进慢，服务端可控性弱 |

厂商数据（仅供筛选，不是本机结论）：

- mlx-serve：M5 Ultra 256GB 上 Qwen3.6-35B-A3B 4-bit 424 tok/s、Qwen3.8-27B 4-bit 242 tok/s；M4 Max 比 v26.8 快 10–51%。
- MTPLX：Qwen3.6-27B 81.7 tok/s、Qwen3.8-27B 87.6 tok/s、Qwen3.5-4B 227.8 tok/s（M5 Max 128GB）；整体约 1.6×（16GB M4 mini）到 2.24×（M5 Max）。
- gmlx：M5 Max 上 prefill 快于 llama.cpp；投机解码 + prompt cache + KV quant 齐备。
- Muse Glimmer：M4 Max 无投机 23.7 tok/s → DFlash 37.8 tok/s（1.5×）；M5 Max 26.6 → 50.2（1.8×）。

## 4. 明天先做的同机基准

同一台 M2 Max 64GB、同一套云熙系统提示词 + 工具 schema，跑：

**引擎**
- 现有 `sidecar/local_llm_server.py`（MLX 基线）
- mlx-serve（MLX 4-bit + 可选 GGUF）
- MTPLX（Qwen3.6/3.8、Gemma 4）
- llama.cpp / gmlx（GGUF 路径，许可证先确认）

**模型**
1. Qwen3.8-27B-4bit
2. Qwen3.6-35B-A3B-4bit
3. Muse Glimmer-30B-4bit
4. Gemma 4 26B-A4B（现有）
5. Qwen3.5-9B（现有，低延迟基线）
6. Ternary Bonsai 2 27B（可选）

**指标**
- 首 token 延迟（4k / 16k / 64k 上下文）
- decode tok/s、prefill tok/s
- 峰值内存、加载时间、空闲卸载
- 工具调用：完整 schema、参数正确率、失败恢复
- 中文人格/陪伴质量、事实性、长上下文
- 流式/中断/并发稳定性
- 断网与回环守卫（确认没有云请求）

**通过条件**
- 工具调用不越权、不伪造成功；
- 私密会话本地失败时明确报错，不回落云端；
- 许可证允许当前用途（尤其 gmlx 的 BSL）。

## 5. 对适配器/分配器的直接影响

- 适配器字段至少要有：`backend`（mlx-server / mtplx / llama.cpp / openai-compatible / anthropic）、`model`、`context`、`tools`、`vision`、`quant`、`local`、`license`、`runtime_status`。
- **工具协议要按模型适配**：Gemma 4 的 tool parser、Qwen 的 XML、Muse Glimmer 的 ATEM 都不同；不能只换 endpoint。
- **推理通道**：有的引擎把 thinking 放在独立字段/通道，适配器要统一成 `content + reasoning`，不能把 thinking 混进正文。
- **生命周期**：本地模型的加载/卸载/端口/健康检查由适配器管；默认只绑定 `127.0.0.1`。
- **隐私闸门**：`local-only` 会话不允许构造云端客户端；网络工具在本地模式默认禁用。
- **任务分配器**：聊天走本地、任务走云端；但“从私密聊天触发的任务”默认先问一次，只发最小上下文。

## 7. 无限制版 Qwen3.8（2026-10-24 追加）

“无限制版千问3.8”不是官方发布的单一模型，而是社区基于 `Qwen/Qwen3.8-27B` 做的 **abliterated / Heretic / uncensored** 衍生权重。它们主要减少拒答，不是真正“没有限制”，也不会改变底层能力与工具权限。

### 7.1 主流变体

| 变体 | 方法 | 特点 | 体积/格式 | 下载量* |
|---|---|---|---|---|
| [Huihui-Qwen3.8-27B-abliterated](https://huggingface.co/huihui-ai/Huihui-Qwen3.8-27B-abliterated) | 定向 abliteration；只处理 18–51 层，保留前 15 层；MTP 与视觉未改 | 生态最成熟；作者自述是“crude proof-of-concept” | bf16 + GGUF + MLX 社区量化 | 2.39M（GGUF） |
| [JonathanColetti/Qwen3.8-27B-Uncensored](https://huggingface.co/JonathanColetti/Qwen3.8-27B-Uncensored) | Heretic：拒答数与 KL 散度共同优化；只改 64 个 attn/mlp 模块；显式把 15 个 `mtp.*` 张量接回 | 作者明确写“substantially reduced, not eliminated”；保留 MTP、视觉、262k 上下文；有 imatrix GGUF | bf16 + GGUF | 2.4M（GGUF） |

### 7.2 关键差异

1. **MTP 是否保留**：abliteration 用 transformers 重存时容易丢掉 `mtp.*` 张量，但 `config.json` 仍声明 MTP；JonathanColetti 明确做了张量清点与回接，HauhauCS 也声明保留。**如果要用 MTPLX 加速，必须选显式保留 MTP 的版本，否则速度优势不存在。**
2. **激进程度**：Aggressive 追求“直接回答”，作者自己也建议“reliability-critical, long-context agentic work 用 Balanced 更稳”。这类模型可能牺牲澄清、拒绝不当工具调用和长任务稳定性。
3. **视觉**：Huihui 与 JonathanColetti 都声明保留视觉；Aggressive 通过单独 BF16 projector 提供视觉。实际效果需复测。
4. **“无限制”不等于无风险**：它只降低拒答概率，不会让模型获得事实性、工具正确性或安全性；工具审批仍必须由 Rust 层强制执行，不能交给模型。

### 7.3 对云熙的建议

- **只用于“私密聊天”profile**，不要给 `run_command`、`computer_act`、邮件发送等工具；这些仍走官方模型 + 审批。
- 私密 profile：本地 MLX、无网络工具、无云端摘要、独立会话库；可接受 NSFW/角色扮演，但保留应用层的最小安全策略（自伤/违法/真实伤害等高风险内容不自动执行）。
- 优先评估 **JonathanColetti**（方法可解释、MTP 保留、作者给出未消除拒答的实测）与 **Huihui**（生态成熟）；**Aggressive 不作为默认**。
- 基准要加：拒答率、工具调用正确率、中文人格质量、长上下文、MTP 是否真的生效、视觉是否退化。
- 许可证为 Apache-2.0（衍生权重），但输出内容与用途责任仍在部署方；不要随 App 分发权重。
