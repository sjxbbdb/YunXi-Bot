# 开机问候触发修复方案（已批准）

## 已确认的原因

2026-10-19 09:26 系统开机后，LaunchAgent 已正常运行，邮件巡检也在继续。开机问候没有进入时间、天气或模型环节：同日 00:13 的后台进程启动已经写入当日问候标记并取得通知回执，`startup_care::claim` 仅按自然日去重，因此拒绝了早晨真正开机的问候。

这符合当前 ADR D158/D161 的“每日首次进程启动”，但不能区分电脑开机与部署、崩溃后的进程重启。

## 已批准调整

- 将触发去重依据改为 macOS 的实际开机批次：每次真正开机后，后台首次运行可以生成一次问候；同一批次内后台重启、重新部署、跨日或睡眠唤醒均不再触发。
- 使用系统提供的稳定开机标识，读取失败时明确记录原因并跳过，不用进程 PID 或当前日期冒充开机标识。
- 启动前持久记录本次尝试，仍保留崩溃或通知状态不明时不盲目重发的规则。旧记录若属于当前开机批次，继续视为已尝试；此前开机批次的记录不占用本次机会。不删除、不改写历史台账。
- 继续完整加载人格与画像、获取时间和天气、调用 DeepSeek 生成内容，沿用预算、时效、工具门禁与通知回执。无需修改人格资料或原生应用。
- 同一天真正重启电脑也可问候一次。用户已明确批准取代原先“自然日最多一次”的语义，架构记录见 ADR D162。

## 改动与验收范围

修改启动问候的共享入口、去重测试以及 README/ADR/功能说明；沿用现有审计事件和系统工具，不增加依赖。先写回归用例覆盖：前一开机批次的凌晨记录不挡住新开机、同批次重启不重复、同批次跨日不重复、旧记录兼容、标识读取失败及崩溃恢复。

通过完整格式、构建和测试后备份并更新后台，观察当前真实开机批次自行完成取材和通知。不会通过删除去重记录或手动伪造通知来宣称自动链路通过；无法在不重启电脑的情况下验证下一次真实开机，需在后续实机启动中复核。

## 实施结果

已按方案修复并部署，回归、真实取材与通知及后台重启去重验证通过；详见[功能验收](开机关心与主动冒泡-20261018.md#2026-10-19-开机批次修复验收)。下一次整机开机尚未实测。
