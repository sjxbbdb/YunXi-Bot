## 发现并修复的问题

首次冷启动时，CLI 只等待 Laya 端口监听，没有等待权重加载与预热完成。首轮11个请求全部停在输入分类，尚未进入工具执行。

`ensure_decider_running` 现在在新启动和复用已有服务两条路径上检查 `/health`，最多等待约60秒；未就绪时明确报错，原有分类失败停止行为不变。补充“先 degraded 后 ok”与不可达端点有限等待的回归测试。没有改变模型权重、路由判据或审批策略。

修复后的首个请求包含冷启动，约8.74秒完成。其余耗时包含 DeepSeek 请求及工具执行，不能视为工具自身性能基准。

## 多步任务与失败路径

复用现有 `e2e_local_task.py`，以真实 DeepSeek 和基础 Laya 复验，42/42项检查通过：

- 读取规则 → 选择方案 → 写入 → 回读，独立核对最终文件。
- 决策服务失联时暂停且不写文件，提供人工业务答案后续跑。
- 显式拒绝写入后文件不产生，任务不报成功。
- 文件不存在时错误入账，不编造文件内容，不报成功。
- 工作区外只读调用经过已有 Laya 门禁，实际结果遵守门禁判定。
- 台账重新加载，以及6个原有证据选择样本。

`cargo test` 1092/1092通过（CLI 83、core 1009）；新增验收脚本的3项自检通过。现有 Rust 回归覆盖非法参数、缺失路径、无人应答、工具拒绝与失败回传、重复调用、只读并行、命令超时和 Unix 进程组回收。格式、debug/release构建及 Clippy `-D warnings` 均通过。

日常 `启动.command` 优先使用 release 二进制，已重新构建并通过这个入口实际调用 `now`，3项检查通过，确保日常入口包含本轮修复。入口检查脚本最初把台账头行当成事件，已修正筛选并重新验证；该次检查异常不计入通过结果。

## 结论范围

已验证的是这台 Mac 上当前版本的内置工具调用和上述失败路径，不是7×24稳定性或任意自然语言任务的正确率保证。当前没有配置外部 MCP，本轮没有验收外部 MCP 服务。搜索未配置博查，因此结果仅覆盖 DuckDuckGo Lite；网页与搜索的外部服务仍可能变更或故障。

本轮不改变审批策略。预批准测试证明授权后的调用能工作，显式拒绝测试证明对应拒绝规则生效；不能据此消除此前发现的 Laya `auto` 误放行风险，也不能把 Mac 的进程管理说成 OS 文件隔离。
